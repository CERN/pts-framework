PyPTS — Migration Status

What still needs to be done to fully port the old engine to the new architecture. Originally derived from porting_changes.md review findings (R-*) and parity audit (M-*). Re-verified against the code on 2026-09-15; findings that were fixed or no longer apply have been removed, so the IDs have gaps. All review findings (R-1..R-6) are closed. Branch: architecture_refactor · September 2026.

Parity gaps vs old_code

Capabilities present in the old engine that are still missing from the new architecture. Fix in Phase 1 (before v0.3.0) unless noted.

M-2b · important No scripted/non-interactive path

No --recipe autoload, no "load X, run Y, exit with code N" for CI/headless benches. The roadmap Phase 1 CLI items gesture at this but do not record the loss explicitly. Needed before the framework can be used in CI pipelines.

M-3 · important Per-step inputs/outputs reach the frontends only on FAIL, as flattened text

On a FAIL, build_fail_reason() writes the inputs and outputs into error_info (capped at 8 items each), which the CLI, the GUI's ResultsPanel and the step-table tooltip show. A PASS/DONE step shows no measured values at all: StepOutcome still has no field for them, and the structured values travel only in StepExecuted, which goes to the Report. The old result tree showed every measured value inline.

Other pending Phase 1 items

Blocker One-response-per-request fix for multi-value responses

Old UserLoadingStep (and UserInteractionStep's loadFile_key) read a second value, a file path, off the same response queue after the first answer. UserPromptResponse carries exactly one value, so the file pick must become its own typed request before UserLoadingStep can be ported. (The other old cases no longer apply: UserWrite got its own UserTextRequest, and the serial-port ID mode was dropped.)

Phase 1 CLI StopHmi timing gap

The CLI main thread is parked in input(), so a StopHmi from CORE is only noticed after the next Enter key. Pre-existing asymmetry. Fix before v0.3.0 tagging.

Future Remote CORE (frontend on one machine, engine on another)

Wanted, but has no flag today. Needs event fan-out from CORE to several HMI channels; commands stay point-to-point. A string-topic event bus was considered and rejected. Added when the feature is designed, not before.
