PyPTS — Migration Status

What still needs to be done to fully port the old engine to the new architecture. Derived from porting_changes.md review findings (R-1..R-6) and parity audit (M-1..M-7). Branch: architecture_refactor · September 2026.

Code-review findings (R-1..R-6)

Spotted during the August 2026 porting session. None fixed yet; fix in Phase 1.

R-1 · critical process_outputs() sits outside run()'s except block

A judging failure (missing output key, unknown output type, non-numeric range) escapes the step — no StepFinished (GUI row stuck on "Running…"), no SequenceFinished, RunFinished(ERROR) with zero outcomes blamed on the Sequencer. Test blind spot: judging tests never go through run().
Fix: move process_outputs() inside the try in step/step.py.

R-2 · critical PythonModuleStep re-imports the user's module on every step call

The old engine imported once per process, so module-level state persisted across steps. Re-importing per step breaks that contract and writes __pycache__ beside the operator's recipes on every step.
Fix: cache the imported module object in step/step.py (load_python_module per sequence, not per step).

R-3 · important Non-RecipeError load failures escape to the poll catch-all

Triggers: None values for steps:/globals:/ locals:, steptype: 5, scalar step entries. Operator sees nothing. Needs type validation in from_document + defensive except Exception → report_own_error in CORE.

R-4 · important A dead/wedged CORE makes the GUI window unclosable

allow_close is only ever set by the StopHmi handshake. If CORE never sends it, the operator cannot close the window. The CLI already has wait_until_stopped with a bounded-grace fallback; the GUI needs the same.

R-5 · important LoadRecipe accepted mid-run

Swaps the recipe under the running sequence and repaints the step table with new IDs; the rest of the run's events miss their rows. Reachable from the CLI. CORE should refuse LoadRecipe while a run is in flight.

R-6 · trivial Stray -1 typo in a startup.py docstring line

In the uncommitted --no-debug-monitor edit.

Parity gaps vs old_code (M-1..M-7)

Capabilities present in the old engine that are missing from the new architecture with no tracking elsewhere. Fix in Phase 1 (before v0.3.0).

M-1 · design decision needed UserPromptRequest.options shape — decide before porting User* steps

The old format was a list of single-entry dicts: - 'yes': 'Press me'; empty caption → key.capitalize(); no options → one unlabelled button. The new options: tuple[str, ...] collapsed this. This is baked into a pickled dataclass — the shape must be decided before the User* step port or it becomes a protocol change.

M-2 · important No embedding API

The old run_recipe_app / run_pts / PtsApi are gone. There is no supported way to drive the engine from another Python program. Roadmap Phase 2 plugin plan addresses this.

M-2b · important No scripted/non-interactive path

No --recipe autoload, no "load X, run Y, exit with code N" for CI/headless benches. The roadmap Phase 1 CLI items gesture at this but do not record the loss explicitly. Needed before the framework can be used in CI pipelines.

M-3 · important Per-step inputs/outputs no longer reach any frontend

StepOutcome has no field for them. The old result tree showed every measured value inline. The operator's only view of measurements is gone. Must be added to StepFinished and rendered in both the GUI's ResultsPanel and the CLI output.

M-4 · important Report TDMS plots absent

The old report.py discovered .tdms files in the run folder and embedded FFT + time-domain matplotlib plots in the HTML. This is absent from every Report TODO. Roadmap Phase 4.

M-5 · important Abort does not produce per-step STOP results

Old code marked the interrupted step and every un-run step STOP (table grayed, CSV rows present). New code stops emitting — remaining rows stay "Pending" with no explanation. Implement alongside the Report port: abort should close open rows with STOP and write them to the CSV.

M-5b · trivial Window title does not show recipe name

The old engine set the window title to "PTS: <recipe>" on load. Matters when several bench windows are open simultaneously. One-line fix in gui/main_window.py on RecipeLoaded.

M-6 · important indexed: true on a step input is silently ignored

The step runs once with the whole list as the value — contradicts the loader's "loud refusal" principle. Make it a load-time RecipeError until IndexedStep expansion is ported.

M-7 · important Step-level continue_on_error: makes a recipe fail to load

The old engine accepted it on 6 of 10 step types; comprehensive_recipe.yml carries it 8 times. In the new architecture it causes a load-time error on some types. Tolerate-and-warn like the header-level key until the policy is designed.

Other pending Phase 1 items

Blocker One-response-per-request fix for multi-value responses

Some old_code interaction steps read a second value off the same response queue after the first answer (a file path, a measured value, a (port, baudrate, IDN) triple). UserPromptResponse does not model this. Each follow-up must become its own typed request before UserLoadingStep can be ported.

Phase 1 CLI StopHmi timing gap

The CLI main thread is parked in input(), so a StopHmi from CORE is only noticed after the next Enter key. Pre-existing asymmetry. Fix before v0.3.0 tagging.

Future Remote CORE (frontend on one machine, engine on another)

Wanted, but has no flag today. Needs event fan-out from CORE to several HMI channels; commands stay point-to-point. A string-topic event bus was considered and rejected. Added when the feature is designed, not before.
