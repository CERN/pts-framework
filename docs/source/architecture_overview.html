PyPTS — architecture of the new code

How the framework is put together on the architecture_refactor branch: which processes and threads exist, who spawns them, how modules talk, how the watchdog decides a module is gone, how a recipe becomes a report — and what imports what.

Scope: src/pypts/** excluding old_code/ 95 modules · ~17 000 lines Python ≥ 3.11 import name pypts · distribution pts-framework

Overview

PyPTS runs YAML recipes — ordered sequences of steps — against hardware on a test bench, and writes a report. The refactor rebuilt the framework around three rules that everything else follows from:

Modules never touch each other

No module holds a reference to another, and no module owns a queue it did not receive. Everything goes through CORE, the mediator — with exactly one exception: log records, which go straight to the Logger so that logging survives a dead CORE.

A message is a frozen value

Every message is a @dataclass(frozen=True, slots=True) of plain values, declared in the module that owns its link, and a member of that link's union type. Every handler is a match closed with unhandled(), so a forgotten message raises instead of vanishing.

One process boundary, not four

Only HMI↔CORE crosses processes, so only its messages are pickled. The Sequencer and the Report are threads of the Core process, and their links are plain queue.Queue — which is why they may carry live objects such as a parsed Recipe.

Three consequences are worth carrying into everything below:

  • The framework is polling, not blocking. Every event loop drains its inbox with get_nowait(), does its periodic work, and sleeps 10 ms. Nothing waits on a queue except the Logger, which has only one job.
  • A sequence runs on a worker thread of its own, so the Sequencer's event loop keeps turning while a step is executing — otherwise heartbeats stop, StopSequence is never read, and a step waiting for an operator's answer deadlocks.
  • The run log is the system's only shared observability surface. Every QueueWrapper traces itself at DEBUG, so at --log-level DEBUG the log contains every message twice — once from the sender, once from the receiver. The Debug Monitor is a reader of that file and nothing more.

Why spawn, always

startup.main() pins set_start_method("spawn") on every platform, before the first Queue() is built. Two reasons: the configuration notice may have created a QApplication in the launcher process and forking a process holding live Qt state is unsupported; and Windows — where development happens — always spawns, so pinning it makes Linux exercise the same code paths rather than quietly different ones.

Signals and console encoding

Ctrl+C at a terminal raises SIGINT in every process of the foreground group. Each child entry point therefore calls utilities/common.py: ignore_keyboard_interrupt() (SIG_IGN, never a handler that logs — a Python signal handler runs between bytecodes and logging takes locks, so a logging handler could deadlock against a log call the same thread was already making). The launcher deliberately does not: it is the one process that must still hear Ctrl+C, and it then runs the orderly shutdown it owns. Every entry point also calls pin_ascii_console(), so no message can fail a run on its encoding; the log file keeps its UTF-8.

--mode connect is accepted by argparse but has no branch. It falls through the if args.mode == "gui" and silently starts the CLI. It is not implemented.

3. Shutdown

There is exactly one way the application ends, and every path funnels into it. A frontend never leaves of its own accord: it asks.

1
Somebody asks The operator closes the window or types exit → HmiClient.request_shutdown() sends ShutdownRequested. The launcher sends the same message in its finally, because it cannot assume the frontend got the chance. CORE's stop_all_modules() is idempotent for exactly this reason.
2
CORE asks everyone to stop, and starts a 5 s clock StopSequencer → Sequencer, StopHmi → frontend. StopReport is held back: the Sequencer may still be finishing an aborted sequence whose StepExecuted / RunFinished / GenerateReport must reach the Report first.
3
The Sequencer stops its run, then itself stop_running_sequence() sets the flag and joins the sequence thread for 2 s. A sequence that will not stop is reported as CRITICAL — teardown has not run and the bench state is unknown — and abandoned. Then SequencerStopped.
4
SequencerStopped releases the held StopReport release_stop_report(), exactly once. The shutdown deadline releases it too, if the Sequencer never answers.
5
CORE leaves when all three have answered — or names those that did not check_stop_status(): all of module_running false → leave. Past the deadline → one ERROR naming the late modules by their operator-facing names, then leave anyway. There is nothing to kill: both submodules are daemon threads, and the HMI is a process the launcher owns.
6
The launcher terminates what is left, then stops the Logger last stop_core() joins CORE for 5 s and terminate()s it if needed. Then StopLogger — a queued message, so the Logger acts on it only after writing everything already in flight — and a 5 s join. The Debug Monitor is deliberately left running.

Two orderly-exit budgets, five seconds each. CORE's SHUTDOWN_TIMEOUT_S covers every module noticing the request, finishing what it is doing and reporting itself stopped; the launcher's CORE_SHUTDOWN_TIMEOUT_S and LOGGER_SHUTDOWN_TIMEOUT_S bound the joins. Core.THREAD_JOIN_TIMEOUT_S (also 5 s) is not a shutdown budget — the thread has already reported itself stopped, so it only covers the return from the loop.

4. The messaging model

One transport: QueueWrapper

messages/queue_wrapper.py holds a single generic class, and it is the transport for every link in the system. It wraps anything with put() and get_nowait() — which is precisely what lets one class serve a process boundary (multiprocessing.Queue) and a thread boundary (queue.Queue).

class QueueWrapper(Generic[Msg]):
    DEFAULT_BATCH = 64                 # one receive() cannot starve the other inboxes

    def send(self, message: Msg) -> None:
        _trace.debug("send %s %r", self.link, message)   # traced BEFORE the put,
        self._queue.put(message)                         # so a message that fails to
        self.sent += 1                                   # pickle is still recorded

    def receive(self, limit=DEFAULT_BATCH) -> Iterator[Msg]:
        ...                                              # get_nowait(); a generator, so a
        self.received += 1                               # caller that stops early leaves
        _trace.debug("recv %s %r", self.link, message)   # the rest queued
        yield message

Four properties fall out of those twenty lines:

  • It never blocks. receive() yields what is waiting right now and returns on Empty. Every event loop in the framework is built on that.
  • The type parameter is the link's union. QueueWrapper[HmiToCore] is what makes mypy able to prove a match is exhaustive.
  • Every wrapper traces itself on its own logger, pypts.trace, at DEBUG — which is why each carries a link name, and why it imports logging directly rather than pypts.logger.log (that module imports this one). It is also the only way to see the Core↔Sequencer and Core↔Report traffic, which never leaves the engine process.
  • Counters are per holder, not per link. A wrapper pickled into a child process gives the child its own sent / received.

Beside it, two names that carry the exhaustiveness contract:

def unhandled(message: Never) -> NoReturn:
    raise UnhandledMessage(f"No handler for message: {message!r}")

Typed Never: if a union member is not matched, the value reaching unhandled() is not Never and mypy fails the build. At runtime it raises rather than dropping the message.

Adding a message — two steps

  1. Declare the frozen dataclass in the link module, and add it to that link's union.
  2. Handle it with a case in the recipient's handler.

Everything else finds you: mypy flags every match that is now incomplete (because unhandled(message: Never) stops type-checking), and tests/unit_tests/test_messages.py drives every member of every union through the real handler and fails until the message has an example and a branch.

Blocking request/response across a process boundary

A step that asks the operator a question has to block; the event loop that will deliver the answer must not. PendingRequests is how those two facts coexist.

# asker - on the SEQUENCE thread                 # event loop - draining the inbox
pending.start(request_id)                        ...
core.send(UserPromptRequest(request_id, ...))    pending.return_caller(request_id, choice)
answer = pending.wait(request_id, ...)
  • Register before sending, or a fast responder wins the race and the answer is dropped. Sequencer.ask_operator() is the only place that knows this ordering, which is why a step just calls runtime.ask() and cannot get it wrong.
  • The waiter polls; it does not sleep once. wait() loops on slot.get(timeout=min(0.1, remaining)) so should_abort is looked at every 100 ms — without which an operator pressing Stop while a question is on screen would wait out the full 300 s timeout. The loop lives in PendingRequests rather than in the caller because the slot is registered once and cancelled once: a caller looping on short waits of its own would cancel its own request on the first empty turn.
  • A returned None is indistinguishable from a timeout, on purpose. The asker treats "declined", "timed out" and "run stopped" the same; ask_or_raise() turns all three into PromptUnanswered, and the step becomes ERROR.
  • The thread that calls wait() must not be the one draining the inbox, or the module deadlocks. This is the single reason a sequence runs on a worker thread.

5. Heartbeats & the watchdog

Both halves of the protocol — the interval, the two thresholds and the module names — are declared together in utilities/heartbeat_manager.py, because they only mean anything as a set: a timeout shorter than the interval declares every module dead, and a module name that does not match the key in CORE's tables is a heartbeat CORE cannot place. The names used to be spelled four times, with nothing checking that they agreed.

ConstantValueJob
DEFAULT_INTERVAL_S1.0 sHow often a module beats. tick() is cheap enough to call every loop iteration and decides for itself when one is due.
HEARTBEAT_TIMEOUT_S5.0 sReported. One WARNING, and the run carries on. Five seconds of quiet is as likely to be a stall as a death — a large recipe parsed inline, a native dialog starving a timer, a machine that swapped — and a warning that is wrong costs nothing.
HEARTBEAT_FATAL_S15.0 sActed on. Three times the timeout, deliberately: the two thresholds do different jobs and must not share a number. This one aborts a technician's test, so it must not be wrong.
HMI, SEQUENCER, REPORTthe three CORE watchesEach module puts its own name on every Heartbeat as source, which is what lets one CORE handler serve all three links instead of three that differ only in which dict key they write.
COREthe one that beats backNot in the three above: those are the modules CORE watches, and it does not watch itself.

Only the HMI watches CORE. The Sequencer and the Report are threads of CORE's process — they cannot outlive it, so a heartbeat towards them would watch for something that cannot happen and double the trace traffic doing it. The HMI is the one module in a process of its own, and so the one that can be left running with nothing on the other end of its link: a CORE killed outright, or one whose event loop wedged while the process stayed up.

What CORE does about silence

Core.do_periodic_tasks(), every 10 ms:

  1. Beat first. hmi_heartbeat.tick() before everything else, so a looping CORE is always saying so — including all through a shutdown, when the HMI is being stopped and must not conclude from the silence that the engine died under it.
  2. Nothing to watch once shutting down. An early return: every module has been asked to stop and is expected to go quiet, check_stop_status() already has its own budget and already names whoever fails to answer, and without this the fatal branch would re-report the same dead module — and re-send its ModuleErrorReported — a hundred times a second.
  3. last_seen is None → note_a_module_has_not_started(). Never-heard-from is not the same as gone; a module that has never spoken cannot be said to have stopped responding. It waits out the same 5 s threshold, says so once, and does not end the run — a module that never starts at all is caught where it can be caught properly (the launcher's ui_process.join() returns at once if the frontend dies on import, and join_submodules() reports a thread that failed to start).
  4. Past 5 s → one WARNING in the operator's words ("The test engine has stopped responding."), plus two DEBUG lines carrying the measurements. The latch is cleared by note_heartbeat(), which also logs that the outage ended — so the log says an outage finished instead of just going quiet.
  5. Past 15 s → end_run_for_silent_module(), if the watchdog is armed.

The fatal path, and why it reuses the ordinary shutdown

end_run_for_silent_module() tells the operator before anything stops — a window that simply vanishes leaves a technician with a half-finished test and no reason for it. It does so through handle_module_error(), the same path a reported failure takes, with a synthesised ModuleError(severity=CRITICAL, operation="heartbeat"). Then the ordinary stop_all_modules(), unchanged. Nothing new is invented for this case, which is the point: a watchdog that shut down differently from every other exit would be a second shutdown path to keep working. The honest cost is that the five-second budget is spent waiting for a module that will not answer — it is why we are there.

The gate

[watchdog] enabled in config.ini (default true) gates the acting half only. A silent module is reported at WARNING either way. Off is for a developer with a debugger attached to CORE, where a breakpoint in an event loop is indistinguishable from an event loop that has died. Core.__init__(watchdog_enabled=None) asks the configuration — which is what a real run does; a test passes the value explicitly, the way the Report is passed its output_dir, because outside a run there is no launcher to have created a config.

The HMI's side

HmiClient.check_core_is_alive() is the orphan case, and the only reason the reverse heartbeat exists. It uses HeartbeatWatch with the same two thresholds: is_silent() → one WARNING; is_lost() → log.error("The engine has stopped responding, so pypts is closing.") and stop(). It is deliberately not gated by [watchdog] enabled: that flag is about CORE ending a run, and a frontend with no engine behind it has nothing left to do either way. It is silent once running is False — a normal shutdown ends with CORE leaving its loop, so its heartbeats stop by design, and the GUI's QTimer goes on firing.

A watch starts at construction time, not at the epoch. HeartbeatWatch.last_seen is seeded with time.time() because a watch starting at zero reads as silent for fifty-odd years and fires before the first beat can arrive. CORE's table does the opposite for the same reason: it seeds None, because seeding a timestamp asserted that every module had been heard from when CORE was built — at which point the HMI has not even been spawned, and a cold PySide6 import over a network home directory is seconds of perfectly normal startup.

How the Debug Monitor sees liveness

None of CORE's liveness state ever leaves CORE — module_running, last_heartbeat and heartbeat_lost are dicts in core.py, and no message on the core->hmi link carries any of them. It does not have to: every Heartbeat is a message, every message crosses a QueueWrapper, and every wrapper traces itself — so the run log already contains each module's pulse at 1 Hz. debug_monitor/liveness.py folds that stream back into the same state from three sources: heartbeat traces, the *Stopped messages (a module that said goodbye is not one that vanished), and three machine-read DEBUG lines CORE writes on purpose:

log.debug("Heartbeat timeout for module: %s", name)   # prefix, then nothing but the name
log.debug("Heartbeat fatal for module: %s", name)
log.debug("Module is responding again: %s", beat.source)

The derived state and CORE's verdict are computed from the same evidence by different code, so a disagreement between them is a defect worth seeing rather than a display glitch. Modules are discovered, never registered: a name becomes a module the first time it is seen sending on a link, or the first time CORE names it in a liveness line — which is what lets the tool be useful about a part of the system that did not exist when the tool was written.

6. Error handling

Four tools in utilities/error_handling.py, and the split between them is the design: the decorators are the net for what nobody expected; the functions are how a method handles a failure it recognised. The split is deliberately explicit rather than a flag, because which of the two a piece of code needs is a property of where it sits.

ToolBehaviourWhere it belongs
@catch_and_report_errors()Reports and continues; the caller gets None and the loop comes round again.Event loops. A module that dies on one bad message stops answering CORE, stops sending heartbeats, and takes the run with it.

Neither function raises, so the raise site keeps control of what happens next. All four need the object to have a core attribute — that module's outbox — and all four survive it being absent, because an error handler that raises AttributeError while handling an error destroys the one thing worth keeping. send_module_error() then writes both records itself.

What CORE does with a ModuleError

Core.handle_module_error() writes two records: one the operator can read, naming the part of the software that failed and what it said, and one at DEBUG naming the method and the exception type with the traceback under it. The traceback never appears above DEBUG — in the operator's panel it hides the line that matters. Then, unless the severity is only WARNING, it sends ModuleErrorReported to the frontend.

The sender rates its own failure — it is the only one who can — and CORE takes it at its word: LOG_LEVEL_FOR_SEVERITY maps WARNING/ERROR/CRITICAL straight onto logging levels. Logging it and showing it is all CORE does about an error today; what else to do is Phase 1's to settle. Two lookup tables translate protocol names into operator language on the way out: FRIENDLY_MODULE_NAME ("test engine", "report writer", "operator interface") and FRIENDLY_SOURCE_NAME (dotted module → "the recipe reader", "the settings file reader"); an unrecognised source is described as "the software" rather than by its import path.

CORE's own two exceptions to the rules

  • CORE cannot use the decorators. It is the module errors are reported to. Core.poll() wraps the whole drain of one inbox in a try: an UnhandledMessage or anything else is logged and dropped, because letting it escape takes the mediator down and with it every other module's only way of being heard. The cost is that one bad message abandons the rest of that batch — the exception leaves the receive() generator and the remainder stays queued for the next tick. They are delayed, not lost.
  • CORE has no outbox to itself, so report_own_error() builds the same ModuleError by hand and feeds its own handler.

7. Logging

One dedicated process owns the only open handle on the log file and is the single writer. Every other process and thread pushes logging.LogRecord objects onto the shared queue through logging's own QueueHandler; the Logger drains it and writes them out. That queue is what guarantees no parallel writes.

LOG_FORMAT = "%(asctime)s.%(msecs)03d;%(levelname)s;%(processName)s"
             ";%(filename)s:%(funcName)s;%(message)s"

2026-08-12 09:32:58.056;DEBUG;Core;queue_wrapper.py:send;send core->sequencer StopSequencer()
2026-08-12 09:32:58.101;DEBUG;Sequencer;queue_wrapper.py:receive;recv core->sequencer StopSequencer()
  • init_logging() is called once per process, first thing in every entry point. A thread entry point must never call it — the root logger belongs to the process, which is why core_main() configures it and the Sequencer and Report inherit it. With no queue it falls back to a stdout handler, which is what standalone tools and tests get.
  • Logging is %-style, never f-strings (ruff's G004 enforces it). Lazy formatting is why the DEBUG trace costs nothing when the level is higher.
  • logger/logging_rules.md is the authority on what a line says and at which level. In one sentence: INFO and above are written for the technician — exactly what the GUI's log panel shows them — and everything developer-facing is DEBUG.
  • Lifecycle wording is fixed and names its module: <NAME> module starting. (DEBUG) / started. (INFO) / entered its main event loop. / left its main event loop. / stopping. / stopped. (INFO), where <NAME> is one of LAUNCHER LOGGER CORE SEQUENCER REPORT GUI CLI.
  • The Logger's queue is the one queue in the framework carrying two kinds of item, so it is the one place where "anything else" is a meaningful answer: not a LoggerControl → it is a LogRecord. A late StopLogger from another module cannot cut the final drain short.
  • Nothing may take the Logger down: handle_item() and write_record() both swallow and report to stderr, and the loop ignores KeyboardInterrupt.

Two temporary decisions, both with revert TODOs in the roadmap: the shipped [logging] level is DEBUG for the duration of the refactor (so every run carries the message trace and the Monitor always has something to read), and the Debug Monitor is on by default. Both go back to opt-in before v1.0.

8. From recipe file to report

1
The operator opens a file GUI toolbar or load_recipe <path> → HmiClient.load_recipe() → LoadRecipe.
2
CORE parses and validates — validation gates execution Recipe.from_file() → recipe_parser.load_recipe(). On failure the Sequencer gets nothing at all; the operator sees it through the ModuleError path. On success: UseRecipe(recipe) to the Sequencer — the live object, one process, nothing copied — and RecipeLoaded(summary) to the HMI.
3
The parsing pipeline, in order read → parse YAML (document 1 is the header, the rest are sequences) → normalize (the recipe language is case-insensitive; keys and structural values are lowercased once, so everything downstream stays strict) → validate (every problem in one RecipeError, so the author fixes the file in one round trip) → check the framework version (warn-only) → apply defaults → expand Indexed steps → build Recipe → Sequence → Step through the registry.
4
The operator presses Start StartSequence(name) → CORE → RunSequence(name) → Sequencer.run_sequence(), which refuses if one is already running and otherwise starts the Sequence thread.
5
The Sequencer builds the Runtime and emits RunStarted The Runtime gets the recipe's globals plus three seams: emit = the outbox's send, should_stop = the stop flag, ask = ask_operator. emit is then wrapped by make_metadata_watcher() so a change to a global named in report_metadata becomes a RunMetadata — the Report cannot read globals, since it is a thread fed by events while the globals live on the sequence thread. The step layer knows nothing about this and emits what it always emitted.
6
step.run_sequence() runs the body SequenceStarted → Step.run_steps(sequence.steps) → in a finally run_steps(teardown_steps, run_to_end=True) → aggregate → SequenceFinished. Free of any queue or thread, so a future nested-sequence step can call it for a nested sequence exactly as the Sequencer calls it for the top one.
7
CORE fans the events out as they arrive RunStarted / SequenceStarted → Report and HMI. StepStarted / StepFinished / SequenceFinished → HMI only. StepExecuted → Report only. RunFinished → both, immediately followed by GenerateReport to the Report. The same object is relayed rather than repacked, so nothing is lost on the way.
8
The Report writes as it goes One folder per run, <reports_dir>/<timestamp>_<recipe>, created on RunStarted. Each StepExecuted appends one row and flushes — so a run that crashed keeps what it had. On RunFinished: close, rewrite_csv() to backfill the verdict and the metadata that were unknown when the early rows were written, and rename_run_dir() to append the serial number to the folder name (the serial simply does not exist when the folder is created).
9
The HTML is built from the rows, then announced Every run-level value is on every row, which is what makes report.html regenerable from report.csv alone — point rows_from_csv() at a past run and render it again. ReportGenerated → CORE → StatusChanged + ReportReady(report_path, report_dir) → the GUI's "Open report folder" button.

The step lifecycle

Owned entirely by the base class. A subclass overrides _step() and nothing else.

resolve inputs  ->  _step()  ->  judge outputs  ->  StepResult

Step.run() is the one place in the execution layer that catches broadly, because turning an exception into data is its job — and it nets the output judging too, not only _step(). It emits three events per step: StepStarted before the work, then StepFinished (flat, for the frontend) and StepExecuted (rich, for the Report) — in that order, so the frontend's event is never held up by the record-keeping.

PhaseRules
inputsAn entry that is not a mapping is the value: a: 2. The only other source is {type: global, global_name: ...}. An unknown type raises rather than being left in place as a weird argument. No type coercion anywhere: '45' stays a string, 45 an int.
_step()Returns a dict judged key by key; any other value is wrapped as {"output": value}; None becomes {}. Raise to fail the step.
outputspassfail, equals, range judge and set the verdict; pass says this output is not a measurement (verdict DONE); global stores it in the run's one scope and leaves the verdict alone. No judging entry at all → DONE. When several entries judge, the last one wins — kept from the old engine for parity, and a recorded TODO. Judging gets its own try, because a recipe declaring an output the step never returned must be an ERROR on that step, not an exception unwinding run_steps() and abandoning every later step without even the SKIP row.
StepResultThe rich, engine-internal object; it holds the live Step and must never cross the HMI boundary. to_outcome() is the pickle-safe projection that does. error_info carries either the full traceback (ERROR) or the operator's failure reason (FAIL/SKIP), because that is the field the step table's tooltip, the CLI line and the CSV already read — one sentence reaches all four places and the log.

A FAIL reason is built for the technician, not the developer: the failing checks first (voltage = 4.2, expected between 4.9 and 5.1), then the inputs the step was given and the outputs it produced — the two things needed to tell a bad unit from a bad test setup. Values are capped at 80 characters and lists at 8 items, so one bad step cannot turn a log line into a ten-kilobyte paragraph in the panel, the tooltip and a CSV cell at once.

run_steps() — the sequence policy, in one place

  • An ERROR or a FAIL is recorded and the sequence carries on. That is continue_on_error: True, the default: one bad step does not decide for the other nineteen.
  • A step with continue_on_error: false ends the run when it errors or fails. Per step and nowhere else — there is no recipe-level and no globals form, which is exactly what the old engine's three disagreeing sources of truth were. The old per-step critical override is dropped with them.
  • The stop flag is checked between steps, never inside one, so a step can leave its hardware in a known state. It stays a separate branch from the verdict, so Stop still ends a run at once even though an ERROR on its own does not.
  • Whichever of the two ends the list early, every remaining step is still run with a skip_reason rather than dropped: it emits its events and comes back SKIP, so the step table settles every row and the report has a row per step however the run ended. SKIP is the lowest ResultType, so this cannot change what the sequence aggregates to.
  • run_to_end=True disables both early exits. Teardown callers pass it: cleanup runs after an abort and after a halt, and one failing cleanup step must not skip the rest of the cleanup — which is the opposite of what teardown is for.

Step types

step/registry.py is a plain dict — the replacement for the old factory's eval() over the steptype string, which was arbitrary code execution driven by a recipe file with a NameError as its only diagnostic. A recipe can only select from this table, and an unknown name gets an error listing what would have worked. build_step() splats every key except steptype into the constructor, so an unknown key is a TypeError at load time rather than a surprise at run time. Keys are lowercase: the YAML spelling is case-insensitive, and the YAML names drop the classes' Step suffix.

The recipe format lives in one importable file

recipe/rules.py holds definitions and nothing else: HEADER_REQUIRED, HEADER_DEFAULTS, SEQUENCE_REQUIRED, SEQUENCE_DEFAULTS, STEP_REQUIRED, STEP_TYPE_REQUIRED, STEP_COMMON_DEFAULTS, STEP_TYPE_DEFAULTS, INPUT_TYPES, OUTPUT_TYPES, EXPANDED_STEP_TYPES. validator.py checks against them, recipe_parser.py applies them, and a unit test pins STEP_TYPE_REQUIRED's keys to the registry's. version in a recipe header is the pypts version the recipe was written for, not a version of the recipe; a major.minor mismatch is a notice the operator sees, never a refusal.

The Debug Monitor's one-way rule

Nothing in core/, sequencer/, report/, messages/, logger/ or hmi/ may import helper_applications/debug_monitor/. It depends on the framework; the framework must never depend on it. The launcher starts it with subprocess.Popen on a module string for exactly this reason. A --mode debug console existed here once and was removed, because it gave the software two shapes — the product, and the product plus a tap — and anything only visible in the second shape is invisible on the machine where it matters. What that buys, beyond keeping one build: ordering is free (every process funnels through the single-writer Logger, so the order of the file is the order of the system), and replay is free (the same parser reads a run that finished last week).

The four interesting edges

messages → recipe

core_sequencer_communication.py imports Recipe, because UseRecipe carries one. The message layer therefore depends on the data layer — legal only because this link never crosses a process boundary and nothing is ever pickled.

recipe ↔ step, resolved two ways

logger ↔ messages, broken by a plain logger

logger/log.py imports QueueWrapper and the Logger's control messages. So queue_wrapper.py cannot import log; it takes logging.getLogger("pypts.trace") instead.

PySide6 has exactly one door

  • QueueWrapper[Msg].

Everywhere else the house style is the opposite: plain, old-school, readable Python — an if/else over a conditional expression, a named local over a clever one-liner, a loop over stacked comprehensions. SIM108 and N818 are disabled in ruff for exactly that reason.
