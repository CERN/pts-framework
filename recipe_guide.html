PyPTS Recipe Guide

Purpose. The definitive reference for what a recipe is and what the current framework does with it. One document, one version of the truth.

1. The model in 30 seconds

A recipe is a multi-document YAML file:

document 1        recipe header   — name, version, description, main_sequence, globals, report_metadata
document 2..N     sequences       — each: sequence_name, description, steps, teardown_steps

A sequence is an ordered list of steps. A step has a steptype (which kind of step it is, §10), a step_name, the fields its type needs, inputs (where its arguments come from, §6) and outputs (what to do with what it returned, §7).

One variable scope: globals, for the whole run. Steps never talk to each other directly — one stores a value with a global output, a later one reads it with a global input. Anything narrower is a step's own inputs and outputs.

Every step produces one ResultType. A sequence's result is the most severe of its steps' (§8).

One main sequence, any number of groups. main_sequence is the sequence that runs. Every other sequence document is a group of steps that main — or another group — calls with a steptype: Sequence step, as often and as deep as needed (§10).

Recipe
└── Sequence "Main"
    ├── steps           run in order
    └── teardown_steps  always run afterwards — after a pass, a failure or a stop

The recipe language is case-insensitive: Step_Name: is step_name:, and steptype: pythonmodule is PythonModule. What you name keeps its case — sequence, step, input, output and global names, module, method_name.

2. File anatomy

A whole recipe — header, a main sequence, and one group it calls:

name: LED driver acceptance
version: '0.2'
description: Checks the LED driver board at 5 V
main_sequence: Main
report_metadata: [serial_number]
globals:
  target_voltage: 5.0
---                                    # YAML document separator
sequence_name: Main
steps:
  - steptype: UserWrite
    step_name: Serial number
    message: Scan or type the serial number.
    outputs:
      output: {type: global, global_name: serial_number}
  - steptype: PythonModule
    step_name: Check 5V rail
    module: led_tests.py
    method_name: read_voltage
    inputs:
      channel: 1
      target: {type: global, global_name: target_voltage}
    outputs:
      voltage: {type: range, min: 4.9, max: 5.1}
teardown_steps:
  - steptype: Sequence
    sequence_name: Power off
---
sequence_name: Power off
steps:
  - steptype: Wait
    step_name: Settle
    wait_time: 0.5

Loaded with yaml.safe_load_all — document order is significant. Document 1 is the header; every following document is a sequence, named by its sequence_name. A recipe kept under resources/ also carries SPDX header comments (REUSE).

Every load checks the whole file and reports every problem in one error, each at a location you can find: sequence 'Main', steps[2] 'Check 5V rail': method_name: Field required — steps counted from 1, as the step table counts them.

3. Recipe header

name: LED driver acceptance      # required; shown in the GUI and the report
version: '0.2'                   # required; the PyPTS version the recipe was written for
description: Checks the LED driver board at 5 V
main_sequence: Main              # the sequence that runs; empty = the first one
report_metadata: [serial_number] # globals stamped on every report row
globals:                         # the run's variables and their starting values
  target_voltage: 5.0
  tolerance: 0.1
FieldRequiredPurpose
nameyesGUI header, report metadata
versionyesThe PyPTS version the recipe was written for. Its major.minor is compared with the running PyPTS; a mismatch is logged and shown to the operator, and the recipe still loads. Quote it ('0.2'); a bare 0.2 also works
descriptionno ("")GUI, log
main_sequenceno (the first sequence)The sequence that runs; the others are groups it calls with Sequence steps (§10). No Sequence step may call it. Matched without case
report_metadatano ([serial_number])List of global names whose values the report stamps on every CSV row and in the HTML header; [] for none. Each entry is a name written as text — a number is refused
globalsno ({})Flat name: value mapping: the run's variables and their starting values

Any other header key is ignored.

serial_number is not injected. The engine has no concept of a serial number. Capture it with a UserWrite step that stores it in the serial_number global, as the example in §2 does; the report picks it up through report_metadata. resources/recipes/Development_recipes/userwritestep_demo.yml shows it running.

4. Sequence document

sequence_name: Main          # required; what main_sequence and Sequence steps name
description: Main test flow
steps:                       # required; at least one step
  - ...
teardown_steps:              # optional; runs after the steps, whatever happened
  - ...
FieldRequiredPurpose
sequence_nameyesThe name; unique in the file regardless of case — Main and main are the same name
stepsyes, at least oneThe steps, run in order
descriptionno ("")GUI, log
teardown_stepsno ([])Run after steps after a pass, a failure or a stop. Inside a teardown everything runs to the end: continue_on_error: false does not stop it

Any other sequence key is ignored (the Recipe Creator warns about it). Removed on purpose: setup_steps (put those steps at the front of steps), locals (use globals), and parameters / outputs (a called sequence shares the run's globals).

5. Step — common fields

- steptype: PythonModule     # required; selects the step type (§10)
  step_name: Check 3V3 rail  # required; shown in the step table and the report
  description: ...           # optional
  id: my-stable-id           # optional; a fresh id if absent
  skip: false                # optional; true records SKIP without running it
  continue_on_error: true    # optional; see §9.1
  inputs: {}                 # optional; §6
  outputs: {}                # optional; §7
  # ... the fields of the step type (§10)
  • An unknown key is refused when the recipe loads — every key becomes an argument of the step, so a typo (skipp: true) is an error, not a silently ignored line.
  • skip and continue_on_error take true/false; a text field takes text or a number (§12).
  • Two step types differ: a Sequence step is named after the sequence it calls and takes no step_name, id, inputs or outputs; an Indexed step puts inputs and outputs on its template (§10).

6. inputs — where arguments come from

inputs:
  channel: 1                                           # a literal: the value itself
  label: 'rail A'
  target: {type: global, global_name: target_voltage}  # the value of a global
Written asValue the step gets
anything but a mappingthe value itself, as written
{type: global, global_name: <name>}the global's value when the step runs

A mapping must name its type; global is the only one. No type coercion: '45' is the string "45", 45 the int. A global name is found exactly as written — 7 and '7' are two globals.

Repeating a step over several parameter sets is an Indexed step with a template and parameter_sets, expanded into ordinary steps when the recipe loads (§10).

6.1 Where module: is found

A PythonModule step's module: is tried, in order, as:

  1. a file next to the recipe — example_tests.py or example_tests, relative to the recipe's folder (or an absolute path);
  2. a dotted import name — mypackage.tests, or the standard library.

A file is loaded once and shared by every step that names it. There is no project-wide search: the recipe says where its code is. The module is not imported when the recipe loads, so a wrong module or method_name is an ERROR on that step when it runs.

7. outputs — judging and storing results

outputs:
  voltage:  {type: range, min: 4.9, max: 5.1}
  measured: {type: global, global_name: last_voltage}
  ok:       {type: passfail}

Each entry names one value the step returned and says what to do with it. An entry is always a mapping and always names its type:

typeExtra keysEffect on the result
passfail—PASS if the value is truthy, else FAIL
equalsvaluePASS if the value == value (no coercion), else FAIL
rangemin, maxPASS if min ≤ float(value) ≤ max, else FAIL
pass—Not a measurement: the result is DONE, whatever came back; the step need not return it
globalglobal_nameStores the value in that global; leaves the result alone

What a step returns: a mapping is used as it is; None is an empty one; any other value is the output named output. So a function that returns 5.0 is judged with outputs: {output: {type: range, ...}}.

Result rule: the result starts as DONE. Each judging entry (passfail/equals/range) assigns it; with several, the last one wins — write one judging entry per step to avoid surprises. A global entry never touches it. An entry other than pass whose value the step did not return is an ERROR naming what it did return.

8. Result model

ResultType is an IntEnum; the ordering is the aggregation rule:

SKIP(0) < DONE(1) < PASS(2) < FAIL(3) < ERROR(4) < STOP(5)
  • A sequence's result is the highest of its steps' — one FAIL among PASSes makes it FAIL.
  • By default nothing halts a sequence: an ERROR or a FAIL is recorded and the next step runs.

    A step with continue_on_error: false ends the run when it errors or fails; every remaining step is recorded SKIP.

  • STOP is produced by an operator abort.
  • DONE means "ran, no verdict" — a step with no judging outputs entry.

9. Execution control

9.1 continue_on_error`

- steptype: PythonModule
  step_name: power_on
  continue_on_error: false   # end the run if this step errors or fails
  ...

Default is true` (carry on). Set false` when stopping is safer — power supply never came up, fixture is open. It is accepted on every step type and only on steps: there is no recipe-level form. On an Indexed` step it applies to every generated step. Teardown steps always run to the end regardless. critical:` is no longer supported and is refused at load time.

9.2 Abort

A stop request is checked between steps, never inside one, so a step can leave its hardware in a known state. Every step that did not run is still recorded as SKIP` with the reason "Not run: the run was stopped by the operator.", so the step table and the CSV have a row for each; the run's result is STOP`. Interactive steps poll for the stop every 100 ms while waiting for the operator.

10. Step type catalogue

Six step types are available (plus Indexed`, which is expanded at load time). steptype` values are case-insensitive.

PythonModule — run user Python

- steptype: PythonModule
  step_name: measure_voltage
  description: Reads the 3V3 rail and compares against limits
  module: example_tests.py
  method_name: range_test
  inputs:
    value: {type: global, global_name: measured}
    min: 3.1
    max: 3.5
  outputs:
    result: {type: range, min: 3.1, max: 3.5}
  • Calls the function method_name of module (found as §6.1 says). Methods only; the old action_type and its read_attribute/write_attribute are gone.
  • Every inputs entry is passed as a keyword argument of that name.
  • Return value: a mapping is used as it is; None is {}; anything else is {"output": value} (§7).
  • Required fields: step_name, module, method_name (not empty).

Wait` — sleep

- steptype: Wait
  step_name: settle
  description: Let the rail settle
  wait_time: 3               # seconds (int or float)

Always returns DONE`.

UserInteraction` — prompt operator with buttons

- steptype: UserInteraction
  step_name: confirm_wiring
  description: Operator confirms the harness is connected
  message: Connect the harness, then press Next.
  image_path: harness.jpg    # optional
  options: [Next]
  outputs:
    output: { type: equals, value: Next }
  • options` is a list of strings. Each string is both the button label and the value the step returns as output`.
  • An empty options` list is refused at load time, as is an image_path` that does not exist.
  • The GUI always adds its own Cancel button. Cancelling, a timeout or a stop makes the step ERROR`; the run carries on unless continue_on_error: false`.
  • The old dict format (- next: Next`) and the cancel_key` global are not supported.

UserWrite` — operator types a value

- steptype: UserWrite
  step_name: get_serial_number
  description: Scan or type the serial number
  message: Scan or type the serial number of the unit under test.
  outputs:
    output: { type: global, global_name: serial_number }

Text-entry mode only. The typed string is stored per outputs`. The old serial-port picker mode (ID` key) is not available.

UserLoading` — operator picks a file or folder

- steptype: UserLoading
  step_name: pick_calibration_file
  description: Choose the calibration file for this unit
  message: Select the calibration file for this unit.
  select: file               # optional: file (default) or folder, case-insensitive
  image_path: cal.png        # optional
  outputs:
    output: { type: global, global_name: calibration_file }
  • The chosen path is stored per outputs` as an absolute, resolved path string; a later step reads it with inputs: {path: {type: global, global_name: calibration_file}}`.
  • select` other than file`/folder` is refused at load time. There is no file filter, no start folder and no save-as mode.
  • The step checks the answer itself: a path that does not exist, or a folder where a file was asked for (or the other way round), is ERROR`. Cancelling, a timeout or a stop is ERROR` too.
  • One request, one response: the old type's second value on the response queue is gone. Worked example: resources/recipes/Development_recipes/userloadingstep_demo.yml` (GUI mode — the CLI declines).

Sequence — call a group of steps

---
sequence_name: Main
steps:
  - steptype: Sequence
    sequence_name: PowerCycle    # required; case-insensitive
    description: Before calibration   # optional; else PowerCycle's own description
    skip: false                  # optional
    continue_on_error: true      # optional
teardown_steps:
  - steptype: Sequence
    sequence_name: Shutdown      # a group may be called from teardown too
---
sequence_name: PowerCycle
description: Switch the unit off and on again
steps:
  - ...
teardown_steps:
  - ...

Group tests in sequence documents of their own and run them inside main. A Sequence step names the sequence it calls; that sequence is written exactly like any other sequence document.

  • No step_name, inputs, outputs or id — all four are refused at load time. The row is named after the called sequence; a group shares the run's globals; its verdict comes from its steps; every call gets fresh ids.
  • Call as often and as deep as you like. A group may call other groups, and the same group may be called many times — each call is its own copy with its own rows. To run a group N times, write the call N times; there is no repeat key.
  • Refused at load time: a sequence_name no sequence has, a call to the main sequence, and a sequence that ends up calling itself (the error shows the chain, e.g. Main -> PowerCycle -> Settle -> PowerCycle). A Sequence step cannot be the template of an Indexed step; an Indexed step inside a called sequence works as usual.
  • A group is one result. Its verdict is the worst of everything it ran, its own teardown included. Its steps follow its row in the step table.
  • skip: true records the group's steps SKIP and still runs its teardown. A group the run never reaches (after a Stop or a halt) is SKIP throughout, teardown included — nothing in it was set up.
  • continue_on_error: false anywhere ends the whole run, not only the group: the rest is SKIP, every teardown on the way out still runs (innermost first), and the run ends FAIL or ERROR. On the Sequence step itself it halts on the group's verdict.
  • Stop, Pause and teardown work at every depth: Stop is checked before every step, Pause holds before a step inside a group, and anything called from teardown_steps runs to the end.
  • Totals count real steps. A group's row is not counted in the run's step counts; the steps inside it are. Log lines inside a group are indented.
  • Worked example: resources/recipes/Development_recipes/sequencestep_demo.yml (runs headless).

Not yet in the frontends: the GUI and CLI still offer every sequence to start and show group rows without indentation; the report has no group column yet; the Recipe Creator and its verificator do not know the step yet. These follow in the next stages (roadmap).

12. YAML pitfalls

  1. yes`/no`/on`/off`/true` are booleans in YAML 1.1. An option written options: [Yes, No]`

    produces the booleans True`/False`, not the strings "Yes"`/"No"`. Always quote: options: ['Yes', 'No']`, and quote the matching equals` value too.

  2. A text field takes text or a number, nothing else. step_name, message, description, module,

    method_name and the header's name refuse a YAML boolean (message: yes), a date (description: 2024-01-01) or a list when the recipe loads, with message: Input should be a valid string. Quote the value: message: 'yes'. A number is read as its text (version: 0.2, step_name: 7). skip and continue_on_error take true/false.

  3. None` is a string, not null. YAML null is null`, ~`, or empty. Recipes use None`

    as a placeholder; quote it where needed.

  4. Quoting changes the type. value: 45` ≠ value: '45'` for equals`. range` is safe

    (it calls float()`).

  5. The leading - before steptype makes a step a list element. Omitting it turns

    steps into one mapping instead of a list of steps, and the recipe is refused: steps: Input should be a valid list.

  6. A key with nothing after the colon is absent. A bare globals: or skip: reads as null and counts as not

    written: an optional field keeps its default, a required one is missing (wait_time: Field required). Write globals: {} to mean "empty" on purpose.

  7. Duplicate sequence_name across documents is refused when the recipe loads — compared without case,

    so Main and main are the same name.

  8. Tabs are illegal in YAML. Indentation must be spaces.

13. What the verificator checks

The Recipe Creator's verificator (helper_applications/recipe_creator/verificator.py) answers one question: would PyPTS load this recipe? It answers it with the framework's own checks, so it can never disagree with the real load. It returns every problem in one pass, each with a line number and a hint on how to fix it.

Errors — the recipe will not load:

  • Everything the framework's recipe models check: required fields, value types, unknown step keys, the inputs/outputs vocabulary, Sequence and Indexed step shapes, report_metadata. The message is the framework's own, for example sequence 'Main', steps[1] 'Pause': wait_time: Field required.
  • A duplicate sequence name (compared without case), and a main_sequence that names no sequence.
  • Once all of the above is clean, whatever the framework's real load still refuses: select that is neither file nor folder, an empty method_name or options, a Sequence step calling a sequence that does not exist, the main sequence, or itself in a loop. These are found one at a time and carry no line number.

Warnings — the recipe loads, but something looks wrong: version written as a number, an empty name or version, a removed sequence key (setup_steps, parameters, outputs, locals), an unknown sequence key (ignored).

Not checked, because the framework does not check it at load time either: that module/method_name exist, that an image_path exists, that a global input names a global something will have set, or the value of wait_time.
