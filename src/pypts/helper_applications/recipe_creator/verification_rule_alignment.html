1What this is and is not

The Recipe Creator has its own recipe checker — recipe_verificator/verificator.py, 1163 lines — separate from the one the framework uses to load a recipe (src/pypts/recipe/). The two have drifted. This work aligns the Creator’s rules with the framework’s, as they stand today.

The shape of the change

The verificator stays. Its rules change.

It keeps its size, its line numbers, its hints and its independence. No delegation to the framework, no attribution machinery, no final gate. One file, roughly sixty lines.

Explicitly not doing

  • Not changing src/pypts/recipe/. The framework is the reference; it is not touched.
  • Not gutting the verificator so it calls the framework’s validator for its verdict. That was an earlier proposal and is dropped.
  • Not building a guard against drift returning in future. Accepted, on the record: the two remain separate implementations that can drift again.

The properties being restored are these two, and only these:

No false error — the Creator must not report a problem in a recipe the application loads.
No false clean — the Creator must not stay silent about a recipe the application refuses.

false error Creator complains, app accepts false clean Creator silent, app refuses

2Drift A — case sensitivity

Implemented — 2026-09-16

All four consequences are fixed, by fixes 1–3 in §6. The verificator now normalizes with recipe_parser.normalize_header() and normalize_sequence() — the framework’s own helpers, not a second copy of the rule.

Verified: 12 new tests pass; all 12 corpus recipes agree with the real load path (0 mismatches); ruff and mypy clean.

One root cause with four consequences. The verificator never normalized its input. The framework lowercases every mapping key before validating — recipe_parser.py:303 (_lowercase_keys), applied recursively through sequences, steps, inputs/outputs entry configs, indexed templates and parameter sets. The recipe language is case-insensitive by design. The verificator reads raw keys.

#WhereWhat happens
A1 Every field check;
unknown-key check at :684		 Any mixed-case key — Step_Name:, Global_Name:, Steptype: — produces two wrong messages at once: a “missing required field” error, because the lowercase key is absent, and an “unknown key” warning, because the raw key is tested against rules.py’s lowercase sets. false error
A2 :203 "name" in header_doc is a raw-key test. A header written Name: is rejected as “not a recipe header” and verification stops before a single field is examined. false error
A3 :932 Duplicate sequence names compared case-sensitively. The parser compares them lowercased (recipe_parser.py:95), so sequences named Main and main are a duplicate to the application and unique to the Creator. false clean
A4 :946 main_sequence matched case-sensitively. The parser matches case-insensitively (recipe_parser.py:105), so main_sequence: main against a sequence named Main runs fine and the Creator calls it a broken reference. false error

3Drift B — load-time value rules

Three rules are enforced by step constructors when the recipe loads. The verificator checks that these fields are present, but never what they contain — so each is a recipe the Creator passes and the application then refuses. Note that the framework’s own validator.py does not catch these either; it tests is None, and "" and [] are not None.

#RuleEnforced atSlips through as
B1 select must be file or folder, case-insensitively user_loading_step.py:77 select: sideways false clean
B2 method_name may not be empty python_module_step.py:116 method_name: "" false clean
B3 options may not be empty user_interaction_step.py:65 options: [] false clean

4Drift C — dead code

_header_required_hint is defined twice in verificator.py, at lines 377 and 998. The bodies are byte-identical, so behaviour is unaffected — Python keeps the last definition, making line 377’s copy dead.

Line 377’s copy is deleted. Line 998’s is kept, because it sits with the other seven _*_hint functions in the hints section.

Why it is in this document

It is not a drift, it is a symptom of the same cause: a 1163-line file nobody can hold in one head. It is listed because it is being removed in the same pass, not because it breaks anything.

5Deliberately unchanged

wait_step.py:40 refuses a negative wait_time — but it raises inside _step(), at run time, not on load. A recipe with wait_time: -5 loads without complaint and fails when that step executes.

The verificator therefore stays silent about it, and that is correct. Flagging it would create a new false error: the Creator would refuse a recipe the application loads. Verification answers “will this load?”, not “will every step succeed?”.

6The fix

done Fixes 1–3 are implemented and verified. to do Fixes 4 and 5 are not started.

done 1  Normalize in _run, before anything else

Run each document through the parser’s own public helpers — recipe_parser.normalize_header() and normalize_sequence() (recipe_parser.py:234,239) — rather than reimplementing the lowercasing. Order matters: this must happen before the document-identification test at :203, or A2 survives.

Resolves A1 and A2.

done 2  Make _LineMap case-insensitive

The one subtlety in this change

The line map is built from the raw YAML node, which keeps original-case keys. Lowercase the documents without lowercasing the map and every mixed-case recipe verifies correctly but reports no line numbers at all — the error gutter goes blank and the fix looks like a regression.

Lowercase the map’s keys as it is built, so a lookup for step_name finds the line of Step_Name:.

done 3  Lowercase both sides of the two name comparisons

Sequence-name duplicate detection and the main_sequence lookup, matching recipe_parser.py:95,105. Sequence names keep their original case for display; only the comparison is lowered.

Resolves A3 and A4.

to do 4  Add the three value checks

Import SELECT_VALUES from user_loading_step.py rather than retyping the legal words — one fewer thing to drift. Empty-value checks for method_name and options alongside.

Resolves B1, B2, B3.

to do 5  Delete the dead _header_required_hint

Line 377’s copy. Resolves C.
