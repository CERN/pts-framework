1. Overall verdict

The engine is in good shape. Control flow is plain, message contracts are explicit, and the error-handling split is readable. Most of its findings are drift: context files and docstrings describing constants, data flows and features that no longer exist.

The weight of the problems sits at the edges:

  • The GUI promises behaviour it doesn't have. Pause doesn't pause, the results page can't be reached, and Edit Recipe does nothing.
  • The two GUI stylesheets are about 480-line copies of each other.
  • The recipe verificator is a parallel copy of recipe/validator.py and has already drifted from it.
  • About 1,300 lines of dead legacy code sit in recipe_creator/. Ruff's blanket "ALL" exemption hides that some of it no longer runs.
  • The test suite is well written, but about 44 permanent placeholder skips (some with false reasons) and five copies of the same helpers cloud it.

Deleting dead code and generating the stylesheet from the palette would remove well over 2,000 lines without changing what the operator sees.

3. Cross-cutting themes

  • Prose drift. Context files and docstrings name constants that don't exist (HEARTBEAT_SILENCE_LIMIT_S, POLL_TIMEOUT_S). They describe dropped features (SequenceStep, the local scope, "frozen" messages, "engine not ported"), point to files that were moved (resources/roadmap/pypts_roadmap.md), and list old report columns.
  • Conditional expressions against the style guide. SIM108 is off on purpose, yet x if c else y appears in nearly every module. The worst are nested inside call arguments (top_bar.py:224-268) and repeated five times in one dict literal (report.py:290-295).
  • Blanket lint exemptions hide real bugs. pyproject.toml:146-152 exempts recipe_creator/*, recipe_verificator/* and example_finder/* from all ruff rules. That hid undefined names (F821), a duplicated function definition, unused imports, and noqa comments for rules that are switched off. Much of that code is new, not "pre-refactor".
  • Magic strings for closed sets. Launch mode ("gui"/"cli"/"api"/"headless"), theme, window mode, dialog states, the interaction panel's _mode, debug-monitor verdicts and schema type. A Literal or StrEnum would let mypy catch typos. Today an unknown value silently falls through to a default.
  • Duplicated knowledge. The verificator copies the validator. step_source copies the parser pipeline through a private function. READS_A_VALUE copies OUTPUT_TYPES. Recipe Creator widgets hard-code the per-type keys from rules. There are two YAML highlighters, two stylesheets, and "None means ERROR" in three places.
  • Any and untyped public seams. Operator request/answer seams, log_queue, QueueWrapper.__init__(queue), HeartbeatManager(outbox), and widget model parameters. The concrete types are known in every case.
  • Speculative generality. Decorator parameters used only by tests, SetStdoutEnabled with no production sender, a label/value dict protocol where label always equals value, and template-writer continuation handling for multi-line values that never occur.

4. Engine: core, sequencer, launcher, logger, messages, utilities

Overall: good. Explicit routing, single-path shutdown and clear per-module state. The findings are mostly prose drift and small duplication.

A failing stop() suppresses SequencerStopped; error decorators stacked three deep

Implemented, with testshighexplicitnessverifiedsequencer/sequencer.py:116-147, 513-525

main_loop, poll_core, handle_core_message, run_sequence, stop_sequence, stop and do_periodic_tasks are all @catch_and_report_errors(). The inner ones add nothing the outer ones don't already catch, and they hide which layer is the real boundary. If stop_running_sequence() raises, self.core.send(SequencerStopped()) never runs, so CORE waits out its 5 s budget.

Decorate only the per-message boundary and do_periodic_tasks. Send SequencerStopped from a finally.

Done 2026-09-16 — the finally half. The send moved into a finally in Sequencer.stop(), and the review of the other two links found the same shape twice more: Report.stop() sends ReportStopped after close_csv() (file I/O, the likeliest of the three to raise), and HmiClient.stop() sends HmiStopped after on_stop() — the GUI's own teardown, which closes a window. All three are fixed the same way, with one regression test each (test_sequencer.py, test_report.py, test_hmi_client.py). The exception still reaches CORE as a ModuleError; the goodbye simply leaves first. Written up as §1.48 of pypts_implementation_status.html.
Both halves done 2026-09-16 (roadmap §1.49). The rule adopted: the error boundary is the loop tick, not the call chain. A method carries the decorator only when a failure inside it has nowhere else to go — poll_core(), handle_core_message(), do_periodic_tasks(), and a thread entry point. Twelve decorators came off (five in the Sequencer, seven in the Report); every one was called from exactly one place with nothing after the call, so the swallow just moved one frame up. HmiClient was already this shape and kept its stop() decorator, since wait_until_stopped() calls it with no net above. The sharpest find: the decorator on main_loop() never protected the loop — the while is inside it, so catching there ended the loop and reported a clean stop while CORE went on believing the module was alive. It moved to start(), which sends the goodbye from a finally so a dead loop does not cost CORE its shutdown budget either. One cost, accepted: ModuleError.operation now names the boundary rather than the method that failed; it is a DEBUG-only field and the traceback on the same record still names the method.

10. Strengths worth keeping

  • Routing is visible at a glance. CORE's three handlers are the whole table, each closed with unhandled(), and the same object is relayed without repacking.
  • Shutdown is explicit and single-path. The watchdog reuses stop_all_modules(), and a module that never answers is named.
  • The step extension model. Subclass Step, override _step(). Constructor arguments are the YAML keys, so an unknown key is a load-time error. The registry is a plain dict, replacing eval().
  • Runtime is a real seam. A bare Runtime() is a complete fake, and ask owns the register-before-send ordering.
  • Load-time Indexed expansion. Nothing downstream knows the type exists.
  • The validator gathers every problem into one RecipeError, driven by the rules.py tables, and its messages suggest the fix.
  • Step failures always become data. Remaining steps get SKIP rows, and SequenceFinished always fires.
  • The API layer returns its own dataclasses, answers on the caller's thread so heartbeats keep going, and always sends a decline. Headless exit codes are named.
  • HmiClient has safe decline defaults for every question. log_tail.py is a model single-responsibility module. The CLI's three-thread design is small and correct.
  • Dialogs are pure presentation with injected callables, so they are testable without CORE.
  • Config writes are atomic, errors say how to fix them, and the singleton is lock-guarded with explicit roles.
  • The Recipe Creator model routes every change through QUndoCommand, uses a _MISSING sentinel for correct undo, and delegates to verify_string.
  • Tests read as sentences, include guards on the guards (e.g. proving the exhaustive-handler test can fail), use hand-written small fakes rather than MagicMock trees, and never import old_code.
  • Logging is almost everywhere %-style, with a thoughtful split between technician-facing and DEBUG lines.
