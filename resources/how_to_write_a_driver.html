How to write a device driver

PyPTS hardware layer (pypts.hal) — for anyone adding an instrument to a test bench. The developer-side reference is src/pypts/hal/hal.md.

1. What a driver is

A driver is one plain Python class for one kind of instrument: a power supply, a multimeter, a remote machine. It knows how to open the connection, do the instrument's verbs, and leave the instrument safe. It imports nothing from the framework except its base class, and it contains no threading, no queues, no process code.

PyPTS runs every device's driver in a process of its own, reached over a pipe. A driver that crashes, hangs or leaks takes its own process down, not PyPTS. You do not write any of that: you write the class below, and the framework does the rest.

2. A complete example

A power supply reached over TCP (SCPI), using only the standard library:

"""Driver for the ACME PS-3000 power supply, reached over TCP (SCPI)."""

import logging
import socket

from pypts.hal import PSU

log = logging.getLogger(__name__)


class AcmePsuDriver(PSU):
    """One ACME PS-3000, one TCP connection."""

    def __init__(self):
        self._sock = None

    def connect(self, config):
        host = config["host"]                     # every value arrives as text
        port = int(config.get("port", "5025"))
        self._sock = socket.create_connection((host, port), timeout=10)
        log.info("PS-3000 answered: %s", self._query("*IDN?"))

    def teardown(self):
        if self._sock is None:
            return                                # harmless when nothing is open
        try:
            self._command("OUTP OFF")             # the instrument is left safe first
        finally:
            self._sock.close()
            self._sock = None

    # --- the PSU verbs ---------------------------------------------------

    def set_voltage(self, channel, volts):
        self._command("INST OUT%d" % channel)
        self._command("VOLT %.3f" % volts)

    def set_current_limit(self, channel, amps):
        self._command("INST OUT%d" % channel)
        self._command("CURR %.3f" % amps)

    def output_on(self, channel):
        self._command("INST OUT%d" % channel)
        self._command("OUTP ON")

    def output_off(self, channel):
        self._command("INST OUT%d" % channel)
        self._command("OUTP OFF")

    def measure_voltage(self, channel):
        self._command("INST OUT%d" % channel)
        return float(self._query("MEAS:VOLT?"))

    def measure_current(self, channel):
        self._command("INST OUT%d" % channel)
        return float(self._query("MEAS:CURR?"))

    # --- the wire, private: not an operation ------------------------------

    def _command(self, text):
        self._sock.sendall((text + "\n").encode("ascii"))

    def _query(self, text):
        self._command(text)
        return self._sock.makefile().readline().strip()

That is the whole driver. Save it in a module the bench's Python can import — installed as a package, or in a folder that is on sys.path when PyPTS starts.

3. Tell PyPTS about the device

One bare-named section per device in bench.ini (%LOCALAPPDATA%\pypts\bench.ini on Windows, ~/.config/pypts/bench.ini elsewhere — created empty from a template on first start, beside config.ini):

[psu1]
driver = bench_drivers.acme_psu.AcmePsuDriver   ; required: the driver class, dotted
call_timeout_s = 30                             ; optional: longest one call may take, default 60
host = 192.168.0.40                             ; everything else goes to connect()
port = 5025
  • driver and call_timeout_s are read by the framework; every other key goes to your connect(config) as text — convert numbers yourself.
  • Keys are lower-cased by the INI parser.
  • A key named like a password is masked in the log; the file itself is plain text.
  • A hand edit of bench.ini applies from the next start (File → Restart in the GUI).

Test code then reaches the device by its logical name:

from pypts.hal import get_device

def power_up():
    psu = get_device("psu1")        # opened on first use, closed when the run ends
    psu.set_voltage(1, 3.3)
    psu.output_on(1)
    return {"vout": psu.measure_voltage(1)}

4. The rules

4.1 Derive from a device type, never from BaseDriver

Import the type from pypts.hal: PSU, DMM, Scope, Load, SSH, or Other for anything else. A driver that derives from BaseDriver directly is refused at open. Each type names the verbs a driver of that type implements, so recipes can swap one PSU for another:

TypeVerbs
PSUset_voltage, set_current_limit, output_on, output_off, measure_voltage, measure_current (channel counts from 1)
DMMmeasure_dc_voltage, measure_ac_voltage, measure_dc_current, measure_resistance
Scopeset_timebase, set_vertical_scale, arm_single, read_waveform
Loadset_mode (CC/CV/CR/CP), set_level, input_on, input_off, measure_voltage, measure_current
SSHexecute, put_file, get_file
Othernone — every public method you add is the interface

A type's verbs are abstract and mandatory — a driver that omits one fails at open with a TypeError naming it.

4.2 Implement the lifecycle

  • connect(config) — open the connection the section describes. All values are text. Raise when the instrument cannot be reached: the device then fails at open with your message.
  • teardown() — where the instrument is left safe: outputs and loads off, then disconnect. There is no separate safe-state method. Teardown runs at every end of a device — a normal close, PyPTS dying, or on a fresh connection when your driver was stuck — so it must work right after connect() on an instrument in any state, and be harmless when nothing is open. The framework runs it exactly once per connection, never twice.
  • recover(config) — optional. The default is teardown + connect; override it when the instrument has a cheaper reset. Test code triggers it with device.recover(); the framework never recovers on its own.

4.3 Every public method becomes an operation

Any method not starting with _ (and not a lifecycle method) is callable from test code. Keep the wire protocol in _private helpers. Arguments and return values cross a process boundary, so they must be what pickle can carry: numbers, strings, bytes, lists, dicts... — not sockets, locks or Qt objects. An argument that cannot be sent is refused before anything reaches the instrument; a return value that cannot be sent comes back as an error, and the device stays usable.

4.4 Names you must not use

ConnectionDriver uses these names itself, so a driver method with one of them could never be reached: name, device_type, operations, open, close, recover, is_open, abandon. A driver that uses one is refused at open, naming the offending methods. (Overriding the lifecycle recover() is allowed: lifecycle methods are not operations, so the check never fires on it.)

4.5 Logging and printing

Log with logging.getLogger(__name__). Your driver's records keep their level in the PyPTS run log, prefixed Device 'psu1': ... — INFO and above reaches the technician's panel, so log at INFO what an operator should see and keep the chatter at DEBUG. A vendor library's records below WARNING are turned down to DEBUG. Anything printed goes to the run log at DEBUG.

4.6 Vendor libraries

Import the vendor library at the top of the module, and turn a missing one into a message that names what to install:

try:
    import pyvisa
except ImportError as exc:
    raise ImportError(
        "AcmeScopeDriver needs pyvisa; install it with 'pip install pyvisa'."
    ) from exc

The shipped pypts.hal.drivers.ssh.SshDriver shows the pattern; pypts.hal.drivers.weather.OpenMeteoDriver is a driver that needs no vendor library at all and turns every failure of its far end into one clear error.

4.7 Do not start processes

The driver process is a daemon, and a daemon cannot have children: do not use multiprocessing inside a driver. Threads are allowed, but anything they log between calls is delivered with the next call, not immediately.

5. What the framework does for you

SituationWhat happens
Driver raisesTest code gets DriverError("Device 'psu1': 'set_voltage' failed: ...") with your message; the device stays usable; the traceback is in the log at DEBUG.
A call exceeds call_timeout_sThe stuck driver process is killed and the call raises. The instrument keeps its state until the device is closed — then a fresh process connects and runs teardown() (the rescue) — or until test code calls recover().
The driver process crashesDriverError("Device 'psu1' stopped unexpectedly (exit code N)."); recover() brings it back on a fresh process.
The run ends, in any wayEvery opened device is closed, newest first: teardown() on the live process, or on a fresh connection when the process was stuck or gone. A device that still cannot be torn down is an ERROR naming it (... may still be energised).
PyPTS diesThe pipe closes and the driver process runs teardown() itself before exiting — unless it is stuck in a call.
The run is abandoned (Stop gave up on its thread)Every opened device is torn down on one 16 s shared deadline, newest first, and then refuses open() and recover() for good.
bench.ini was discarded at startupEvery get_device() fails with the discarded-bench DriverError until the file is fixed and PyPTS restarted.
The one net you provide: everything above funnels into your teardown(). If it does not reliably switch the outputs off, nothing else will.

6. Testing the driver

  • In-process, vendor library mocked — build the class directly and call its methods; see tests/unit_tests/test_hal_ssh.py.
  • Through a real driver process — open it with ConnectionDriver("x", "my_module.MyDriver", {...}) and call it; see tests/unit_tests/test_hal_connection.py and the loopback driver it uses.
  • On the bench, outside PyPTS — a plain script can use the same devices. The INI file given to from_ini() uses bench.ini's format: one bare-named section per device, e.g. [psu1]. 
    from pypts.hal import LocalSetup, get_device

if __name__ == "__main__":                 # required: spawn re-imports this file
    with LocalSetup.from_ini("bench.ini"):
        print(get_device("psu1").measure_voltage(1))
    Without the __main__ guard every driver process re-runs the script and dies at once with stopped unexpectedly (exit code 1).

7. Checklist

  • ☐ Derives from PSU / DMM / Scope / Load / SSH / Other, not BaseDriver.
  • ☐ connect(config) treats every value as text and raises a clear error when the instrument is unreachable.
  • ☐ teardown() leaves the instrument safe, works right after connect(), and is harmless when nothing is open.
  • ☐ No public method named name, device_type, operations, open, close, recover, is_open or abandon; the wire protocol is in _private helpers.
  • ☐ Arguments and return values are picklable.
  • ☐ Logs through logging.getLogger(__name__); operator-relevant lines at INFO.
  • ☐ Vendor import at the top of the module, with the extra to install named.
  • ☐ No multiprocessing inside the driver.
  • ☐ The module is importable on the bench (installed, or on sys.path).
  • ☐ A [<name>] section exists in bench.ini and the demo recipe or a standalone script talks to the instrument.
