1. The model in one picture

Modules never touch a queue and never call each other. Everything goes through CORE — except log records, which go straight to the Logger so that logging survives a dead CORE.

┌──────────────┐ │ LAUNCHER │ builds HMI↔CORE queues + log queue └──┬────────┬──┘ parent of every process HmiStopped + │ │ ShutdownRequested│ │ spawns ▼ ▼ ┌─────────┐ hmi->core ┌────────┐ core->sequencer ┌───────────┐ │ HMI │ ───────────► │ │ ────────────────► │ SEQUENCER │ │ GUI/CLI │ ◄─────────── │ CORE │ ◄──────────────── │ │ └─────────┘ core->hmi │ │ sequencer->core └───────────┘ │ │mediator│ core->report ┌───────────┐ │ │ │ ────────────────► │ REPORT │ │ │ │ ◄──────────────── │ │ │ └────┬───┘ report->core └───────────┘ │ │ │ └────────────────────────┴─────────────────────────────┘ any->logger ▼ (LogRecords + control, NOT via CORE) ┌────────┐ │ LOGGER │ single writer of the run log └────────┘
One process boundary that matters: HMI ↔ CORE. Sequencer and Report are separate processes today, but the roadmap turns them into threads inside the engine process — which costs one line in the launcher, because no module knows what its Channel wraps.

2. Links & queues

A link is a pair of modules. Each direction is its own queue wrapped in its own Channel, named by a constant in messages/links.py — that name is what a trace line is identified by.

Link nameDirectionQueue built byContract module
hmi->coreHMI → CORElauncher startup.pyhmi_link.py
core->hmiCORE → HMI
core->sequencerCORE → SequencerCORE Core.__init__sequencer_link.py
sequencer->coreSequencer → CORE

report->coreReport → CORE
any->loggerevery process → Loggerlauncherlogger_link.py

Seven queues in total (6 link directions + 1 log queue), all multiprocessing.Queue today. Two rules keep the topology honest:

  • The owner builds the handle. Whoever owns a link constructs both channels and hands them to the module that needs them. A module cannot invent a channel to somebody it has no business talking to — the topology is enforced by construction, not by convention.
  • One swappable transport. Channel wraps anything with put() and get_nowait(). The launcher picks multiprocessing.Queue; CORE takes a queue_factory argument (default Queue) so tests — and later the thread migration — pass queue.Queue instead.
The log queue is the odd one out: it carries two kinds of item — plain logging.LogRecord objects put there by logging's own QueueHandler, and the LoggerControl dataclasses. The Logger tells them apart with isinstance, which is why control messages must not be LogRecord-shaped.

3. The transport: Channel

One generic class, messages/channel.py. A typed, one-way pipe with two operations.

self.core.send(StartSequence("power_on"))      # never blocks, never inspects

for message in self.inbox.receive():           # never blocks; yields what is waiting now
    self.handle_core_message(message)
MemberWhat it does
send(message)DEBUG-traces, then put(), then increments sent. The trace comes before the put so a message that fails to pickle is still recorded.
receive(limit=64)Generator. Yields waiting messages up to limit and stops on empty. Bounded so one busy link cannot starve the other inboxes; a caller that breaks early leaves the rest queued.
linkThe direction's name, from links.py. An unnamed channel traces as ?.
sent / receivedPer-process counters. A pickled channel handed to a child increments the child's own copy — that is the useful reading, not a defect.

Nothing ever blocks on a queue. Every module runs a poll loop (while running: poll → periodic tasks → sleep(0.01)), so a message sent between two ticks simply arrives on the next one. The only exception is the Logger, which blocks on get() because it has no second source to service.

The trace — the only debug switch there is

Both send() and receive() log one DEBUG line to the pypts.trace logger, so --log-level DEBUG puts every message in the system into the run log twice: once from the sender, once from the receiver. A send with no matching receive is a lost message, and seeing that is the whole point.

...;DEBUG;Core;channel.py:send;send core->sequencer RunSequence(sequence_name='power_on')
...;DEBUG;Sequencer;channel.py:receive;recv core->sequencer RunSequence(sequence_name='power_on')

grep 'sequencer->core' pypts_*.log     # the whole-system view of one link
There is no debug build and nothing else to turn on. Because the trace sits on the one object every message passes through, no module has to remember to log anything, and no new message can escape it. It is also the only way to see core↔sequencer and core↔report, which never leave the engine process.

4. The messages, per link

Every message is a frozen slotted dataclass of plain values. Frozen because a message is a fact that has already happened; slotted because a typo in a field name should be an AttributeError, not a silent new attribute. Each direction has a union type — that union is the contract.

CMD an instruction to one recipient, which may be refused   EVT a fact that has already happened   STUB declared, nothing sends or carries it out yet

Shared vocabulary — common.py and run_events.py

A type lives here when more than one link uses it: either every module sends it, or CORE forwards it from one link to another. Forwarding matters — CORE relays the same object rather than repacking it into a dict, which is how the old code lost the severity enum on every hop.

5. Who handles what, and where

One handler per inbox. Every one is a match closed with unhandled(message) — never case _: pass.

CORE's three handlers are the whole routing table. Read them and you know the system:

def handle_sequencer_message(self, message: SequencerToCore) -> None:
    match message:
        case SequencerStopped():
            self.module_running[SEQUENCER] = False
        case RunStarted() | RunFinished() | SequenceStarted() | ... :
            self.to_hmi.send(message)          # relayed, not repacked
        case Heartbeat():
            self.note_heartbeat(message)
        case ModuleError():
            self.handle_module_error(message)
        case _:
            unhandled(message)
Two different survival policies. Every other module wraps its handlers in @catch_and_report_errors(), which reports the failure to CORE as a ModuleError and carries on. CORE cannot — it is what errors are reported to — so Core.poll() catches UnhandledMessage and everything else, logs it, and drops that message. The cost is that one bad message abandons the rest of that batch; those stay queued for the next tick.

One handler is shared: the GUI and the CLI both use HmiClient. The protocol lives once in hmi_client.py; subclasses override only the show_* hooks they can draw, and every hook has a logging default — so adding a message to CoreToHmi cannot break a frontend that has not caught up.

6. Adding a message

Two edits. That is the whole procedure.

# 1. Declare it in the link module, and add it to that link's union
@dataclass(frozen=True, slots=True)
class StartSequence:
    sequence_name: str

HmiToCore = LoadRecipe | StartSequence | ...

# 2. Handle it with a case in the recipient's handler
case StartSequence(sequence_name=name):
    self.start_sequence(name)
Everything else is found for you. A type checker flags every match that is now incomplete, because unhandled() takes a Never and only type-checks once every union member has been matched. test_messages.py fails until the message has an example in its table and a branch in its recipient — it enumerates the unions with typing.get_args(), so a new message is covered automatically. It also asserts the message is a frozen dataclass, survives a pickle round trip, and carries no live queue or handle.

A message shared by two links — anything CORE forwards rather than repacks — belongs in common.py or run_events.py, so both ends refer to the same class.

8. Heartbeats, errors, questions, shutdown

Heartbeats

Every module ticks a HeartbeatManager from its periodic tasks — one Heartbeat(source, timestamp) per second on its outbox to CORE. CORE records it per module and warns after 5 s of silence, once per outage (its loop turns every 10 ms), and logs again when the module answers. What CORE should do about a timeout — restart, abort, tell the operator — is still an open roadmap decision; today it only warns.

Errors

@catch_and_report_errors() → ModuleError → CORE logs it, and if the severity is above WARNING forwards it to the HMI as ModuleErrorReported. CORE deciding what reaches the frontend is what keeps the runtime log readable during a long run.

Questions to the operator (request/response)

The asking side generates a request_id with uuid4(); that id is what lets the pair cross a process boundary at all. The old engine put a live queue.SimpleQueue inside the event and had the GUI answer straight into it, which only worked because both ends were threads.

# asking side (a step, on its own worker thread)
request_id = uuid4()
pending.start(request_id)                       # register BEFORE sending
core.send(UserPromptRequest(request_id, "Connect the DUT", ("OK", "Abort")))
answer = pending.wait(request_id)               # None if it timed out

# event loop, draining the inbox
case UserPromptResponse(request_id=rid, choice=choice):
    pending.resolve(rid, choice)
The thread that calls wait() must not be the thread draining the channel, or the answer can never arrive and the module deadlocks. The Sequencer is single-threaded today, so porting user-interaction steps means running the sequence on a worker thread while the event loop keeps turning. Noted as a TODO in the roadmap.

Shutdown — one path, and it is idempotent

HMI request_shutdown() ──ShutdownRequested──► CORE CORE stop_all_modules() ──StopReport──► Report ──ReportStopped──► CORE ──StopSequencer──► Sequencer ──SequencerStopped──► CORE ──StopHmi──► HMI ──HmiStopped──► CORE CORE exits once no module is still running. launcher (after joining the UI process): ──HmiStopped──► CORE (states as fact what CORE would otherwise wait for) ──ShutdownRequested──► CORE (second request; stop_all_modules() guards itself) join(5 s) else terminate() ─► then StopLogger, join(5 s) else terminate()

A frontend never stops itself: it asks, and CORE brings everything down in order. The launcher is the supervisor of last resort and uses the same channel, because CORE having exactly one shutdown path is worth more than the launcher having a link of its own.

9. What is real, what is a stub

Real todayDeclared but not carried out
  • Channel + trace, all 7 queues, all 6 handlers
  • Every union, every dataclass, the pickle guarantee
  • Heartbeats, error reporting, the full shutdown handshake
  • GUI and CLI sharing one protocol implementation
  • The Logger: single writer, control messages, drain on stop
  • Core.load_recipe() — recipe layer not ported; answers StatusChanged, never RecipeLoaded
  • Sequencer.run_sequence() — execution engine not ported, so no run-progress event is ever emitted yet
  • Report.generate_report() / export_report() — CSV/HTML logic not ported
  • SetConfigParameter — CORE logs and ignores it; propagating a change to running processes is unsolved
  • PendingRequests — lands with the execution engine

The messages exist ahead of their senders on purpose: the CLI, the GUI and the Report all have to agree on them, and agreeing before the call sites exist is much cheaper than agreeing after.
