1. Where these five sit

The messages package splits cleanly in two. Four modules are link contracts — core_hmi_communication.py, core_sequencer_communication.py, core_report_communication.py, to_logger_communication.py — each declaring the messages of one link and the union type per direction. The five files in this report are everything else: the substrate those contracts are written on top of.

They are not five variations of one idea. Each answers a different question, and the four questions do not intersect:

FileAnswersKind of thingSize
queue_wrapper.pyHow does a message move, and how is a handler kept complete?Behaviour (one class, one function, one exception)9.6 kB
links.pyWhat is each direction called? Seven string constants, nothing else1.1 kB
common_messages.pyWhat vocabulary does more than one link need?Data (2 enums, 3 dataclasses)3.3 kB
run_events.pyWhat does a run look like from outside the engine?Data (11 dataclasses)5.1 kB
blocking_messages.pyHow does the asker block until an answer comes back?Behaviour (one class)3.6 kB

Import layering

Verified against the source: there is exactly one import edge among the five, and none of them imports a link module. That is what makes the package's dependency graph a layering rather than a web.

links.py queue_wrapper.py blocking_messages.py (imports (logging, queue, (queue, threading, nothing) typing) uuid) │ │ │ │ │ │ no messages import at │ │ │ all - generic machinery ▼ ▼ ▼ ┌──────────────────────────────────────────────────────────┐ │ used by launcher, core, logger, hmi, sequencer, report │ └──────────────────────────────────────────────────────────┘ common_messages.py ◄────────────── run_events.py the one edge: (stdlib only) ResultType, StepOutcome run_events is built ▲ ▲ out of the value types │ │ every link module core_hmi_communication.py, core_sequencer_communication.py (Heartbeat, ModuleError)
Two deliberate cycle-breaks. links.py imports nothing at all, which is what lets both messages and logger use it. queue_wrapper.py reaches its logger with logging.getLogger("pypts.trace") rather than importing pypts.logger.log, because log.py imports it. Both are stated in the source docstrings, not inferred here.

2. common_messages.py — vocabulary shared by more than one link

LIVE All five types are sent or consumed today.

NameWhat it isWho uses it
ErrorSeverityEnum: WARNING / ERROR / CRITICAL utilities/error_handling.py, CORE (decides what the operator sees)
ModuleErrorfrozen dataclass: source, severity, message, exception, traceback, operation, error_typeSent by the two decorators in utilities/error_handling.py, and by report_error() / report_problem() from a raise site that recognised the failure itself; in all three engine link unions
Heartbeatfrozen dataclass: source, timestamp utilities/heartbeat_manager.py; in all three link unions
ResultTypeIntEnum: SKIP 0 … STOP 5 run_events.py, CLI, GUI, hmi_client.py
StepOutcomefrozen dataclass: step_id, step_name, result, error_infosame as above

Responsibility

Hold the types that would otherwise be declared twice — or, worse, be repacked on the way through CORE. The docstring is explicit that this is a reaction to a real defect: the old code flattened ModuleErrorEvent into a five-key dict at every sender, which downgraded severity from an enum to a string, and CORE never rebuilt it. Putting the type here means CORE forwards the same object from one link to another.

Decisions worth knowing

  • Heartbeat.source looks redundant — CORE knows which queue it drained — but it lets one CORE handler serve all three links instead of three near-identical ones.
  • ResultType's integer order is load-bearing: a group aggregates to the highest member, so one FAIL among PASSes makes the group FAIL. Ported unchanged from old_code/recipe.py.
  • StepOutcome is deliberately not old_code's StepResult. StepResult holds a live Step and a tree of subresults; neither may cross the HMI process boundary. The Report gets the rich object in-engine, the HMI gets this.

3. run_events.py — what the engine reports while a recipe runs

MOSTLY STUB Declared and wired into two link unions; almost nothing emits them, because Sequencer.run_sequence() is not ported.

Eleven frozen dataclasses in two groups.

GroupMembersCarries
Progress (7)RecipeLoaded, RunStarted, RunFinished, SequenceStarted, SequenceFinished, StepStarted, StepFinished Names, a ResultType, and StepOutcomes
Questions (4)UserPromptRequest/Response, SerialNumberRequest/Response A request_id: UUID plus the question or the answer

Responsibility

These originate in the Sequencer, travel to CORE, and CORE forwards them unchanged to the HMI. Because each therefore appears in both core_sequencer_communication's union and core_hmi_communication's union, it has to be defined in one place that is neither — this file. The set is a one-for-one port of the nine Qt signals in old_code/event_proxy.py, which the docstring calls the closest thing the project has to a requirements document for what a frontend needs in order to draw a run.

Decisions worth knowing

  • A message says what happened, never how to draw it. The old proxy's colour lookup (get_step_result_colors) is presentation and stays in the GUI.
  • RunFinished.outcomes is flat and in execution order. The old engine handed the GUI a nested tree; nesting is a Report concern and the results table only ever walked it flat.
  • The request_id is the whole reason a question can cross a process boundary. The old engine put a live SimpleQueue inside the event and had the GUI answer straight into it — which only worked because both ends were threads in one process.
  • Declared before the senders exist on purpose: the CLI, the GUI and the Report all have to agree on this set, and agreeing before the call sites exist is cheaper than after.

4. blocking_messages.py — the waiting half of a request/response pair

HALF-WIRED The Sequencer owns a PendingRequests and calls return_caller(); nothing calls start()/wait() yet.

One class, PendingRequests, and one constant, DEFAULT_TIMEOUT_S = 300.0 (five minutes — matching the timeout the old interaction steps allowed an operator standing at the bench). Internally: a dict[UUID, SimpleQueue] behind a Lock.

MethodCalled byContract
start(request_id)the asker, before sending Registering after the send would race a fast responder and the answer would be dropped as unknown
wait(request_id, timeout_s=None)the asker Blocks; returns the value, or None on timeout. Always removes the entry, so a late answer is discarded by return_caller() rather than handed to nobody. Raises KeyError if start() was never called
return_caller(request_id, value)the event loop draining the inbox Returns False if nobody is waiting — the caller should log that, it means the two ends disagree about what is in flight
cancel(request_id)internal / cleanup Idempotent, so wait() can call it unconditionally in a finally

Responsibility

Turn an asynchronous message pair into a blocking call, without either half knowing about queues or links. Note what this file does not import: nothing from messages at all. It is generic machinery keyed by UUID — the UserPromptRequest half lives in run_events.py, and the two are joined only by the id.

Threading constraint, stated in the docstring. The thread that calls wait() must not be the thread that drains the inbox, or the answer can never arrive and the module deadlocks. The Sequencer is single-threaded today, so porting the user-interaction steps in Phase 1 means running the sequence on its own worker thread while the event loop keeps turning.

What is wired today: Sequencer.__init__ constructs self.pending (sequencer.py:63) and deliver_response() calls self.pending.return_caller(...), warning when nobody was waiting (sequencer.py:141). The asking side arrives with the execution engine.

5. queue_wrapper.py — the one transport

LIVE Every message in the framework passes through this class; seven wrappers are built at startup.

Three public names — QueueWrapper, unhandled(), UnhandledMessage — and they are the only things messages/__init__.py re-exports.

QueueWrapper[Msg] — a typed handle on one direction of one link

  • Duck-typed queue. It accepts any object with put() and get_nowait(). That single decision is what lets the same class serve a process boundary (multiprocessing.Queue for HMI↔CORE), a thread boundary (queue.Queue for Sequencer and Report), and a future socket-backed queue-alike for --mode connect. No module ever learns which one it holds.
  • Nothing ever blocks. receive() is a generator that yields what is on the queue right now, up to DEFAULT_BATCH = 64. The limit stops a busy link starving the other inboxes in the same tick; a generator rather than a list, so a caller that breaks early leaves the rest queued instead of having paid to remove it.
  • Topology by construction. A wrapper is built by whoever owns the link — the launcher builds the HMI↔CORE pair, CORE builds its links to the Sequencer and the Report — and handed to the module that uses it. A module cannot invent a link to somebody it has no business talking to.
  • Self-tracing. send() and receive() each emit one DEBUG line on the pypts.trace logger. A run at --log-level DEBUG therefore contains every message twice, and a message that was sent and never received — the failure actually worth seeing — becomes visible. Because the trace sits on the object every message already passes through, no module has to remember to log and no new message can escape it.
  • Counters. sent and received, incremented after the put and as the message is handed to the caller, so neither number ever claims something that did not happen. They belong to the holder, not to the link: a wrapper pickled into a child process gives that child its own copy.

unhandled() — the closing case of every handler

Two jobs in one call. Its parameter is typed Never, so a type checker accepts the call only when every member of the union has already been matched — a forgotten message is a reported error. At runtime it raises UnhandledMessage, so the same mistake is loud in a plain run where no checker was involved. It replaces the old case _: pass, under which CORE quietly discarded every error the HMI reported.

Micro-detail that is easy to undo by accident. The trace uses %-style arguments (_trace.debug("send %s %r", …)) so the repr() is computed only if a handler will actually emit. Below DEBUG the whole method costs one cached level check. Rewriting it as an f-string would silently make every send pay for a repr it throws away.

6. links.py — the name of every direction

LIVE All seven constants are in use.

HMI_TO_CORE = "hmi->core"          CORE_TO_HMI = "core->hmi"
CORE_TO_SEQUENCER = "core->sequencer"   SEQUENCER_TO_CORE = "sequencer->core"
CORE_TO_REPORT = "core->report"    REPORT_TO_CORE = "report->core"
ANY_TO_LOGGER = "any->logger"

Responsibility

One string per direction, defined once, so the launcher, CORE and anyone reading a log cannot drift apart on spelling. They are handed to QueueWrapper(link=…) by whoever builds the wrapper, and they are what a trace line is identified by — which makes grep 'sequencer->core' pypts_*.log the whole-system view of one link.

This matters more than it looks. The Sequencer and the Report are threads of the Core process, so %(processName)s says Core for their records too. The link name is the only thing in the run log that tells those two apart.

ANY_TO_LOGGER is not a link between two modules but the one path out of every process; the docstring says it is named here with the rest rather than being the single anonymous wrapper. Consumers today: launcher/startup.py (3), core/core.py (4), logger/log.py (1), plus helper_applications/debug_monitor, which builds its filter checkboxes from these names rather than spelling them again.

7. Overlap analysis

Short answer: there is no duplicated functionality among the five. Each owns a distinct axis, and removing any one of them breaks something the others cannot supply. There are, however, four seams where two files describe adjacent halves of one idea, and one place where the same information genuinely exists twice — by design.

AxisOwnerIf it were removed
Movementqueue_wrapper.pyEvery module touches a raw queue — the thing the architecture exists to prevent
Identitylinks.pyLink names get spelled inline at seven call sites; the trace and the log filters drift
Cross-link payloadscommon_messages.pyHeartbeat and ModuleError get declared per link, and CORE cannot forward one object
Run narrativerun_events.pyThe eleven progress/question types get declared twice, once per union
Ask-and-blockblocking_messages.pyEvery asker re-invents an id→queue map with its own locking and timeout

Seam A — common_messages.py ↔ run_events.py: the criterion does not describe half the file

Both files hold "types more than one place needs", so the boundary between them is the one worth checking. common_messages.py's docstring states the rule: "A type belongs here when it appears in at least two link modules." Checked against the imports:

  • Heartbeat and ModuleError — imported by all three engine link modules. The rule holds exactly.
  • ResultType and StepOutcome — imported by no link module at all. The only importer inside messages/ is run_events.py; outside it, the CLI, the GUI and hmi_client.py take them straight from common.

So half of common_messages.py is there for a different reason than the one written down: not "used by two links", but "value types that the run events are built out of and that a frontend renders directly". That is a defensible reason — StepOutcome is what a results table draws, independently of which message delivered it — but as written, the file's own rule would put both types in run_events.py.

Recommendation: restate the criterion rather than move the types. The header line already says "vocabulary shared by more than one link"; widening that to "more than one module" makes it true of all five members, and keeps the HMI importing a value type from a file that has no run-progress semantics in it.

Seam B — blocking_messages.py ↔ run_events.py: one mechanism, two files

A request/response round trip is split: the four dataclasses are in run_events.py, the waiting machinery is in blocking_messages.py, and the only thing joining them is the request_id. Neither file imports the other.

This is the right split, and it is load-bearing rather than cosmetic: PendingRequests imports nothing from messages, so it works for any future request/response pair without touching the message layer, and the messages stay pure data with no threading in them. The only cost is that reading either file alone does not tell the whole story — already mitigated, since run_events.py ends its questions section with "The waiting side is in blocking_messages.py" and blocking_messages.py opens with a worked example of both halves.

Seam C — links.py ↔ queue_wrapper.py: naming is a convention, not a constraint

QueueWrapper.__init__ takes link: str = "". Nothing checks that the string came from links.py; a typo — "core->hmi ", "core→hmi" — constructs happily and produces trace lines that no grep and no Monitor filter will match. An unnamed wrapper traces as "?", which the tests rely on, so the empty default is intentional.

This is not overlap; it is a missing constraint at the join between the two files. Cheap and low-risk to tighten (a StrEnum, or Literal[…] on the parameter), and all seven production call sites already import from links.py, so nothing would have to change to satisfy it. Worth raising as a roadmap TODO rather than doing unasked.

Seam D — queue_wrapper.py also owns a log format

The trace text "send <link> <repr>" / "recv <link> <repr>" is not private to this file. helper_applications/debug_monitor/ trace_parser.py re-derives it with a regex, matching on the two method names (send, receive) and the two prefixes (send , recv ) — and it documents the mismatch between them, because both are needed. The Monitor's own docstring names this: "the trace text lives in pypts/messages/queue_wrapper.py; if it changes, this file is what has to follow."

So queue_wrapper.py owns one thing beyond transport: an implicit wire format for the run log, with a consumer in another package. It is not duplicated inside the five files, but it is the one responsibility in them that leaks outside the module, and it is the reason a one-word change to a debug string is a breaking change.

The one genuine duplication: counters vs. the trace

QueueWrapper.sent/received and the DEBUG trace answer the same question — how many messages moved on this link. Both live in the same file, and the docstring already argues the case: the counters are per-holder, always on, and readable in-process; the trace is whole-system, DEBUG-only, and written to one file by the Logger regardless of which process emitted it. Neither can be derived from the other at runtime. Complementary, not redundant — but it is worth knowing that a number and a log line can disagree, and that when they do, the trace is the whole-system view.

One judgement call worth recording

unhandled() and UnhandledMessage live in queue_wrapper.py, and they have nothing to do with a queue — they are the handler side of the contract. The justification is that the transport and the exhaustive match are two halves of "a typed link", and that messages/__init__.py re-exports all three names together, so nobody imports them by path anyway. A reader looking for unhandled() would probably not guess the file, and a third of the module docstring is spent on something the module title does not cover. Not a defect; the alternative (a handlers.py holding two names) is arguably worse.

8. Drift found while reading

messages.md says PendingRequests has no user. It has half of one. sequencer.py:63 constructs self.pending = PendingRequests() and sequencer.py:141 calls self.pending.return_caller(...) from deliver_response(), logging a warning when nobody was waiting. What has no user is the asking side — start() and wait() — which lands with the execution engine, exactly as the threading note predicts. The catalogue's open-items list is accurate about the constraint and stale about the status.

Nothing else read here contradicted messages.md, the roadmap or CLAUDE.md. The statuses in this report (LIVE / HALF-WIRED / MOSTLY STUB) were taken from the call sites, not from the docs.
