The shape today

The launcher module presents one interface: main() -> None, plus sys.argv. Behind it are 145 lines that resolve the configuration, resolve the log level, decide the stdout policy, create three queues, start two processes and one subprocess, run the frontend, and shut everything down in order. There is no seam between deciding and doing, so nothing between line 128 and line 241 can be exercised without spawning the real system.

Deepening candidates

1

The boot sequence has no interface, so its decisions cannot be read without starting the system

Strong in-process
launcher/startup.py:78–241 · tests/unit_tests/test_startup.py:83–113 · tests/functional_tests/test_launcher.py (6 skipped)
Problem
Deciding and doing are interleaved line by line, so every decision the launcher makes — which level, which log file, whether stdout echoes, which frontend, which notice — is observable only by spawning the processes that consume it. The one test that calls main() stops it by monkeypatching ConfigHandler.bootstrap to raise, which is the honest measure of the interface: there is no other way in.
Solution
One seam, where facts stop being decided and start being acted on. resolve_run(argv, config) returns a RunPlan — mode, level, log file path, stdout policy, the notice if any, whether the Monitor is wanted — and main() becomes plan, start, stop. The spawner is a parameter, so a test substitutes a recorder for Process.
Wins
  • The interface becomes the test surface
  • Locality: every boot decision in one place
  • Six skipped functional tests become unit tests
  • Leverage: candidates 2, 4, 5, 6 land on it

2

mode is a bare string compared in five places, and one of its three values silently does the wrong thing

Strong in-process
launcher/startup.py:91–96, 132, 139, 162, 213–222, 248 · launcher/startup.py:44–45 (the GUI import)
Problem
argparse declares three modes; the implementation branches on == "gui" and lets everything else fall through to the CLI. --mode connect therefore starts a CLI and says nothing — the interface promises a mode that does not exist. The same string is compared again for the notice channel, for the stdout policy and for the process branch, so four facts are derived independently from one word. And because gui_main is imported at module level, --mode cli loads PySide6 anyway (recorded, roadmap §1.2).
Solution
One table keyed by mode, holding what the mode actually determines: how the frontend starts, whether it runs in its own process, whether stdout echoes, how a notice is shown. connect gets an entry that refuses with a message instead of an entry that lies. The frontend import moves inside its own starter.
Wins
  • connect refuses instead of pretending
  • Locality: one row per mode, four facts each
  • A CLI bench stops importing Qt
  • A fourth mode is a row, not five edits
Before — one string, four re-derivations

3

The Logger is started outside the block that stops it, so a failure in the next four lines hangs the run

Strong in-process
launcher/startup.py:165–177, 182, 235–241 · logger/log.py:155–177 (the blocking loop)
Problem
logger_process.start() is at line 170; the try whose finally sends StopLogger opens at 182. Between them sit init_logging() and two Queue() constructions. Anything raised there escapes with a live, non-daemon Logger blocked in log_queue.get() — a loop only StopLogger ends — and interpreter exit joins it. The launcher does not crash; it hangs, and has to be killed.
Solution
Make the Logger's lifetime the interface: a context manager that starts the process, yields the control wrapper, and on exit sends StopLogger, joins with the timeout, and terminates if it must. Start and stop stop being two places that have to agree.
Wins
  • No window where a child outlives its stopper
  • Locality: one module owns start, stop, timeout
  • Shutdown order becomes nesting, not line order
Before — the gap
170 start() 172–177 182 try: 238 StopLogger
a raise in the red band → the Logger is never told to stop → exit blocks on join
After — one bracket
with running_logger(path, stdout) as control:
start · yield · StopLogger · join · terminate
no line can fall between the start and the stop
4

The configuration is built so a bad file cannot stop the run; the launcher then lets one of its values do exactly that

Strong in-process
launcher/startup.py:155 · utilities/local_storage.py:31–50 · config_handler/config_handler.py:96–111
Problem
get_log_file_path(config.get_parameter("paths.logs_dir")) creates the directory, and the value is user-editable in config.ini. An unwritable or invalid path raises OSError at line 155 — before the Logger exists, before the try, and after the notice machinery has already run — so the operator gets a bare traceback on stderr, no log file and no notice. DISCARDED exists precisely so that a bad configuration degrades to defaults with a notice; that policy stops at the config module's edge.
Solution
Give the launcher the same policy for the values it consumes that the config module has for the file: resolving the log destination is one call that either returns a usable path or falls back to the template default and reports why, through the notice channel candidate 5 defines.
Wins
  • One rule for a bad configuration, file or value
  • A run always has a log to explain itself
  • The operator gets a notice, not a traceback
Before — two policies for one class of error
config.ini broken → DISCARDED → defaults, notice, ERROR in the log
paths.logs_dir bad → OSError at :155 → traceback, no log, no notice
the careful path and the fatal path are one line apart
After
resolve_log_destination(config) → path, notice?
try the configured directory, fall back to the
template default, report the reason the same way
the run survives every value the user can type

The launcher phrases the configuration module's errors, so it has to know which field belongs to which outcome

Worth exploring in-process
launcher/startup.py:128–148, 244–254 · config_handler/config_handler.py:96–111, 241–266
Problem
bootstrap() hands back a handler; the launcher reassembles the story from three of its attributes and hard-codes both messages, including which outcome carries a bootstrap_problem and which does not. The config module's interface has leaked its enum, its field-per-outcome rule and its wording into a module whose stated job is starting processes. A fourth outcome is an edit here.
Solution
config.bootstrap_notice() -> Notice | None, carrying title, text and severity. The launcher keeps only what is genuinely its own: which channel this mode can show a notice on. show_config_popup(mode, title, text, warning=) narrows to show_notice(mode, notice).
Wins
  • Interface shrinks from four facts to one
  • Locality: outcomes and their wording in one module
  • The launcher stops phrasing config errors
  • Candidate 4's fallback reuses the channel

6

Nothing watches CORE, though the module docstring promises a supervisor

Worth exploring ports & adapters
launcher/startup.py:8–11, 213–222 · messages/core_hmi_communication.py:125–136 · core/core.py:536–556
Problem
The docstring says the launcher owns the process tree and "has to survive anything the others do", but in GUI mode main() blocks on ui_process.join() and waits for exactly one child. Heartbeat is a member of HmiToCore only: CORE watches the frontend and its own threads, and no one watches CORE. If CORE dies, the GUI keeps drawing against a dead link, the launcher stays blocked, and the operator has a window that is alive and answers nothing.
Solution
Either narrow the promise — say in the docstring that the launcher reaps and does not supervise — or put supervision behind the seam candidate 1 creates: supervise(children) waits for the first child to exit, whichever it is, and brings the rest down through the existing shutdown path.
Wins
  • A dead CORE ends the run instead of freezing it
  • One place decides what a lost child means
  • Docstring and behaviour say the same thing

7

A developer tool sits in the boot path, and can delay CORE by five seconds

Worth exploring local-substitutable
launcher/startup.py:20–31, 202–203, 206–211, 283–331
Problem
start_debug_monitor() polls for the run log until it exists or MONITOR_LOG_WAIT_S elapses, and it is called before CORE is started — with the Monitor on by default. The usual case costs one is_file(), but a slow or failed Logger delays the whole run by up to five seconds before CORE has been spawned at all. The module docstring is explicit that the Monitor "cannot stop the run"; today it can hold it up.
Solution
Start CORE and the frontend first and the Monitor last, so the wait overlaps a run that is already up; or hand the wait to the Monitor itself, which is the module that knows why it needs the file.
Wins
  • The tool cannot delay the framework
  • Boot order matches the stated dependency
  • The wait lives with the reason for it
Before
Logger Monitor wait CORE frontend
the framework waits behind a tool that only reads a file
After
Logger CORE frontend Monitor wait
the wait overlaps a run that is already going

Already on the books — not re-litigated here

  • stop_core() forges HmiStopped() on the frontend's behalf — card 8 of architecture_deepening_review.html. Still the widest leak in this file; it is recorded, so it gets a pointer rather than a card.
  • --mode cli imports PySide6 — roadmap §1.2 TODO. Folded into candidate 2, where the fix falls out of the mode table instead of being a separate change.
  • --mode connect unimplemented — roadmap TODO. Candidate 2 does not implement it; it makes the launcher say so instead of starting the wrong frontend.
  • Monitor TODOs — inherited stdout, Ctrl+C reaching the child, pid under a venv — roadmap §1.4.1. Candidate 7 is about boot ordering only and touches none of them.

Where the depth already is — do not "fix" these

  • _open_message_box() split out of show_config_popup() — an internal seam that exists so three tests can make the popup fail on purpose. Exactly the shape this review is asking for elsewhere.
  • stop_core()'s ask-then-kill order — a small interface over a real invariant, and the only part of the shutdown covered by tests.
  • The spawn pin — four lines, ten lines of comment saying why, and a test that asserts both branches.
  • The Monitor started as a string, never an import — the one-way dependency is enforced by the shape of the call, not by a convention.

Top recommendation

1 — Put a seam between deciding and doing

It is the candidate the others are waiting on. A RunPlan gives candidate 2 somewhere for the mode table to land, candidate 4 somewhere to fall back to, candidate 5 somewhere to carry a notice, and candidate 6 somewhere to hold the child list. It is also the only one that moves the test story: the six skipped placeholders in test_launcher.py exist because the facts they want to assert are unreachable today, and most of them are properties of the plan rather than of the running system.
