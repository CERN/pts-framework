XY graph + stream container — design

2026-10-19 · branch architecture_refactor · status: agreed design, not implemented · revised 2026-11-02 with every review decision (blockers B1–B4, all high, medium and minor findings, Q1–Q8)

1. Goal

A PythonModule step's test function produces live data (a demo sine wave), registers it under a name in a stream container, and the GUI draws it live in an XY graph while any step whose recipe says graph: <name> runs. The stream container is not part of the HAL (revised 2026-10-19, §3). The XY graph code is copied from C:/git/pyrade_xy_graph (GitLab pyrade/hmi/gui/pyrade_xy_graph) for now and becomes a package / sub-repository later.

2a. Architecture pictures

3. Stream container — src/pypts/stream_handler/ (fills the stub)

Why not the HAL: the HAL is about devices and is meant to ship on its own; streams need no device (the sine demo is simulated) and a driver runs in its own process, so it could never call the container directly anyway. Keeping the container free of every other pypts import means it can ship on its own too.

from pypts.stream_handler import register_stream

stream = register_stream("sine", unit="V")
stream.push(t, y)          # one sample, or two equal-length arrays
stream.close()
  • No imports from the rest of pypts. A StreamSession(folder) is the per-run container. It tells nobody when a stream opens: the file appearing is the signal (§4).
  • One active session per process, the whole pattern of the active LocalSetup (hal/local_setup.py) — the slot, its lock, the identity-based deactivate (a nested with StreamSession does not clear the outer one), and the abandon fence (below).
  • Where the Sequencer opens it (review M2). In execute_sequence(), where run_dir (made by start_run_folder()) is in scope — not in run_body(), where the with LocalSetup(...) block is. The session closes its streams just before RunFinished is sent.
  • In a plain script, with StreamSession("some/folder"): activates one, as LocalSetup.from_ini() does for devices.
  • No run folder (review B1/Q2). StreamSession(None) is a session with streams off: register_stream returns a Stream whose push() writes nothing, so test code needs no special case. The Sequencer opens it this way when run_dir is empty; the session itself logs one WARNING on its first registration (only it sees registrations — there is no callback), e.g. Stream 'sine' is not recorded: this run has no run folder. (wording per logger/logging_rules.md).
  • stream_csv_path(folder, name) is the one path rule: <folder>/streams/<safe name>.csv. The container writes there and the GUI reads there, so the two sides cannot disagree. Safe name (review H3): the same rule as utilities.local_storage.safe_name_part() — alphanumerics kept, everything else an underscore, at most 60 characters — written out in the container itself, which imports nothing else from pypts. So ch?1, a/b, V:out and ..\report all stay inside streams/.
  • register_stream(name, unit=None) opens (append mode) the file at stream_csv_path() and, if the file is new, writes the header row: x,y [<unit>], or x,y with no unit. The unit lives in the file, so headless runs, which keep only the files, keep it too.
  • CSV dialect (review M3), owned here: csv.writer on a file opened with newline='', encoding='utf-8' — the run folder's convention from report/report.py. Rows end in \r\n; the GUI reader is written against exactly this.
  • Stream.push(x, y) appends rows (one sample, or two equal-length arrays) and flushes once per call; guarded by a lock so a background thread may push. The demo pushes in small batches.
  • Stream.close() closes the file under the same lock; idempotent. At run end the session closes every stream still open.
  • Lifetime rules (review H1, H2, Q6).
    • Push after close — the stream's own, or the run end's — is dropped silently, with one DEBUG line per stream. A background thread outliving its step cannot raise on a bare thread.
    • Abandon fence: when the Sequencer ends a run it marks the session abandoned (as abandon_active_setup() does for devices). A handle from that run then drops its pushes the same way; it never resolves the next run's session, so run 1's data cannot land in run 2's streams/.
    • Re-registering a name appends to the same file; x must keep rising per name (caller's duty).
  • With no active session, register_stream raises a clear error (as get_device does).
  • For the engine-side WARNING (§6) the session answers has_stream(name) — was this name registered in this run.
  • Public API in stream_handler/__init__.py: register_stream, Stream, StreamSession, stream_csv_path.

4. Connection layer — no new message

Decided 2026-11-02 (review Q1): the CSV file is the entire contract between CORE and the GUI.

  • The GUI already receives the run folder in RunStarted.run_dir, and the step's graph: X (on StepSummary.graph, §5) names the stream. stream_csv_path(run_dir, X) gives the file.
  • Whether the stream exists yet is answered by whether the file exists — the GUI polls on its graph timer, the same way it already follows the run log (it opens the log once the Logger has created it).
  • The unit comes from the CSV header row (§3).
  • Nothing is added to messages/ except the StepSummary.graph field; no new message, no CORE routing change, no hmi_client.py hook, no Sequencer callback.

5. Recipe key

- steptype: PythonModule
  step_name: Sine sweep
  module: sine_tests.py
  action_type: method
  method_name: run_sine
  graph: sine
  • graph: str | None = None on _StepFields in recipe/recipe_schema.py (and STEP_COMMON_DEFAULTS), stored as step.graph by Step.__init__.
  • Sequence steps (review B3, decided 2026-11-02: supported). build_step() passes every YAML key to the constructor (step/registry.py), and SequenceStep.__init__ lists its parameters with no **kwargs — so graph: str | None = None is added there explicitly and passed on to Step.__init__, exactly as image_path is. Without it a schema-valid recipe would fail to load with a TypeError.
  • On a group it means what image_path means there: the innermost one wins. The group's graph shows while its inner steps run; an inner step with its own graph or image_path takes the right column while that step runs, and the group's graph returns after it (same stack rule as RunDisplay.image_path in hmi/gui/run_display.py).
  • Carried to the frontend on StepSummary.graph (messages/run_events.py), so the GUI knows at recipe load which rows want a graph.
  • Indexed: the wrapper's value goes on every generated step unless the template names its own (same rule as image_path).
  • A number as a name (graph: 07) is read by YAML as a number and becomes '7'; recipe_guide.html says to quote such names (graph: "07").

6. GUI

  • A new small widget in hmi/gui/ (e.g. stream_graph.py) wraps pyrade_xy_graph.ui.plot_widget.ScopePlotWidget + pyrade_xy_graph.core.data_store.DataStore. The two are not wired upstream (the glue lives in graph_widget.py, which PyPTS does not import), so the wrapper re-creates it: data_updated → get_signal → update_signal, with the x key set explicitly (the DataStore default is 'Time') (review M5).
  • Tailing (review M3): no second tailer. The existing hmi/gui/log_tail.py:LogTail already handles torn-line hold-back, open-when-created and the Windows share mode; it is reused, or its line logic extracted into a shared helper, for the CSV files.
  • Bounded (review H6): the DataStore gets a fixed max_len (a scope window, one named constant in the wrapper); the reader keeps a byte offset per stream name instead of re-reading from 0 on every StepStarted; the rows read in one timer tick go in as one batch, so one repaint per tick.
  • The GUI keeps the current run's run_dir from RunStarted and builds each path with stream_csv_path(run_dir, X).
  • On StepStarted for a row with graph: X: the right column swaps the picture for the graph, clears it, and a QTimer (a few times a second) reads X.csv from the start and then new lines. While the file does not exist yet, the graph shows "Waiting for stream X" and the same timer checks again. With an empty run_dir (no run folder, review B1/Q2) there is no file to wait for: no picture area.
  • Question picture (review B2, decided 2026-11-02). While a question with its own picture is open on a step with a graph, the question's picture takes the area (as a question picture does today). When it is answered the graph returns and catches up from its byte offset; the stream kept recording meanwhile.
  • Run end (review H5). On RunFinished the graph is torn down and the logo marked with the run verdict (set_run_result()) shows, held until the next run — as today.
  • The graph lives exactly while its step runs (review Q3, decided 2026-11-02). On that step's StepFinished the running stack pops and the right column shows what it would show without the graph: the enclosing group's picture or graph (§5), or no picture area — the same repaint a picture gets today (RunDisplay + CenterContent._show_run_view()). The graph is one more state of that one decider, not a widget managed beside it (review B2).
  • Looking back (decided 2026-11-02). A look-back (gui.md §19) at a step that had a graph — during or after the run, by the same rules and with the same end conditions as a picture — draws a static graph of the whole file at stream_csv_path(run_dir, X), read once at the click (a snapshot; a stream still being written does not update it), where the step's picture would go. RunDisplay's _Seen records the graph on screen at StepStarted — an inherited group graph included — next to image_path, and StepReview carries it. If the file does not exist (the stream was never registered, or a run without a folder, review Q2): no picture area (show_no_picture()), as for a step without a picture. After the run the GUI still holds that run_dir, until the next RunStarted or recipe load (both end a look-back anyway).
  • The typo WARNING is not the GUI's (review H4/Q4). The Sequencer, which opens the session and sees every step finish, logs it: when a step with graph: X finishes and session.has_stream(X) is false, one WARNING in the run log, e.g. Step 'Watch it' shows graph 'bg_sine', but no stream of that name was registered. (wording per logger/logging_rules.md). Not logged in a run without a folder, which already has its own WARNING. CLI and headless see it too.

7. Copied code — src/pyrade_xy_graph/

  • Copy of pyrade_xy_graph/ (core/, ui/, main.py, __init__.py); no tests/, no old_graph/, no committed .DS_Store/.pyc.
  • Documented deviations from upstream (review M5/Q5, option a) — each one line, listed in a DEVIATIONS note in the folder so the later swap knows what to re-apply or get merged upstream:
    • ui/plot_widget.py: the tdms_exporter import is dropped — it registers a TDMS entry in pyqtgraph's right-click Export dialog that crashes (nptdms is not installed).
    • ui/plot_widget.py: the import-time global pg.setConfigOptions(...) is dropped (or moved onto the widget), so it neither changes pyqtgraph for the whole process nor ignores the GUI's dark palette.
    core/trace_level.py was checked (2026-11-02, upstream af9e4b0): it registers TRACE = 5 under the name TRACE, exactly as pypts/logger/levels.py does, and adds Logger.trace() only if absent — no clash, kept unchanged. The packaging hygiene (requires-python >=3.9 wrong, stale pymeasure) is upstream's pyproject.toml, which is not copied — reported to the author.
  • Added to packaging ([tool.setuptools.packages.find]) as a second top-level package — a conscious choice, temporary until the swap. Excluded from ruff; mypy needs nothing ([tool.mypy] is an opt-in files list and the folder is simply not on it).
  • New dependency: pyqtgraph. The plot path needs only that and numpy; h5py/nptdms/pandas are used only by parts PyPTS does not call — they are not added. matplotlib, unused in src/, is removed from [project].dependencies in the same change.
  • Later swap: delete the folder, add the package or sub-repository; no PyPTS code changes.
