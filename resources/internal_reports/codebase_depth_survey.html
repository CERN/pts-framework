Codebase Depth Survey

src/pypts/ excluding old_code/ · branch architecture_refactor · 2 September 2026
Read: messages/ (all), core/core.py, sequencer/sequencer.py, step/ (all), recipe/ (all), report/report.py, hmi/hmi_client.py, hmi/gui/*, config_handler/, utilities/, hardware_layer/hal.py — about 16,300 lines. Analysis only; no files were changed.

This tree is unusually deep already. A survey like this normally turns up a layer of pass-throughs. This one does not — the depth is deliberate, and in several places the reasoning is written down in the docstring beside the code.

So what follows is a short list of specific seams in the wrong place, not a general indictment. Four findings are worth acting on; two are recorded so they are not rediscovered later as surprises.

The vocabulary this uses

Interface — everything a caller must know to use a module correctly: the signature, but also invariants, ordering constraints, error modes and required configuration.
Depth — leverage at the interface. How much behaviour a caller or a test can exercise per unit of interface they have to learn.
Seam — a place where behaviour can be altered without editing in that place. Where the seam goes is its own decision, separate from what sits behind it.
Adapter — a concrete thing satisfying an interface at a seam. One adapter is a hypothetical seam; two adapters is a real one.
Deletion test — imagine deleting the module. If complexity vanishes it was a pass-through. If it reappears across N callers, it was earning its keep.
Locality — what maintainers get from depth: change, bugs and verification concentrate in one place instead of spreading across callers.

Where the depth already is — do not "fix" these

QueueWrapper

DEEPEST IN THE TREE

messages/queue_wrapper.py

send(msg)  |  receive(limit)  |  link=
transport-agnosticism · DEBUG trace on both sides
batch cap · per-holder counters · generator semantics
two methods over seven links and two transports

Behind two methods: transport-agnosticism, the DEBUG trace on both send and receive, the batch cap that stopped one busy link starving the other inboxes, per-holder counters, and generator semantics so a caller that stops early leaves the rest queued.

Two genuine adapters — multiprocessing.Queue across the HMI seam, queue.Queue inside the engine — so this is a real seam, not a hypothetical one. Deletion test: seven links re-implement tracing and batching. It replaced 612 lines with about 200 and the leverage went up.

Step

DEEP

step/step.py

_step(runtime, step_input) -> Any
resolve inputs · five output-judging types · verdict aggregation
exception → StepResult · three emitted events
timing · skip / continue_on_error
WaitStep's whole body is twelve lines

A step author learns one method plus the fact that the YAML keys become constructor arguments. That ratio is the point.

run() catching broadly is correct here precisely because turning the exception into data is its job — which is the distinction that makes it not a swallow.

Runtime

BEST TESTABILITY DESIGN HERE

step/runtime.py

Four things to know — globals, emit, should_stop, ask — all injected, and a bare Runtime() is the fake context. Nothing in step/ imports a queue or the Sequencer. The interface is the test surface, exactly.

Note what was removed to get there: the class-level stop Event (one abort flag for every run the process would ever do) and the Qt thread. Both were interface, not implementation — callers had to know about them.

HmiClient

DEEP · REAL SEAM

hmi/hmi_client.py

Override the show_* hooks you can draw; call the command methods. Behind it: the whole CoreToHmi routing table, the stop handshake, heartbeats. Two adapters (GUI, CLI), so again a real seam.

The defaults-that-log make adding a message unable to break a frontend that has not caught up — and ask_user's default declines rather than ignoring, because a blocked step must hear something. That is an error mode handled at the interface, which is where it belongs.

This module is why the CLI/GUI handshake drift is now structurally impossible rather than merely fixed.

Correctly shaped, at its size limit

Core

WATCH, DO NOT SPLIT

core/core.py — 751 lines, 23 methods

Its interface is core_main(...) plus the three link unions; the 23 methods are implementation. A mediator's complexity has to live somewhere, and concentrating it is locality, not a smell.

The thing to watch: load_recipe and start_sequence are policy, not routing, and they are what will grow as Phase 1 lands. When Core crosses roughly 900 lines, that policy pair is the natural thing to lift out — not the handlers.

Findings

1

error_handling's undeclared self.core invariant

FIX FIRST

utilities/error_handling.py

send_module_error reaches its outbox with getattr(instance, "core", None). So the interface of both decorators and of report_error / report_problem includes a fact no signature states: the instance must carry an attribute literally named core.

The tell that this is interface rather than implementation is that it has leaked into its callers' documentation. Three unrelated classes each carry a line explaining why their attribute is named core:

Sequencer:  "Named `core` because @catch_and_report_errors() reports failures through it."
HmiClient:  the same sentence, verbatim.
Report:     the same again.

When three modules have to document your invariant, it is in the wrong place.

The failure mode is silent in the direction that matters. Rename the attribute and the object keeps working, keeps passing tests, and quietly stops reporting to CORE — the fallback logs and returns. mypy's scope is messages/ and the handler modules, so nothing catches it.

Two candidate shapes, both cheap:

  • A Reporter Protocol (core: QueueWrapper[...]) the three modules declare they satisfy. Keeps the current call style; makes the invariant checkable the day mypy's scope widens.
  • Pass the outbox into the decorator factory. Explicit, but noisier at every use site and awkward for bound methods.

Recommendation: the Protocol. The getattr fallback stays — it is genuinely wanted for a driver or a half-built object with no CORE behind it — but it stops being the only thing holding the contract together.

2

Report.render_html() — the internal seam that is almost there

HIGHEST VALUE

report/report.py — 533 lines, 22 methods

Three distinct concerns share one class: run-directory lifecycle (make_run_dir / rename_run_dir / close_csv), CSV accumulation (record_step / rewrite_csv), and HTML rendering (render_html, about 100 lines inline). The external interface is small and fine.

The rendering is already nearly a pure function — rows_from_csv() exists at module level, and render_html reads from accumulated state. Roadmap Phase 4 wants configurable templates, report.type and report.theme. That is two adapters, so a real seam, and it is not there yet.

Recommendation: pull rendering out to a pure render(rows, run_metadata) -> str at module level, with Report calling it. Dependency category 1 (in-process, pure computation) — no port, no injection, just a function.

It becomes testable on a list of dicts with no Report instance, no config and no filesystem, and Phase 4's template adapter drops in behind an interface that already exists. Low risk, because it moves no behaviour.
3

recipe/step_source.py duplicates the parser's traversal

DRIFT RISK

recipe/step_source.py, recipe/recipe_parser.py

_one_sequence() calls normalize_sequence(), apply_defaults(), and then recipe_parser._expand_indexed_steps() — a private function — twice, reconstructing what _build_sequence() does. The module's own docstring names the problem:

The row list is built exactly as `recipe_parser._build_sequence()` builds it -
steps, then teardown_steps, each expanded - because that is the order
`Sequence.to_summary()` emits ... A test in tests/unit_tests/test_recipe.py
pins the two together.

A test pinning two implementations together is the signature of a seam in the wrong place. The ordering contract exists only because there are two traversals; it can drift the moment _build_sequence changes and someone does not read the docstring.

Verified: step_source.py:84-85 are the only external callers of _expand_indexed_steps.

Recommendation: record the effective mapping during the build — on the Step, or as a parallel tuple on Sequence — and make step_yaml_by_sequence a projection over what the parser already produced. One traversal, so the ordering contract disappears rather than being enforced. The never-raises convenience-view policy stays as it is.

This also removes the GUI's dependence on re-parsing the recipe file, which is the reason the module exists at all.

4

utilities/common.py fails the deletion test

REPEAT FINDING

utilities/common.py

convert_string_to_int has zero production callers. A grep across src/ and tests/ finds only its own definition and its own test. It exists to reword int()'s exception. Delete it and no complexity reappears anywhere; delete it and one test goes with it.

This was already flagged in architecture_deepening_review.html (21 August) as a fold-in, and it is still here on 2 September. Not urgent — but it is the only module in the tree that is pure overhead, and utilities/ is exactly where such things accumulate quietly.
5

The GUI set_dark(bool) chain

CLEANUP, LOW PRIORITY

hmi/gui/gui.py, and eight widget modules

Eight widgets implement set_dark; GUI._apply_theme fans out to five by hand, two of which fan out further.

The layer beneath is exemplary and I would hold it up as a model: palette.py is the single token source, no hex literal is allowed anywhere else, and python -m pypts.hmi.gui.palette renders every token on screen for review before a change is committed.

The weakness is only the manual wiring: one method, N implementers, a hand-maintained call list. Add a themed widget, forget the line in _apply_theme, and it silently keeps its old colours — no error, just wrong pixels in one theme.

A Qt signal widgets connect to, or a registry walked once, would make forgetting impossible. gui.md documents the current design and it works, so this is a cleanup, not a defect.

6

Runtime.emit / ask typed Any

RECORDED · NO ACTION

step/runtime.py

The largest seam in the step layer is untyped, and the docstring gives the reason: a Callable[[SequencerToCore], None] drags the link union into step/ and fails contravariance against the no-op default.

That is a real constraint, honestly stated, and the alternative costs more than it buys. Leaving it alone — noted here so it is not rediscovered as a surprise.

What I would do, in order

  1. Report.render_html → pure function. Best leverage per unit of effort; unblocks Phase 4's two adapters; moves no behaviour.
  2. step_source → projection over the build. Deletes a drift risk and a private-function reach in one change.
  3. Reporter Protocol for error_handling. Closes a silent-failure class. Do it before mypy's scope widens, not after.
  4. Delete utilities/common.py. One grep confirms it is dead; second time of asking.
  5. GUI theme fanout and Runtime.emit typing — leave. Both are documented trades.

On the HAL

hardware_layer/hal.py — empty, Phase 5

Nothing to assess, but the design already recorded in the docstring is the right one. A plain library with Device / family bases / concrete drivers, called with ordinary function calls, keeps the specification's "usable standalone" true by construction rather than by discipline.

The open question it names — how a bench is described in the configuration — is correctly identified as the thing that must be settled before any of it is written.

Removing the placeholder [hardware.example_device] section rather than leaving a shape to inherit was right. No adapter is better than one hypothetical adapter.
