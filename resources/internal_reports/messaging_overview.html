1. The model in one picture

Modules never touch a queue and never call each other. Everything goes through CORE — except log records, which go straight to the Logger so that logging survives a dead CORE.

┌──────────────┐ │ LAUNCHER │ builds HMI↔CORE queues + log queue └──┬────────┬──┘ parent of every process HmiStopped + │ │ ShutdownRequested│ │ spawns ▼ ▼ ┌─────────┐ ╔═══════════════════════════════════════╗ │ HMI │ ║ CORE process ║ │ GUI/CLI │ hmi->core ║ ┌────────┐ core->sequencer ┌───────┐ ║ │ │ ──────────► ║ │ │ ───────────────► │ SEQU- │ ║ │ process │ ◄────────── ║ │ CORE │ ◄─────────────── │ ENCER │ ║ │ (GUI) / │ core->hmi ║ │mediator│ sequencer->core └───────┘ ║ │ launcher│ ║ │ │ core->report ┌───────┐ ║ │ (CLI) │ ║ │ main │ ───────────────► │REPORT │ ║ └─────────┘ ║ │ thread │ ◄─────────────── │ │ ║ │ ║ └────┬───┘ report->core └───────┘ ║ │ ║ │ threads │ ║ │ ╚══════╪══════════════════════╪════════╝ └─────────────────────────┴──────────────────────┘ any->logger ▼ (LogRecords + control, NOT via CORE) ┌────────┐ │ LOGGER │ process; single writer of the run log └────────┘
One process boundary, and it is deliberate: HMI ↔ CORE, so the operator's window survives an engine crash. The Sequencer and the Report are threads of the Core process: their links are plain queue.Queue, nothing on them is pickled, and the engine will be able to hand the Sequencer a live object — a recipe, a device handle — when the execution engine lands.
What that costs. A fault in either thread can take CORE down with it, where a dead child process could previously be observed and reported. And the run log cannot tell them apart: the format names the process (%(processName)s), so Sequencer and Report records both read Core. The filename:funcName column and the link name in a trace line are what identify them now.

2. Links & queues

A link is a pair of modules. Each direction is its own queue wrapped in its own QueueWrapper, named by a constant in messages/links.py — that name is what a trace line is identified by. A link module is named after the two ends it joins and holds both directions; the Logger is the exception, named for its single direction because nothing is ever sent back.

Seven queues in total (6 link directions + 1 log queue). Three of them cross a process boundary and are therefore multiprocessing.Queue; the four engine links are plain queue.Queue. Two rules keep the topology honest:

  • The owner builds the handle. Whoever owns a link constructs both wrappers and hands them to the module that needs them. A module cannot invent a link to somebody it has no business talking to — the topology is enforced by construction, not by convention.
  • One swappable transport. QueueWrapper wraps anything with put() and get_nowait(), which is why the same class serves a process boundary and a thread boundary. The launcher builds the HMI↔Core pair out of multiprocessing.Queue because that link crosses a process boundary; CORE builds its four submodule links out of queue.Queue because the Sequencer and the Report are threads of its own process. Neither end knows which of the two it is holding.
The log queue is the odd one out: it carries two kinds of item — plain logging.LogRecord objects put there by logging's own QueueHandler, and the LoggerControl dataclasses. The Logger tells them apart with isinstance, which is why control messages must not be LogRecord-shaped.

3. The transport: QueueWrapper

One generic class, messages/queue_wrapper.py. A typed, one-way pipe with two operations.

self.core.send(StartSequence("power_on"))      # never blocks, never inspects

for message in self.inbox.receive():           # never blocks; yields what is waiting now
    self.handle_core_message(message)
MemberWhat it does
send(message)DEBUG-traces, then put(), then increments sent. The trace comes before the put so a message that fails to pickle is still recorded.
receive(limit=64)Generator. Yields waiting messages up to limit and stops on empty. Bounded so one busy link cannot starve the other inboxes; a caller that breaks early leaves the rest queued.
linkThe direction's name, from links.py. An unnamed wrapper traces as ?.
sent / receivedCounters belonging to the holder. A wrapper pickled to a child process increments the child's own copy; the Sequencer and the Report share CORE's object, so both numbers live in one place.

Nothing ever blocks on a queue. Every module runs a poll loop (while running: poll → periodic tasks → sleep(0.01)), so a message sent between two ticks simply arrives on the next one. The only exception is the Logger, which blocks on get() because it has no second source to service.

The trace — the only debug switch there is

Both send() and receive() log one DEBUG line to the pypts.trace logger, so --log-level DEBUG puts every message in the system into the run log twice: once from the sender, once from the receiver. A send with no matching receive is a lost message, and seeing that is the whole point.

...;DEBUG;Core;queue_wrapper.py:send;send core->sequencer RunSequence(sequence_name='power_on')
...;DEBUG;Core;queue_wrapper.py:receive;recv core->sequencer RunSequence(sequence_name='power_on')

grep 'sequencer->core' pypts_*.log     # the whole-system view of one link
There is no debug build and nothing else to turn on. Because the trace sits on the one object every message passes through, no module has to remember to log anything, and no new message can escape it. It is also the only way to see core↔sequencer and core↔report, which never leave the Core process — and, now that both are threads of it, the link name is the only thing in the line that says which module was involved.

4. The messages, per link → moved

The catalogue now lives in src/pypts/messages/messages.md — every message on every link, what it means, and which of them nothing sends yet. It moved out of this page on purpose: the structure above is settled, the message set is the next thing to review, and one file per concern beats one page that goes stale in halves.

What holds for all of them, and belongs here rather than there: every message is a frozen slotted dataclass of plain values, each direction has a union type that is the contract, and a type shared by two links lives in common_messages.py or run_events.py so both ends refer to the same class. Only the HMI link is pickled; the four engine links are in-process and no longer have to be.

5. Who handles what, and where

One handler per inbox. Every one is a match closed with unhandled(message) — never case _: pass.

CORE's three handlers are the whole routing table. Read them and you know the system:

def handle_sequencer_message(self, message: SequencerToCore) -> None:
    match message:
        case SequencerStopped():
            self.module_running[SEQUENCER] = False
        case RunStarted() | RunFinished() | SequenceStarted() | ... :
            self.to_hmi.send(message)          # relayed, not repacked
        case Heartbeat():
            self.note_heartbeat(message)
        case ModuleError():
            self.handle_module_error(message)
        case _:
            unhandled(message)
Two different survival policies. Every other module wraps its handlers in @catch_and_report_errors(), which reports the failure to CORE as a ModuleError and carries on. CORE cannot — it is what errors are reported to — so Core.poll() catches UnhandledMessage and everything else, logs it, and drops that message. The cost is that one bad message abandons the rest of that batch; those stay queued for the next tick.

One handler is shared: the GUI and the CLI both use HmiClient. The protocol lives once in hmi_client.py; subclasses override only the show_* hooks they can draw, and every hook has a logging default — so adding a message to CoreToHmi cannot break a frontend that has not caught up.

6. Adding a message

Two edits. That is the whole procedure.

# 1. Declare it in the link module, and add it to that link's union
@dataclass(frozen=True, slots=True)
class StartSequence:
    sequence_name: str

HmiToCore = LoadRecipe | StartSequence | ...

# 2. Handle it with a case in the recipient's handler
case StartSequence(sequence_name=name):
    self.start_sequence(name)
Everything else is found for you. A type checker flags every match that is now incomplete, because unhandled() takes a Never and only type-checks once every union member has been matched. test_messages.py fails until the message has an example in its table and a branch in its recipient — it enumerates the unions with typing.get_args(), so a new message is covered automatically. It also asserts the message is a frozen dataclass, survives a pickle round trip, and carries no live queue or handle.

A message shared by two links — anything CORE forwards rather than repacks — belongs in common_messages.py or run_events.py, so both ends refer to the same class.

8. Heartbeats, errors, questions, shutdown

Heartbeats

Every module ticks a HeartbeatManager from its periodic tasks — one Heartbeat(source, timestamp) per second on its outbox to CORE. CORE records it per module and warns after 5 s of silence, once per outage (its loop turns every 10 ms), and logs again when the module answers. What CORE should do about a timeout — restart, abort, tell the operator — is still an open roadmap decision; today it only warns.

Errors

Two ways in, one way through. A failure nobody expected is caught by the decorator around the method — @catch_and_report_errors() for an event loop, @report_and_reraise() for the execution layer. A failure the method recognised is handled where it happened, in an ordinary except, and reported with report_error() (a live exception) or report_problem() (a refusal, with nothing raised behind it) at whatever severity the method thinks it deserves. Neither function raises, so the raise site keeps control of what it does next.

Either way it becomes one ModuleError, carrying the module, the method (operation), the exception type and the traceback → CORE logs it at the level its severity asks for, and if the severity is above WARNING forwards it to the HMI as ModuleErrorReported. CORE deciding what reaches the frontend is what keeps the runtime log readable during a long run. What CORE should do beyond that — stop the sequence, abort the run — is deliberately still open (roadmap §1.11).

Questions to the operator (request/response)

The asking side generates a request_id with uuid4(); that id is what lets the pair cross the HMI process boundary at all. The old engine put a live queue.SimpleQueue inside the event and had the GUI answer straight into it, which only worked because both ends were threads of one process — which the Sequencer and CORE are again, but the operator answering the question is not.

# asking side (a step, on its own worker thread)
request_id = uuid4()
pending.start(request_id)                       # register BEFORE sending
core.send(UserPromptRequest(request_id, "Connect the DUT", ("OK", "Abort")))
answer = pending.wait(request_id)               # None if it timed out

# event loop, draining the inbox
case UserPromptResponse(request_id=rid, choice=choice):
    pending.return_caller(rid, choice)
The thread that calls wait() must not be the thread draining the inbox, or the answer can never arrive and the module deadlocks. The Sequencer runs its loop on one thread today, so porting user-interaction steps means running the sequence on a worker thread while the event loop keeps turning. Noted as a TODO in the roadmap.

Shutdown — one path, and it is idempotent

HMI request_shutdown() ──ShutdownRequested──► CORE CORE stop_all_modules() ──StopReport──► Report ──ReportStopped──► CORE ──StopSequencer──► Sequencer ──SequencerStopped──► CORE ──StopHmi──► HMI ──HmiStopped──► CORE CORE exits its loop once no module is still running, then join_submodules() waits for both threads to return (5 s each, then a warning). launcher (after joining the UI process): ──HmiStopped──► CORE (states as fact what CORE would otherwise wait for) ──ShutdownRequested──► CORE (second request; stop_all_modules() guards itself) join(5 s) else terminate() ─► then StopLogger, join(5 s) else terminate()

A frontend never stops itself: it asks, and CORE brings everything down in order. The launcher is the supervisor of last resort and uses the same link, because CORE having exactly one shutdown path is worth more than the launcher having a link of its own. The submodule threads are daemons: the clean path joins them, but one that wedges must not be able to keep the Core process alive.

9. What is real, what is a stub

Real todayDeclared but not carried out
  • QueueWrapper + trace, all 7 queues, all 6 handlers
  • The two-process topology: Sequencer and Report run as threads of CORE
  • Every union, every dataclass, the pickle guarantee on the HMI link
  • Heartbeats, error reporting, the full shutdown handshake
  • GUI and CLI sharing one protocol implementation
  • The Logger: single writer, control messages, drain on stop
  • Core.load_recipe() — recipe layer not ported; answers StatusChanged, never RecipeLoaded
  • Sequencer.run_sequence() — execution engine not ported, so no run-progress event is ever emitted yet
  • Report.generate_report() / export_report() — CSV/HTML logic not ported
  • SetConfigParameter — CORE logs and ignores it; propagating a change to running processes is unsolved
  • PendingRequests — lands with the execution engine
  • Heartbeat timeouts still only warn; CORE sends no heartbeat of its own

The messages exist ahead of their senders on purpose: the CLI, the GUI and the Report all have to agree on them, and agreeing before the call sites exist is much cheaper than agreeing after. The catalogue of them is now src/pypts/messages/messages.md, and reworking it is its own task.
