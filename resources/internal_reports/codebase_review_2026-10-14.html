New findings from the re-review

N1Abandoning an idle device can take about 20 s against an 11 s budgetmediumnewhal · bug
hal/connection_driver.py:216-225 (abandon, idle path) · :56 RESCUE_TIMEOUT_S · local_setup.py ABANDONED_DEVICES_TIMEOUT_S
Problem
When a device is idle, abandon() runs teardown with a 10 s timeout. If that times out, it then calls _rescue(), which has 10 s more. The budget assumes "rescue 10 s inside abandon 11 s", but that only holds for a busy device.
Impact
The join gives up at 11 s and reports "may still be energised" while the rescue is still running. CORE then exits and kills the rescue part way through the teardown.
Solution
Give both steps one shared deadline, for example teardown gets half and the rescue gets what is left. Add a test with a teardown that hangs.
N3A failure after the steps empties RunFinished.outcomeslownewsequencer
sequencer/sequencer.py:381-384
Problem
real_results is set only when run_body() returns. If closing the devices raises inside run_body, the run is ERROR and its outcome list is empty, even though steps ran.
Impact
The GUI and API lose the per-step results of that run. The CSV still has them.
Solution
Collect the outcomes in a holder that run_body fills as it goes. Assert on outcomes in the existing close-failure test.
N4Narrow races in the abandon pathlownewhal
hal/connection_driver.py:195-230 · hal/local_setup.py:126-198
Problem
A call's own timeout rescue can start just before abandon() sets _abandoned, and then two teardowns run at once. A get_device() that passes its check just before abandon can add a device after the device list was copied.
Impact
Rare: either a teardown is sent twice, or one device is missed during shutdown.
Solution
Set _abandoned and take the copy of _devices under the setup lock. Let only one rescue run per device (a flag checked under a small lock).
N5Creator and Editor v2 still offer passfail where it is refusedlownewcreator/editor · ergonomics
recipe_creator/rc_widgets.py:771 · recipe_editor/schema_form.py:788
Problem
The output-type list is the same for every step type, so passfail appears on UserInteraction and UserWrite. The verificator then refuses it, with a clear message.
Impact
Nothing breaks, but the UI offers a choice and then rejects it.
Solution
Build the list from the step type's schema, leaving out what is refused.

High (first pass)

#1RunFinished is not guaranteed after RunStartedhighfixedsequencer · bug
sequencer/sequencer.py:380-407 · step/step.py:605 · status 1.72
Problem
Only run_sequence_body() was guarded. An exception from LocalSetup, the metadata or the summary, or a sys.exit() in test code, skipped RunFinished.
Impact
The GUI and CLI stayed on "Running" forever, headless/CI hung, and the CSV was never finished.
Now
The run is ERROR until run_body and the summary have both returned, and RunFinished is sent from a finally. A SystemExit in a step is a step ERROR. Covered by three new sequencer tests. Pts.run() has no timeout, by decision.
#2passfail passed any truthy value, including "FAIL" and "False"highfixedstep · false PASS
step/step.py:525-536 · recipe/recipe_schema.py (_refuse_passfail) · status 1.70
Problem
passed = bool(value): any non-empty string passed.
Impact
A failed unit was reported as PASS.
Now
Only bool / numpy.bool_ is a verdict; anything else is an ERROR naming the value and its type. UserInteraction and UserWrite refuse passfail at load and suggest equals. Every demo that uses passfail returns a real bool.
#3A report_metadata name could overwrite step verdicts in the CSVhighfixedreport/recipe · false PASS
report/report.py:85-98, :336, :470 · recipe_schema.py:242-257 · status 1.74
Problem
A global named result shared the built-in column, and the final rewrite overwrote every row with it.
Impact
The CSV and the HTML showed a wrong verdict.
Now
Every metadata column is meta_<name>, so it cannot collide with a built-in column. Duplicate names are refused at load. One leftover: the HTML report cannot rebuild its metadata lines from the CSV alone, which a docstring still claims it can.
#4Misspelled or removed header/sequence keys were silently droppedhighfixedrecipe · silent failure
recipe/recipe_schema.py:214 · recipe_parser.py:277-285, :333 · status 1.71
Problem
The header and sequence used extra="ignore", so teardown_step: loaded and was quietly dropped.
Impact
Setup or teardown was skipped without a word.
Now
extra="forbid" on every recipe model. Removed sequence keys are refused with their sentence. The verificator lists the valid keys. No shipped recipe was affected.
#5HAL never puts devices in a safe state on abort, timeout or exithighpartly fixedhal · gap
hal/connection_driver.py:195-230, :270-300 · hal/local_setup.py:158-198 · sequencer.py tear_down_abandoned_devices · status 1.75
Problem
teardown() ran only on a clean close; timeouts and abandoned runs killed drivers without it.
Impact
A PSU stayed energised after Stop, a hang or a timeout.
Now
A timed-out call is torn down on a fresh driver process. An abandoned run's devices are torn down side by side, without taking locks, within 11 s. A device that is not torn down is a CRITICAL. The abandoned run's events are dropped.
Left
N1 (budget overrun on the idle path) and N4 (races). By design, Stop still does not interrupt a call blocked in a driver, and a hard kill of PyPTS runs none of this.
#6A missing report did not change the result or exit codehighfixedapi/headless · silent failure
api/embedding.py:319-343 · api/headless.py:49-62, :117 · status 1.73
Problem
A missing ReportReady was one DEBUG line, and Report errors never reached the exit code.
Impact
CI could exit 0 with no report.
Now
A missing report or a Report error is a WARNING, goes into RunResult.report_errors and gives exit 2, FAIL included. The console says "No report was produced." The reviewer found no path to exit 0 without a report.

#16Dead and broken code ships in helper_applicationsmediumopencreator · simplicity

#17Creator and editor duplicate the file layer, and both save unsafelymediumopencreator/editor · simplicity + bug
recipe_editor/editor_window.py:1096-1141 (path set at 1128, write at 1133) · recipe_creator_new.py:476-519 (506, 511)
Problem
The file actions are written twice. Save As sets the path before the write. write_text is not atomic, and the editor's open does not catch UnicodeDecodeError.
Impact
After a failed Save As, the next Save writes to the wrong file, and a failed write can destroy an existing recipe.
Solution
Write one shared helper: set the path only after the write succeeds, and use a temp file plus replace().
#18gui.py is a 1900-line class with hand-synced state flagsmediumopengui · simplicity

Problem
The log-follow flags and the three run-state variables are still updated by hand in many places.
Impact
This is the hardest part of the GUI to change safely.
Solution
Add a LogFollower class, and replace the three variables with one RunState enum and _set_run_state().
