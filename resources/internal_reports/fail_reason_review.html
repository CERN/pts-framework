1. Output judging runs outside run()'s try, so a bad output entry kills the whole sequence

Medium

C:\Git\pts-framework\src\pypts\step\step.py:437

The code. process_outputs() and the new reason-building sit in run()'s else: clause — which is outside the try/except Exception, not inside it:

try:
    step_input = self.process_inputs(runtime)
    raw_output = self._step(runtime, step_input)
except Exception:                      # <- only covers the two lines above
    step_result.set_error(traceback.format_exc(), step_input)
else:                                  # <- unprotected
    ...
    verdict = self.process_outputs(runtime, step_output, failures)
    ...
    step_result.set_result(verdict, step_input, step_output, reason)

Why it is a defect. The module docstring states the opposite contract: "a step failure must become data (StepResult with ResultType.ERROR and the traceback), never a silent continue. run() is the one place that catches broadly, because turning the exception into a result is its job." It does not, for anything raised after _step() returns.

Concrete scenario. A recipe declares outputs: {voltage: {type: range, min: 4.9, max: 5.1}} and

  • the step returns {"volts": 4.2} (a typo in the recipe) → KeyError('voltage'), or
  • the step returns {"voltage": "n/a"} → float("n/a") raises ValueError, or
  • the entry names an unknown type → the deliberate ValueError at step.py:385.

What actually happens. The exception unwinds run() → run_steps() → run_sequence() (whose try/finally runs teardown and re-raises) and is caught only in Sequencer.execute_sequence. Four consequences:

  • SequenceFinished is never emitted — the frontend never learns the sequence ended.
  • result, step_results = run_sequence_body(...) never completes, so step_results is still []: RunFinished carries an empty outcomes tuple and log_run_summary reports "no steps" for a run that ran eleven of them.
  • Every step after the bad one is abandoned with no skip_reason pass, so the GUI step table leaves those rows Pending forever — precisely the outcome run_steps()'s skip-reason design exists to prevent (step.py:485-491).
  • Teardown does still run (the finally), so the bench is left safe.
Pre-existing, but in the hunk. The else: placement predates this commit; the diff rewrites these exact lines and adds more raise surface to them (describe_failed_check(), build_fail_reason(), render_value() all call into user data). Worth deciding now: move the else: body inside the try, or record the "unknown output type is fatal to the run" policy as deliberate in the roadmap. Note that test_an_unknown_output_type_is_refused currently pins the raising behaviour at the process_outputs() level only, not at the run() level.

2. last_line() drops the exception type on a multi-line message

Low–Medium

C:\Git\pts-framework\src\pypts\step\step.py:118

The code. text.splitlines()[-1].strip() returns the last physical line of the stored traceback, not the exception line. The docstring assumes the two are the same ("A traceback's last line is ValueError: the instrument did not answer") — which is only true for single-line messages.

Concrete scenario — reproduced. A step raises ValueError("the instrument did not answer\nGPIB timeout after 5 s"). The new operator-facing ERROR line reads:

ERROR  Step 4/12 'read_voltage' could not run (1.1 s): GPIB timeout after 5 s

No ValueError, and the half of the message that said what went wrong is gone. Multi-line str(exc) is routine for subprocess.CalledProcessError, YAML/schema errors and wrapped instrument-driver errors — exactly the failures a bench hits.

Fix. "".join(traceback.format_exception_only(...)).strip() gives the intended Type: message; if only the stored text is available, take everything from the last line that matches ^\S onward instead of the last line.

3. Truncating a quoted string drops its closing quote

Low

C:\Git\pts-framework\src\pypts\step\step.py:74

The code. render_value() adds the quotes first and truncates after, so a long string loses its closing quote. Reproduced:

>>> render_value("ABC-" + "x"*100)
"'ABC-xxxxxxxx…xxxx..."          # opening quote, no closing quote

Why it matters. It defeats the function's own stated contract and logging_rules.md §6.1's first rule — "strings are quoted, so trailing whitespace and an empty answer are visible rather than being mistaken for a missing value". Once truncated, the reader can no longer tell the value was a string, and any trailing whitespace at the cut is invisible again.

Fix. Truncate the inner text to MAX_VALUE_CHARS - 5, then wrap: 'ABC-xxx…'. Note test_a_huge_value_is_truncated asserts len(rendered) == MAX_VALUE_CHARS, so it needs adjusting with the fix.

4. The per-value cap is bounded; the reason as a whole is not

Low

C:\Git\pts-framework\src\pypts\step\step.py:146

The code. MAX_VALUE_CHARS bounds one value, but build_fail_reason() appends every failing check plus every input and every output with no cap on their number.

Concrete scenario — measured. A step with 200 outputs of 40 characters each produces a 10,503-character reason. That single string becomes:

  • one 10 kB INFO log line — and INFO is what the GUI's LOG OUTPUT panel shows the technician,
  • one 10 kB QToolTip on the step table cell (step_table.py:270),
  • one 10 kB "Info" cell in the results panel (results_panel.py:113),
  • one 10 kB error_info cell in the CSV and the HTML report (report.py:271).

Which is the exact failure mode MAX_VALUE_CHARS was introduced to prevent — its own comment says "none of which is improved by it". A cap on the number of pairs (or a total-length cap with an … and 180 more tail) closes it.

Checked and clear

  • The doc rename is complete. A tree-wide grep for logger.md outside .git/ returns nothing.
  • No caller was broken by the signature changes. process_outputs() has exactly one production caller (run()) and set_result() one; both were updated. The new third/fourth parameters default to None/"", so the test helper judge() and any future subclass keep working.
  • The four error_info consumers all treat it as opaque text (cli.py:170, step_table.py:269, results_panel.py:113, report.py:271). Nothing branches on "error_info is non-empty" in a way the new FAIL reason breaks, and the results panel's column is neutrally titled Info, not Error.
  • The CSV survives the new punctuation. The reason contains ; and ,; report.py writes through csv.DictWriter, which quotes them, and the HTML report escapes through html.escape().
  • Pickle-safety holds. The reason reaches the HMI process only as StepOutcome.error_info, a plain str.
  • The FAIL branch cannot fall through with an empty reason. A FAIL verdict implies passed is False on some check, which implies a non-empty entry in failures, which implies a non-empty build_fail_reason() — so set_result()'s if reason: guard is never the difference between a reason and none.
  • describe_failed_check() cannot KeyError. It reads value / min / max, each of which process_outputs() has already read successfully on the same output_config before the check could be marked failed.

Two notes, not findings

The F6 docstring is looser than it reads. process_outputs() claims the list "never" yields a contradictory sentence beside a PASS. That is true for PASS. What it does allow is a FAIL reason naming a check that last-wins had already overridden — e.g. {a: passfail(False), b: passfail(True), c: passfail(False)} reports FAIL and names both a and c. Every check named did genuinely fail, so the operator is not misled; only the docstring is stricter than the behaviour.

Resolved inputs are now technician-visible. Before this change, input and output values reached the log only through the DEBUG line in log_step_outcome(). On a FAIL they are now on an INFO line, which is what the GUI panel shows and what gets pasted into support tickets. That is the documented intent of logging_rules.md §6.1, so it is called out rather than filed — but a global input holding a serial number or a credential now has one more place to appear.

Overall. The feature is well shaped: one sentence, one field, four consumers, and test_step.py pins both halves of the F6 contract. Finding 1 is the only one worth blocking on, and it is a pre-existing structural issue the commit inherits rather than creates.
