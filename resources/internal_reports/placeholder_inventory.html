The short version. The plumbing is real and the engine is not. Everything boots, talks, heartbeats, logs and configures itself; pressing run reaches a log.warning(...) and stops. Four kinds of emptiness are worth telling apart, and the sections below are ordered by them: a module that does not exist, a function that exists and does nothing, a contract that is declared but never exercised, and a thing that is actually broken rather than merely unfinished.

1. Modules that do not exist yet

Four packages in the shipping layout contain no executable code at all. They are directories that hold the shape of the architecture and nothing else.

PathWhat is actually thereWhere the real thing lives
recipe/recipe.py Two comment lines. EMPTY old_code/recipe.py — parsing, validation, the sequence tree
step/ An empty __init__.py. No step.py, no step types. EMPTY old_code/steps.py — the five step types
hardware_layer/hal.py One comment: # hardware layer. EMPTY Nowhere new — the drivers are hard dependencies of the old engine
stream_handler/ An empty __init__.py. EMPTY spikes/stream_handler/StreamContainer.py and spikes/GUI/XYGraph/, deliberately moved out of the package. Phase 3 promotes them.
Two details in there that are not just "unfinished". src/pypts/recipe/ has no __init__.py at all, so it is not an importable package the way every sibling is — worth fixing whenever the port touches it. And the spikes/ copies are not dormant code: StreamContainer executes and prints at import time, and XY_graph.py has undefined names that raise if reached. Neither is imported by anything today, which is exactly why they were moved out.

2. Functions that do nothing

These exist, are wired, are reachable from the GUI and the CLI, and are decorated and logged like real methods. Each one logs that it cannot do its job and returns.

FunctionSiteBehaviour today
Sequencer.execute_sequence() sequencer/sequencer.py:184 Runs on its own worker thread, logs "the execution engine is not ported yet", exits. The threading shape around it is real and tested; the body is the hole. STUB
Report.generate_report() report/report.py:118 Logs "the report layer is not ported yet". Never answers ReportGenerated. STUB
Report.export_report() report/report.py:128 Same, for ReportExported. STUB
Core.load_recipe() core/core.py:375 Logs, then sends the operator a StatusChanged literally reading "Recipe loading is not implemented yet". Never sends RecipeLoaded. STUB
Core → SetConfigParameter branch core/core.py:314 Accepts the message and logs that it is ignoring it. Deliberate: a live config change would have to reach processes that each read their values at startup, and that is unsolved. STUB
Core.do_periodic_tasks() — heartbeat timeout core/core.py:449–471 Detection is real; the policy is one log.warning. Nothing restarts, aborts the run or tells the operator. POLICY MISSING

Half-stubs — real code with a missing counterpart

  • CORE never asks the Report for anything. The only message it ever sends on that link is StopReport() (core.py:493). GenerateReport and ExportReport have handlers and no caller, so the Report thread runs an event loop, heartbeats, resolves its output directory, logs where reports will go — and is never spoken to.
  • CORE sends no heartbeat of its own. The watch is one-directional: an HMI cannot detect a dead CORE.
  • The GUI cannot ask the operator anything. HmiClient.ask_user() and ask_serial_number() default to declining — deliberately, since a blocked step must hear something. The CLI overrides neither, and the GUI overrides neither, so today every operator question would be auto-answered None. Nothing asks yet, so it does not bite.
  • The GUI is a status label and a stop button. It overrides five presentation hooks of the eleven HmiClient offers; the rest fall through to log.info. No widget system, no recipe preview, no session persistence.
  • --mode connect is accepted by argparse (startup.py:80) and has no branch — it silently falls through and starts the CLI. SILENT

This is the healthiest kind of placeholder in the repo. mypy flags any match that stops covering its union, and test_messages.py fails until every member has an example and a branch — so these fourteen cannot rot quietly, and the day something starts sending them, both ends already work.

Four public methods of ConfigHandler are exercised only by tests: open_for_writing(), set_parameter(), restore_default(), dump() and get_whole_config(). The write path is built and the policy — CORE is the single writer — is decided; no caller in the framework has taken it up yet. Hardware configuration does not exist at all: the placeholder [hardware.*] section was removed rather than left to be designed around, so a hand-written device section is preserved and returned as untyped text and nothing reads it.

8. What blocks what

Almost everything in this report has one of three roots.

recipe/ + step/ are empty
        │
        ├─→ Core.load_recipe()      stub  ─→ RecipeLoaded          never sent
        └─→ Sequencer.execute_sequence()  stub
                    │
                    ├─→ 7 run events       never sent ─→ GUI/CLI hooks never fire
                    ├─→ prompt requests    never sent ─→ ask_user() never called
                    └─→ RunFinished        never sent ─→ CORE never triggers the Report
                                                              │
report/ logic is a stub  ←──────────────────────────────────-─┘
        └─→ ReportGenerated / ReportExported  never sent
        └─→ report.type / report.theme        never read

hardware_layer/ + stream_handler/ are empty
        └─→ nothing above them can touch an instrument at all

So: port the recipe and step layers and the largest block of this report resolves itself — 14 dead messages become live, four presentation paths start firing, 30-odd placeholder tests become writable. The report layer is a second, independent block; the HAL and the stream handler are a third and only matter once a step can run.

What is not unblocked by the port, and needs a decision rather than a port:

  • The heartbeat-timeout policy — detection works, nobody decided what to do about it.
  • SetConfigParameter — needs an answer to "how does a running process learn a value changed?"
  • --mode connect — needs the event fan-out design before it can have a branch.
  • The verificator's broken import — a five-minute fix waiting on where the schema constants should live.
