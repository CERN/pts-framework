1 · The model

A recipe is a multi-document YAML file: document 1 is the header, every following document is a sequence. A sequence is an ordered list of steps. A step names a steptype (which Python class runs it), an input_mapping (where its arguments come from) and an output_mapping (what to do with what came back).

Recipe (header: name, version, main_sequence, globals) └── Sequence "Main" locals pushed on a stack ├── setup_steps ─┐ ├── steps ├─ concatenated into ONE flat list └── teardown_steps ─┘ run in a finally block — always execute

Two scopes only: globals (whole recipe, one flat dict) and locals (one dict per sequence). Steps never call each other — they communicate exclusively by writing and reading these variables. Every step yields one ResultType; results form a tree and a parent takes the max severity of its children.

3 · Documents 2..N — a sequence

sequence_name: Main        # must be the FIRST key
description: The main flow
parameters: {}             # parsed — NEVER USED
locals:                    # sequence-scoped variables
  target_value: '45'
outputs: {}                # parsed — NEVER USED
setup_steps: []
steps: []
teardown_steps: []

All seven keys are read with plain indexing → every one is mandatory, and a blank value (locals: with nothing after it) is null, which crashes on first use. Write locals: {} explicitly.

Locals are pushed by reference, so running the same sequence twice does not start clean. A subsequence cannot see its caller's locals (correct isolation — and the only isolation there is).

4 · A step — common fields

- steptype: PythonModuleStep     # required; selects the class
  step_name: Measure 3V3 rail    # required
  description: ...               # required by the validator
  id: stable-id                  # optional, defaults to a uuid4
  skip: false                    # optional — skipped steps never resolve inputs
  critical: false                # optional
  continue_on_error: false       # optional — NOT accepted by every steptype
  input_mapping: {}
  output_mapping: {}
  • The leading - is structural — steps is a YAML list. Losing it is the most common authoring error.
  • steptype is case-insensitive for 8 of 10 types, case-sensitive for the two SSH ones. Always use exact CamelCase.
  • Construction is eval(step_type + "(**step_data)") → any unknown key in the step is a TypeError at load; an unknown steptype is a raw NameError; a recipe file can execute arbitrary Python.

Two traps. (1) A non-empty global_name key wins over whatever type says — it is checked first. (2) Nothing coerces types: value: 45 ≠ value: '45', and that silently decides equals outcomes.

6 · output_mapping — judging and storing

Each key must exactly match a key in the dict the step returned. A non-dict return is wrapped as {"output": value}; None becomes {}. A mapping key with no matching output is a KeyError → ERROR.

typeextra keyseffect on the step's result
passfail—PASS if truthy, else FAIL
equalsvaluePASS if == (no coercion)
rangemin, maxPASS if min <= float(out) <= max (strings OK)
passthrough—the value already is a ResultType (__result)
locallocal_namestores it — does not change the result
globalglobal_namestores it — does not change the result
The real verdict rule. The result starts at DONE and each judging mapping assigns it, so the last one wins — a failing check followed by a passing one reports PASS. The docs claim "all must pass"; that is false. No judging mapping at all → DONE, which is not a failure.

7 · The result model

SKIP(0) < DONE(1) < PASS(2) < FAIL(3) < ERROR(4) < STOP(5) a parent's result = max(children)

So: one FAIL anywhere makes the whole sequence FAIL; ERROR (an unhandled exception) outranks FAIL; STOP (operator abort) outranks everything; all-skipped → SKIP.

The report's CSV columns are exactly the StepResult fields: recipe_name, recipe_file_name, sequence_name, serial_number, pypts_version, step_name, step_id, step_type, result, inputs, outputs, error_info — anything you want in the report must be a step input or output. There is no free-form annotation channel.

8 · Error & abort flow

try: runtime.continue_on_error = runtime.get_global('continue_on_error')
except: pass
if result is ERROR and (not continue_on_error or step.is_critical()):
    break
  1. Only ERROR stops a sequence. A FAIL — a failed measurement — never halts anything. Intended (characterise the DUT fully), but documented nowhere.
  2. globals.continue_on_error, if present, overrides every step-level setting and is re-read at each step boundary.
  3. If that global is absent, the runtime keeps whatever value the last executed step assigned — and WaitStep / SequenceStep / IndexedStep don't assign one, so step-level settings leak forward.
  4. critical: true re-arms the stop even when continuing is enabled.

Abort: the stop event is checked before each step and again right after it returns → result STOP, then unwind into teardown. Interactive steps poll the same event while waiting, so an abort during a prompt is honoured within ~1 s.

How options really works

options:
  type: direct
  value:
    - 'next': 'Next'      # KEY = the value the step receives back
    - 'cancel': 'Cancel'  # VALUE = the button caption
    - 'yes': ''           # empty caption → falls back to Key.capitalize()

A list of single-entry dicts. No options at all → one unlabelled button. Three response values are magic in the GUI and open a second dialog whose answer is pushed onto the same queue: file (file chooser), wrt (text input), ID (serial-port chooser returning port, baudrate, IDN).

Looping — indexed: true

The only control flow the format has. Give an input a list and mark it indexed; the step runs once per element. Iteration count = the shortest indexed list; empty → SKIP. Non-indexed inputs repeat verbatim. Each iteration is a deepcopy, results become subresults, and per-iteration local/global writes are stripped so iterations don't overwrite each other. There is no while, no repeat, no conditional.

Subsequences — unfinished

parameters and outputs are parsed and then never referenced. SequenceStep returns only __result. To get data out of a subsequence today, the subsequence must write to a global. The draft recipe is entirely commented out with the note "never actually tested yet".

These magic-string globals are the format's worst wart: hidden coupling, order-dependent, undiscoverable. And ssh_client publishes a live paramiko object through a global — unpicklable, so it breaks the moment anything crosses a process boundary.

11 · YAML pitfalls

  1. yes/no/on/off are booleans in YAML 1.1. - yes: '' gives the key True, and comparing against 'yes' then fails. Always quote them.
  2. None is the string "None", not null. YAML null is null, ~, or empty. Only SSHConnectStep defends against both.
  3. Quoting decides the type and nothing coerces — matters for equals. (range is safe; it calls float().)
  4. The leading - is what makes a step a list element.
  5. Key order matters to the validator: header must start with name:, a sequence with sequence_name:.
  6. A blank locals: is null, not {}.
  7. Tabs are illegal. Duplicate keys silently win-last — including duplicate sequence_name across documents.

12 · What the validator actually checks

Checks: each document is a dict; document kind from its first key; header fields present/typed/non-empty; sequence's seven keys present and typed; and for entries in steps only — the per-steptype required-field list, that the two mappings are dicts, and that skip is a bool. Faults carry line numbers.

Does not check:

  • setup_steps and teardown_steps contents — never validated at all
  • that main_sequence names an existing sequence
  • that steptype is known — and SequenceStep/IndexedStep aren't in the rules, so they're wrongly required to have action_type/module/method_name
  • anything inside the mappings: no check that type is valid, that direct has value, that equals has value, that range has min/max
  • that referenced locals/globals are declared, or that a steptype's required globals exist
  • that module/method_name resolve; no uniqueness of step names/ids
The rules live in three disagreeing places — recipe_rules.py, the Recipe Creator's own copy, and yaml_format.rst — and the verificator currently cannot even be imported (its constants come from pypts, which no longer exports them).
