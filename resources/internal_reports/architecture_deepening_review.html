Architecture Deepening Review

pts-framework @ architecture_refactor — 2026-08-21. Surveyed against resources/roadmap/pypts_roadmap.md and porting_changes.md; candidates that merely restate a recorded roadmap TODO were dropped. Vocabulary: a module is anything with an interface (everything a caller must know) and an implementation; it is deep when a small interface hides a lot of behaviour, shallow when the interface is nearly as complex as the implementation. Depth gives callers leverage and maintainers locality. A seam is where an interface lives; an adapter satisfies it there.

Where the depth already is — do not "fix" these

  • hmi/hmi_client.py — one implementation of the whole HMI↔CORE protocol; frontends override only show_*/ask_* hooks, and a test pins that neither overrides the protocol itself. The deepest module in the tree.
  • messages/queue_wrapper.py — 77 lines carrying all seven links across one process seam and several thread seams, tracing both directions. The highest leverage per line in the repo.
  • step/runtime.py's no-op defaults — a bare Runtime() is a complete fake context, which is why test_step.py needs zero monkeypatching. Candidate 2 below must preserve this property while extending it.
  • The test suite — 15 monkeypatches across 20 test modules, event loops driven by hand rather than mocked. Where tests do struggle, that is the friction signal (candidates 1 and 8).

Deepening candidates

1

A step type is declared in four places, and one of them is dead

Strong
recipe/rules.py:52–68 · step/registry.py:30–51 · step/steps.py (constructor signatures) · recipe/validator.py:63–84 · plus the two un-refactored copies in helper_applications/ (roadmap §1.17 TODO)
Problem
Adding a step type today means editing rules.STEP_TYPE_REQUIRED, rules.STEP_TYPE_DEFAULTS, registry.STEP_TYPES, and the class __init__ — which is the third statement of the same required/optional split, since build_step() splats the YAML mapping into it. The knowledge "what is a Wait step" has no locality. And STEP_TYPE_DEFAULTS has no reader at all: one definition, zero uses — a maintainer following rules.py's own "one importable source of truth" docstring will fill it in for a new type and it will do nothing. test_step.py:112–114 exists purely to pin that two of the four copies agree — a test whose only job is guarding duplication is the tell.
Solution
Make the step class the single declaration: each Step subclass states its required and optional recipe keys once (class attributes), and the registry derives what rules.py and validator.validate_step() currently hand-maintain. Delete STEP_TYPE_DEFAULTS. This is the in-tree half of what roadmap §3.2 already sketches as StepPlugin — doing it now, while only two types exist, means the nine remaining step-type ports each land as one file instead of four edits.
Benefits
Locality: a step type's whole contract lives beside its behaviour, so a port MR touches one module. Leverage: the validator, the registry, and (later, Phase 2/6) the verificator and Creator all read the same declaration instead of carrying copies. The duplication-pinning test becomes unnecessary and the real per-type tests get simpler setup.

└─ registry derives name→class  ·  validator derives required keys  ·  parser derives defaults
a new step type = one new module; rules.py shrinks to format-level rules only
Roadmap alignment: §3.2 plans this shape for Phase 2 ("schemas derived from step plugins"). The friction argument is only about timing — the declaration merge pays for itself during the Phase 1 ports, and the entry-point discovery half can still wait for Phase 2.
2

The Runtime seam has two hooks; the Phase 1 port needs four

Strong
step/runtime.py:42–87 · sequencer/sequencer.py:90, 188, 199–204, 235–248 · messages/blocking_messages.py:24–67 · reference: old_code/steps.py (User*, SequenceStep, IndexedStep)
Problem
Runtime is the seam between the step layer and the Sequencer, and it is a good one — emit, should_stop, the variable scopes, base_dir, with no-op defaults that make a bare Runtime() a complete fake. But the next ports need things it does not offer: the four User* types must ask a question and block for the answer (the waiting half, PendingRequests, exists but is private to the Sequencer with no path from a step to it); SequenceStep must resolve a sequence by name (the new Runtime never holds the Recipe — the Sequencer looks up the one sequence and hands it down); and nesting needs parent identity (StepResult.subresults exists and nothing writes it; no run event carries a parent id). When the first interactive step is ported, the cheapest move in that moment — reach for Sequencer.pending from inside execute_sequence, or hand the step a live Sequencer — destroys the exact property that keeps the whole step layer testable without queues.
Solution
Grow the existing seam, before the ports: Runtime.ask(request) → answer (blocking; the Sequencer wires it to PendingRequests.start()/wait() + its outbox; the bare instance answers "declined" immediately), a sequence-resolution hook for SequenceStep, and parentage carried through the emission model. The additions belong on the seam, not beside it — step/ keeps importing message dataclasses only, never QueueWrapper.
Benefits
Leverage: every interactive step type gets prompting for the price of one call, and its tests fake it by constructing a Runtime with a canned answer — no threads, no queues, no monkeypatching. Locality: the deadlock constraint blocking_messages.py warns about ("the thread that calls wait() must not be the thread that drains the inbox") is satisfied in exactly one place, the Sequencer's wiring, instead of in every step that asks. The roadmap's M-1 decision (prompt option shape) then has one obvious home.

SequenceStep ──?──▶ recipe.sequences  (Runtime never holds the Recipe)
first User* port hits this; the shortcut breaks test_step.py's no-queue property
After — same seam, four hooks
Runtime: emit · should_stop · ask() · resolve_sequence()
Sequencer wires ask → PendingRequests + outbox, once;
bare Runtime answers "declined" — still a complete fake
UserPromptStep ──▶ runtime.ask(UserPromptRequest…) — blocks, typed answer back
SequenceStep ──▶ runtime.resolve_sequence(name) — nesting resolves without a Sequencer reference
step tests: Runtime(answer=…) — still zero monkeypatches

The promised parity oracle cannot run: old_code/ is 100% commented out

Strong
all of src/pypts/old_code/ (4,271 lines, no executable line) · tests/functional_tests/test_recipe_execution.py:26–28 · roadmap Phase 0, last item
Problem
Roadmap Phase 0 promises characterization tests — "run an example recipe end-to-end and assert on the CSV rows — this is the safety net for the port in Phase 1" — and test_results_match_the_old_code_baseline sits skipped waiting for them. They are not merely unwritten; they are unwritable: every file in old_code/ is entirely commented out, so nothing there can be imported or executed, and the example recipes beyond the two ported ones do not parse under either engine (F24). Every parity judgement so far (F6 last-wins, M-5 per-step STOP, continue_on_error) has been made by reading, not running. The skipped test makes the port look mechanically safer than it is.
Solution
Stop promising an oracle that cannot fire. Two honest options: (a) check out the last commit where the old engine ran (it is in git history), restore example_tests.py, run the example recipes once, and record the CSVs as golden files the functional test compares against — the oracle runs once, offline, not in CI; or (b) amend Phase 0 to say the baseline is the read-and-record work that already exists (recipe_guide.md §16's 28 findings, porting_changes.md §3's parity matrix) and delete the skipped placeholder. Per the prime rule this is the user's decision; the report only surfaces that the current state is neither.
Benefits
Locality of truth: today the "safety net" exists in three inconsistent states (a plan, a skipped test, an inert reference). Either option collapses them to one. Option (a) additionally gives the nine remaining step-type ports a mechanical parity check where today there is only careful reading.

"Adding a message is two edits" is six to ten for anything CORE forwards

Worth exploring
core/core.py:353–412 · hmi/hmi_client.py:93–127 · report/report.py:123–140 · the three link unions · src/pypts/README.md (the two-step procedure)
Problem
The two-edit procedure holds for point-to-point messages (LoadRecipe). For a forwarded run event — most of the traffic — the real trace for StepExecuted was six files: declare, add to SequencerToCore, add to CoreToReport, a branch in Core.handle_sequencer_message, a branch in Report.handle_core_message, an example in test_messages.py. An event that also reaches a frontend costs nine or ten. Core.handle_sequencer_message is nine case arms of which six are the one-liner self.to_hmi.send(message): in its mediator role CORE is shallow — the interface (two unions matched exhaustively) is as large as the implementation. The cost recurs ~nine more times during the step port, since each User* type brings request/response pairs.
Solution
Narrow, not a bus: let a run event declare which links it rides (a small typed attribute on the event family, or one routing table in run_events.py beside the declarations), and CORE's forwarding arms collapse to one data-driven branch. Commands and everything with behaviour behind it (LoadRecipe, StartSequence, errors, heartbeats) keep their explicit case arms. mypy exhaustiveness and the unhandled() guarantee stay intact for those.
Benefits
Locality: a new run event is declared, routed, and exampled in two files again — the README's promise becomes true for the common case. The routing topology stays explicit, just declared beside the event instead of restated as three one-line case arms.
Contradicts a recorded decision — flag, don't just do. Roadmap §1.1 rejected a string-topic event bus because "it would erase the explicit topology." This proposal is deliberately weaker — typed events, a closed set of links, no subscription — but it moves fan-out from match arms into data, which is the same axis. Worth reopening only because the cost is now measured (6–10 edits per event) and about to be paid ~9 more times; if the answer is "keep the arms," record it and this stops being re-suggested.

Three shapes for one executed step, and the invariant separating them is a docstring

Worth exploring
step/step.py:49–108, 266–277 · messages/common_messages.py:82–94 · messages/run_events.py:129–159 · report/report.py:178–205
Problem
Step.run() builds a StepResult, projects it to StepOutcome twice on adjacent lines, wraps one in StepFinished (for frontends) and the other in StepExecuted (for the Report), and run_sequence() projects a third time into RunFinished(outcomes=…). The reason for the split is real — the pickled HMI seam — but the interface now has three shapes for one fact, and the rule keeping the rich StepExecuted off the HMI unions is enforced by a docstring only: nothing mechanical stops someone adding it to CoreToHmi, and the pickle test would pass. It is also the direct cause of parity loss M-3: per-step inputs/outputs reach no frontend, and cannot without widening StepOutcome or adding a fourth message.
Solution
One emission: StepExecuted becomes the single per-step event, and the HMI-safe subset becomes a projection applied at the seam (CORE projects when forwarding to the HMI link), not a second message emitted by the step. Add the missing negative test either way: assert StepExecuted ∉ CoreToHmi. Settling this also decides M-3's fix — the projection is the one place to choose what the operator sees of inputs/outputs.
Benefits
Locality: what crosses the pickled seam is decided at the seam, in one function, instead of by which of two near-identical messages a step emitted. The step layer emits once; the emission-order test simplifies; the docstring invariant becomes code.
Before — the step chooses per audience
Step.run(): StepResult → to_outcome() ×2 → StepFinished + StepExecuted
two messages, two lines apart, same fact
"engine-internal by contract" — a docstring, untested; RunFinished projects a third time
After — project at the seam
Step.run(): emit StepExecuted (rich)
one emission per step
CORE ──▶ Report: as-is   ·   CORE ──▶ HMI: project(StepExecuted) — pickle-safe subset chosen here
+ a test: StepExecuted is not a member of CoreToHmi

Step identity promises a static table; the engine about to land produces a tree

Strong
step/step.py:141 · recipe/recipe.py:58–68 · hmi/gui/step_table.py:58–71, 112–120 · report/report.py:192 · reference: old_code/steps.py (deepcopy per iteration)
Problem
The interface of StepSummary/StepStarted implies a pre-enumerable set of rows keyed by UUID; step_table._find_row warns and drops anything unknown. IndexedStep deep-copies its template per iteration — copying self.id — so N iterations emit N StepStarted with the same UUID; either one row flickers N times or the port re-mints ids and nothing matches the summary. SequenceStep re-enters run_sequence() with ids the displayed summary never contained — and cannot contain, because an IndexedStep's row count is only known at run time. The Report's step_id column shares the problem, and roadmap §1.13 already asks for a stable-id policy. This is an invariant mismatch, not a missing feature, and it is cheapest to settle before nesting lands (the User* ports don't stress it; SequenceStep/IndexedStep do).
Solution
Decide once what the summary promises. Either identity becomes (step_id, occurrence) with parentage on the events (which candidate 2's emission work would carry anyway), or the summary stops claiming completeness and the table creates rows on first StepStarted, with the summary as the initial fill. Taken once at the contract level, both frontends and the Report inherit the answer; taken later, each grows its own workaround.
Benefits
Locality: the "what is a row" decision lives in the message contract, not in three consumers. Leverage: nesting and iteration land on frontends that already know how to display them; the §1.15 TODO ("display policy for nested rows") gets its prerequisite.
Before — static promise, dynamic reality
RecipeLoaded.summary: rows keyed by uuid4-at-parse
table pre-fills; _find_row drops unknowns
IndexedStep: N events, one UUID  ·  SequenceStep: events with ids no summary held
After — identity decided at the contract
events carry (step_id, occurrence, parent)
summary = initial fill; rows may be born at StepStarted
one decision; GUI table, CSV column, and future Creator identity all inherit it

Stacked @catch_and_report_errors() makes error policy depend on nesting depth

Worth exploring
utilities/error_handling.py:63–98 · sequencer/sequencer.py (8 applications) · report/report.py (9, incl. start and main_loop) · hmi/hmi_client.py (4)
Problem
The decorator swallows, so only the innermost decorated frame on a call chain can ever fire; every outer application is unreachable for anything raised below it. Some nesting is earning its keep (a guard on handle_core_message saves the rest of a batch, as CORE's poll() documents), but four levels is more than that buys, and two spots are actively misleading: if Report.main_loop dies, its decorator swallows, start() logs "Module stopped." and returns — and ReportStopped is never sent, so the log says the module stopped cleanly while CORE waits out SHUTDOWN_TIMEOUT_S and names it abandoned. And Sequencer.execute_sequence is decorated and has the inner try that preserves "one RunStarted ⇒ one RunFinished" — the outer decorator silently voids that invariant for anything raised after the inner block. §1.10 chose two decorator names precisely so the behaviour is "readable at the call site"; stacking makes it depend on depth, which no call site shows. Nothing in test_utilities.py tests the decorators stacked, and nothing tests that a module dying in its loop still tells CORE.
Solution
Concentrate the lifecycle failure path: one guard at the message level (where the batch argument applies) and one at the module lifecycle — start → loop → report-stopped-even-on-failure — owned in one place per module (or in a small shared lifecycle helper, since Sequencer, Report and HmiClient repeat the same start/loop/stop shape). Strip the decorator from start, main_loop, do_periodic_tasks, stop where an inner application already covers them. Add the missing test: a loop that raises still produces *Stopped.
Benefits
Locality: the effective policy for "the module is dying" exists in one frame instead of being the emergent result of four stacked swallows. The "Module stopped."-but-abandoned contradiction becomes impossible by construction.
Before — four swallows deep
@catch… start / @catch… main_loop / @catch… poll / @catch… handler
innermost wins; outers unreachable
loop dies → swallowed → "Module stopped." logged → ReportStopped never sent → CORE: abandoned
After — two guards, each with a job
per-message guard + lifecycle guard
bad message: report, keep batch;
dying loop: report, send *Stopped, exit honestly
+ test: a raising loop still reports itself stopped

The launcher forges half the HMI handshake, and imports everything it spawns

Worth exploring
launcher/startup.py:44–45, 211, 323–341 · core/core.py:562–565 · messages/core_sequencer_communication.py:31 (the messages → recipe → step chain)
Problem
Three leaks across the launcher's stated interface ("spawn and watch"). First, stop_core() sends HmiStopped() on the frontend's behalf — forging a message whose docstring says it means "the frontend's loop has ended"; Core.stop_all_modules() is idempotent precisely because two senders exist, which is the same leak seen from CORE's side. Second, import pypts.launcher.startup loads PySide6 even for --mode cli (roadmap §1.2 TODO, "a one-line change nobody has made"). Third — not yet recorded anywhere — declaring UseRecipe(recipe: Recipe) makes the messages package import the engine's data layer (messages → recipe → step), so the message vocabulary is no longer importable without the engine; a deliberate §1.13 decision with an undocumented consequence. The tests already feel it: test_startup.py has the highest monkeypatch density in the suite.
Solution
Three small cuts, separable: defer the GUI import into the gui branch (the recorded one-liner); replace the forged HmiStopped with the honest fact — the launcher knows the frontend process ended, so either a distinct message saying that, or CORE treating frontend-process-exit as the launcher's to report and HmiStopped as only ever the frontend's; and record (or revisit) the UseRecipe import chain in messages.md — if the vocabulary should stay engine-free, UseRecipe can live beside the Sequencer instead of in the shared vocabulary.
Benefits
Locality: shutdown truth has one author per fact, and Core.stop_all_modules() no longer needs to be idempotent-by-accident. A headless bench stops importing Qt to run a CLI recipe. test_startup.py sheds monkeypatches as the launcher's interface stops including other modules' internals.

After

ResultType puts verdicts and execution facts on one ordered scale

Worth exploring
messages/common_messages.py:62–79 · step/step.py:101–108 · sequencer/sequencer.py:216–217
Problem
SKIP < DONE < PASS < FAIL < ERROR < STOP, and aggregation is max(). PASS/FAIL/ERROR/DONE are verdicts about the unit under test; SKIP and STOP are facts about execution — nothing was measured. On one comparable scale, a sequence where a step errored and the operator then aborted aggregates to STOP: the error disappears from the run verdict. The docstring's "keep the order if you add a member" is the sign the ordering is doing work nobody can check, and nothing pins the error-under-abort case.
Solution
A split, not a deletion: a verdict and a completion state, each aggregated by its own rule, projected to one string where the CSV and the table need a single cell. Interacts directly with M-5 (the old engine marked un-run steps STOP) — settle both in one change, ideally alongside the continue_on_error policy design the roadmap already schedules, since all three are "what does a run's outcome mean."
Benefits
An aborted-but-erroring run stops lying; the aggregation rule becomes checkable per axis; M-5's grayed-out rows get a principled representation instead of overloading the verdict column.
Before — one scale, max() wins
SKIP<DONE<PASS<FAIL<ERROR<STOP
max() of mixed facts
ERROR then abort → run says STOP; the error vanishes from the verdict
After — two axes, one projection
verdict × completion
worst verdict; separate "was interrupted / skipped";
projected to one cell for CSV and table
error-under-abort pinned by test; M-5's STOP rows come free

Top recommendation

Start with candidate 2 — grow the Runtime seam — with candidate 1 as its companion in the same porting wave.

The reasoning is timing, not severity. The next scheduled work is the Phase 1 port of the four User* step types (roadmap §2, Phase 1 step 2), and that port cannot be written against today's Runtime: the asking half of PendingRequests has no path from a step, so whoever ports the first interactive step will either wait on this decision or take the shortcut that couples step/ to the Sequencer and destroys the bare-Runtime() testability the whole step layer stands on. Deepening the seam first means every one of the nine remaining step-type ports lands on an interface that already supports it — that is leverage multiplied nine times, at the moment of maximum payoff.

Candidate 1 (single step-type declaration) belongs in the same wave because it changes the shape of each port MR from four-file edits to one new module — cheapest before the nine ports, pointless after. Candidate 6 (step identity) is the third Phase-1-gated decision, but it only bites when SequenceStep/IndexedStep land, so it can trail the User* ports. Candidate 3 is the one to decide soonest (one conversation, not a refactor); candidates 4, 5, 7, 8, 9 are real but not on the critical path.
