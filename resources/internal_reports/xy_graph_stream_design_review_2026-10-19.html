1. Verdict

The architecture's shape is right and is worth keeping: a zero-import stream container behind a three-name interface, samples crossing the process boundary as a file instead of messages (exactly the constraint stream_handler.md already records), the Sequencer as the only glue, and the HAL untouched. The fact-checks confirmed nearly every pypts identifier the design names.

But the design is not implementable as written. Four blockers (an undefined no-folder run, a right-column promise the existing GUI state machine actively contradicts, a recipe-load crash for graph: on a Sequence step, and the missing licence) and six high findings — most of them lifetime rules the container's interface never states — need decisions first. There is also one genuine simplification on the table: the StreamOpened message may be deletable outright (§5).

2. What was verified and holds

  • Confirmed: stream_handler/ is an empty stub; its md already demands "bulk data never travels through a message queue" and file/shared-memory handoff — the design satisfies it.
  • Confirmed: the active-LocalSetup pattern (hal/local_setup.py:236-247, module global + lock, clear error from get_device() with no setup) is real and is the right template — including the comment explaining why it is deliberately not thread-local (test code starts threads).
  • Confirmed: start_run_folder() (sequencer.py:437), RunStarted.run_dir (run_events.py:143), StepSummary.image_path and the RecipeLoaded route, _StepFields/STEP_COMMON_DEFAULTS, and the Indexed propagation rule (indexed_step.py:121-122) all exist exactly as the design uses them.
  • Confirmed: adding a CoreToHmi message costs exactly the four edits the message layer is built for; CLI and headless inherit a logging default hook for free (hmi_client.py:154-208, test_messages.py:598-615).
  • Confirmed: test functions run on the CORE process's "Sequence" thread, so a process-global active session is visible to them and to threads they start; runs cannot overlap (sequencer.py:249-256).
  • Confirmed: ScopePlotWidget and DataStore exist at the claimed paths; the plot path needs only pyqtgraph + numpy + PySide6 (already a PyPTS dependency); importing the two modules does not pull in h5py/nptdms/pandas.
  • Refuted candidates (checked and dropped): the Indexed image_path rule is quoted correctly; message ordering RunStarted-before-StreamOpened is safe; the hook plan covers all three frontends.

3. Findings

BLOCKERB1 — Runs without a run folder are undefined, including the GUI case

The design hands StreamSession "the run folder (RunStarted.run_dir)" unconditionally. But run_dir is "" for every engineering-mode retest (write_report=False) and when folder creation fails (sequencer.py:363-366, run_events.py:127-136). A retest is a GUI run — exactly where graphs are shown — yet StreamSession("") would write streams/ CWD-relative or fail, and csv_path could not be the absolute path §4 itself requires.

Design §3 · evidence: sequencer.py:363-366, run_events.py:127-144

Fix: decide the no-folder behaviour explicitly (see open decision Q2) and write it into §3.

BLOCKERB2 — "Graph stays until the next step starts" fights the right column's one state machine

The right column already has a single decider: RunDisplay + CenterContent._show_run_view() repaint the picture area on StepFinished (the stack pops), on sequence start/finish, on question answers and on review end — each ending in set_image(...) or show_no_picture(). A separately-managed graph widget gets stomped the moment its step finishes — the exact opposite of the §2 decision. Three interactions are unspecified: a step with both graph: and a question image (_pending_image_path takes the area), the look-back/review view (records only image_path per step), and the state diagram's "picture / logo" idle claim — there is no logo mid-run; a step without a picture inherits the enclosing sequence's picture or the area is hidden.

Design §2, §6, state diagram · evidence: center_view.py:253-281, run_display.py:189-237, interaction_panel.py:430-434

Fix: make the graph a state of RunDisplay/CenterContent (one decider paints picture, graph, question or nothing), define precedence vs question images, state the look-back story, and correct the diagram. Decide whether "stays until next step" survives its cost (Q3).

BLOCKERB3 — graph: on a Sequence step crashes recipe load

§2 makes graph common to every step type and §5 touches only Step.__init__. But build_step() splats YAML keys into constructors (registry.py:64) and SequenceStep.__init__ enumerates its parameters with no **kwargs (sequence_step.py:74-82) — image_path works there only because it was added explicitly. Since SequenceStepSchema extends _StepFields, the schema accepts graph: and the build then raises TypeError → RecipeError: a schema-valid recipe that fails to load.

Design §2, §5 · evidence: registry.py:64, sequence_step.py:74-82, recipe_schema.py:584, recipe_parser.py:800-803

Fix: add graph to SequenceStep.__init__ like image_path (and define what it means for a group), or exclude it from SequenceStepSchema. §9's test list should cover a graph: on every step type.

BLOCKERB4 — The copied code has no licence at all

The design flags this as an open item; the repo scan makes it harder than "open": zero LICENSE file, SPDX header or copyright notice anywhere in pyrade_xy_graph; pyproject.toml has no licence or authors field; all 7 commits are by one CERN author (ncass). A verbatim copy has no permission behind it, and reuse.toml needs an annotation for src/pyrade_xy_graph/**. Nothing may be committed first.

Design §10 · evidence: full-repo search of C:/git/pyrade_xy_graph (0 matches for licence/copyright/SPDX)

Fix: obtain licence + copyright holder from the author/CERN; add the reuse.toml annotation in the same change as the copy.

HIGHH1 — Run-end close races the design's own background pusher

"At run end the container closes every stream still open" (§3) while the demo's start_sine() thread pushes for 10 s after its step returned. Any early run end (step excluded, continue_on_error=False, halt) closes bg_sine.csv under the pusher: the next push() raises ValueError: I/O operation on closed file on a bare test-code thread — outside every PyPTS error boundary (reaches threading.excepthook/stderr, not report_error, and the run log is already closed). Nothing in pypts tracks or joins threads a step starts. The §3 lock guards push-vs-push, not lifetime.

Design §3, §8 · evidence: sequencer teardown path, no thread registry anywhere in src/pypts

Fix: specify push-after-close (recommended: silently drop + one DEBUG line) and make close() take the push lock. Part of the container's interface, not an implementation detail.

HIGHH2 — The copied one-slot pattern omits LocalSetup's abandon fence → cross-run pollution

sequence_is_running() checks only the sequence thread, so run 2 can start while run 1's background pusher lives. With a plain active-session slot, that thread's register_stream resolves run 2's session: run-1 data lands in run 2's streams/ and a StreamOpened attaches old data to the new run. local_setup.py built exactly this fence for devices (_abandoned/_refuse_if_abandoned, lines 119-182; abandon_active_setup() called at sequencer.py:788); the design copies the slot without the fence.

Design §3 · evidence: local_setup.py:119-182,274-292, sequencer.py:293-294,748-798

Fix: copy the whole pattern: sessions get an abandoned flag; a stale handle's push() fails (or drops) with a named error instead of writing into the next run.

HIGHH3 — Stream names become Windows paths with no legality handling

§2's "no safety mechanism" decision covers duplicate names, but register_stream('ch?1') is an OSError, 'a/b' a FileNotFoundError, 'V:out' silently writes an NTFS alternate data stream, and '..\report' escapes streams/ into the run folder. In the background-thread case the thread dies silently and the GUI waits forever. The framework already sanitises every other run-folder name with safe_name_part() (utilities/local_storage.py:60).

Design §3 (register_stream) · evidence: local_storage.py:60-65

Fix: pass the name through safe_name_part() (one line, existing helper) and say so in §3; StreamOpened/the GUI map then key on the sanitised name.

HIGHH4 — The typo WARNING lives on the wrong side: headless/CLI never see it

§2 states the WARNING unconditionally; §2 also says CLI/headless ignore graph: entirely; §6 puts the check in the GUI. So a recipe with graph: bg_sien passes CI headless runs silently and fails visibly only on an operator's bench. The engine owns both facts (the Sequencer opens the session and sees every StepFinished). Secondary: a GUI-side warning for the run's last step can land after end_run_log(), i.e. in the session log instead of the run log it explains.

Design §2 (Warnings, CLI/headless), §6 · evidence: sequencer.py:404-407, gui-side map §6

Fix: move the check into the Sequencer (engine-side, every frontend, correct log); wording per logging_rules.md.

HIGHH5 — Run end: the graph vs the TESTS PASSED/FAILED verdict image

"Run end returns to the existing idle behaviour" (§6) and the timeline's "idle" label misstate the invariant: run_finished() shows the logo marked with the run verdict via set_run_result(), held until the next run. Implemented literally, a run whose last step was graphed either drops the verdict picture or the graph covers it — the design never reconciles the two.

Design §6, timeline figure · evidence: center_view.py:233-243, interaction_panel.py:559

Fix: state it: on RunFinished the verdict image wins and the graph is torn down.

HIGHH6 — Unbounded memory and O(N²) re-reads

No bound anywhere on live data: the wrapped DataStore defaults to max_len=None, whose own comment warns a live session must set it "or RAM grows for the life of the acquisition"; the plot feeds full arrays to setData per update. And §6 re-reads X.csv from byte 0 on every StepStarted with graph: X — an Indexed wrapper stamping graph on all N generated steps makes step k re-parse k·samples rows on the GUI thread. A 100 Hz stream over a 2 h soak is ~720k points.

Design §6 · evidence: pyrade data_store.py:105-118, plot_widget.py:115-124

Fix: set max_len (or a scope window), keep per-name byte offsets instead of from-start re-reads, and batch rows per tick (each DataStore.append emits a synchronous full repaint).

MEDM1 — "Same outgoing path as Runtime.emit" is ambiguous, and both readings are wrong

The real emit is the Sequencer's wrapper (sequencer.py:553-560): run_abandoned guard → core.send → metadata scan mutating a shared dict. Reusing the closure from background-thread registrations adds a data race no current caller has; a bare core.send loses the run_abandoned guard, so a stale thread emits StreamOpened during shutdown. Also note §4's premise is subtly off: test functions never see a Runtime — PythonModuleStep._step() passes only the resolved inputs; the only seam test code has today is from pypts.hal import get_device. The design's process-global session is therefore the only workable mechanism — correct, but the doc should say so, and pick the send path: a dedicated thread-safe guard + core.send, no metadata scan.

Design §4 · evidence: sequencer.py:539-560, python_module_step.py:267-280

MEDM2 — The session's stated anchor doesn't exist; its real home is a decision

"Next to its existing with LocalSetup(...) in execute_sequence()" — the LocalSetup block is in run_body() (sequencer.py:492), where run_dir (a local of execute_sequence(), line 366) is not in scope. The two possible homes differ materially: inside run_body() the session closes before RunFinished; in execute_sequence()'s finally it closes after, while the GUI may still tail. The doc must pick one (recommended: execute_sequence(), closing streams just before RunFinished is sent).

Design §3 · evidence: sequencer.py:366,390,403-414,492

MEDM3 — The CSV dialect is an unpinned two-process contract, and the tail reader already exists

Writer (§3) and reader (§6) are specified in different modules with no shared code: the obvious csv.writer on a text-mode append handle writes x,y\r\r\n on Windows, which a \n-splitting byte-offset reader turns into blank pseudo-lines and \r-suffixed floats; and text-mode seek(byte_offset) is undefined for non-tell() cookies. report.py already pins the run folder's convention (newline='', encoding='utf-8', lines 110, 276) and hmi/gui/log_tail.py:LogTail already solves torn-line hold-back, open-when-created and the Windows share-mode case — the §6 "pure, Qt-free CSV tail reader" re-implements it.

Design §3, §6 · evidence: report.py:110,276, log_tail.py:91-180, log_follower.py:93

Fix: pin the dialect in stream_handler (it owns the file format) and reuse or extract LogTail rather than writing a second tailer.

MEDM4 — Re-registering a name appends a restarted x; the plot pipeline assumes monotonic x

§2 decides "the GUI shows what is in it", but the copied pipeline enables clipToView and auto peak downsampling (plot_widget.py:78,124), which index by sorted x: appended data with x restarting at 0 renders garbled or with chunks silently missing — not a line doubling back. Nothing forbids two live handles on the same CSV either.

Design §2 (Files/Names) · evidence: pyrade plot_widget.py:78,115-124

Fix: document the contract (x monotonic per name; otherwise the plot is undefined), or start a new file per registration.

MEDM5 — "Verbatim copy" ships import-time global side effects and a crashing menu entry

Facts from the pyrade repo the design doesn't mention:

  • plot_widget.py:11 imports tdms_exporter, registering a TDMS entry in pyqtgraph's native right-click Export dialog; choosing it imports nptdms — not installed → ModuleNotFoundError in a Qt slot during a run. So "h5py/nptdms/pandas are used only by parts PyPTS does not call" is wrong at run time, and "verbatim" and "no crash" cannot both hold.
  • plot_widget.py:18-20 sets global pyqtgraph config (antialias, OpenGL, white background / black foreground) at import — and ignores the GUI's dark palette.
  • core/trace_level.py monkeypatches logging.Logger with a trace method and level 5 — to be checked against pypts's own TRACE level and logging_rules.md before import.
  • ScopePlotWidget and DataStore are not wired to each other — the glue lives in graph_widget.py (which imports h5py/pandas at module top); §6's wrapper must re-create it (~6 lines: data_updated → get_signal → update_signal), and the DataStore x-key defaults to 'Time'.
  • Repo hygiene a copy inherits: requires-python >=3.9 is wrong (the code uses 3.10+ syntax at runtime), pymeasure is a stale dependency, committed .DS_Store/.pyc.

Design §7 · evidence: pyrade plot_widget.py:11,18-20, tdms_exporter.py:42,58, trace_level.py, graph_widget.py:108,446-452

Fix: §7 must name the (small) deliberate deviations from verbatim — at minimum drop the tdms_exporter import and the global setConfigOptions — and record them so the "later swap" knows what to re-apply. See Q5.

  • Docs list misses: src/pypts/README.md:35 ("stream_handler | stub…"), logger/logging_rules.md (must catalogue the new WARNING), and three CLAUDE.md sentences beyond the promised stub-drop: the architecture tree (new top-level src/pyrade_xy_graph/), the recipes-folder enumeration (new demo folder), and the reuse.toml-globs sentence (staled by the §10 annotation).
  • Spikes: spikes/stream_handler/StreamContainer.py and spikes/GUI/XYGraph/ are this feature's reference material; stream_handler.md says they need "rewriting rather than moving back" — the design should state their fate.

Design §8–§10 · evidence: reuse.toml globs, src/pypts/README.md:35, stream_handler.md

4. Minor findings

  • A second StreamOpened for a name whose graph is already LIVE is an unspecified GUI transition.
  • Nested with StreamSession inside a run clears the one slot for the rest of the run (identity-based deactivate — same subtlety LocalSetup's _deactivate(self) handles).
  • Pydantic's coerce_numbers_to_str turns graph: 07 into '7' silently.
  • Flush-per-push at 100 Hz holds the lock through an OS flush each sample — consider flushing per batch/interval.
  • StreamOpened.unit never reaches the CSV, so headless runs (which keep only the files) lose it — an argument for putting the unit in the CSV header instead (see §5).
  • A second top-level package in the wheel (pyrade_xy_graph) — namespace ownership on PyPI/registry should be a conscious choice.
  • "Excluded from mypy" is a no-op: [tool.mypy] is an opt-in files list — nothing to do, but the sentence is wrong.
  • matplotlib already sits unused in [project].dependencies — clean it up when adding pyqtgraph, or at least don't cite the deps list as tidy.
  • graphstep_recipes/ breaks the existing naming precedent (stepimage_recipes/ is the feature-demo precedent; <type>step_recipes/ is for step types — graph is not a step type).
  • Doc errata, small: the run folder is <timestamp>_<recipe> (board id is only the report file stem); with LocalSetup is in run_body(); defaults in hmi_client.py log at DEBUG rather than "do nothing"; an unhandled message is reported, not a crash.

5. Simplicity & deep-module assessment

The container itself is a genuinely deep module — three names (register_stream, Stream, StreamSession) hiding file layout, locking, and lifecycle; zero pypts imports; the on_open callback is a clean seam that keeps the message classes out. Keep that. What's missing from its interface (in the full sense: everything a caller must know) are the lifetime rules — push-after-close, re-registration, abandonment, name legality. H1–H3, M4 are all the same root cause: the design specifies the happy path of the interface and leaves its error modes undefined.

The one real simplification candidate: delete StreamOpened. Apply the deletion test — the GUI already receives RunStarted.run_dir, and graph: X names the stream, so the GUI can derive <run_dir>/streams/<safe X>.csv and poll for the file's existence — exactly how it already follows the run log (LogFollower opens it "once the Logger has created it"). What vanishes with the message: the dataclass, two union entries, the EXAMPLES/pickle/handled tests, the hmi_client case + hook + GUI override, the Sequencer's on_open wiring, and the whole M1 emit-path ambiguity. What it costs: unit must ride in the CSV (a header line — which also fixes the headless unit loss, see minor list), the "waiting" state is file-existence polling instead of a message, and the no-folder run (B1) must carry a streams directory some other way — but B1 must be decided under either design. The file becomes the entire contract between the processes: one channel instead of two.

Reuse instead of re-implementation: LogTail (tailing, torn lines, Windows share mode), safe_name_part() (name → filename), report.py's CSV conventions (dialect precedent). The design currently re-specifies all three.

Right column: the design adds a parallel state machine next to RunDisplay's existing one (B2). The deep-module answer is one decider with one more state, not two owners of one widget slot.

Copy scope: "verbatim whole package" is defensible for the later swap-to-dependency, but it is already not achievable verbatim (M5). The honest options are in Q5.

6. Open decisions (answers belong to you)

Q1 — Keep or delete StreamOpened? File-only contract (run_dir + name + polling, unit in the CSV header) vs. the message as designed.
➡️ Recommended: delete it — one channel, less machinery, and the GUI already has the pattern.
Q2 — No-folder runs (engineering retest, folder-creation failure): (a) streams disabled + one engine-side WARNING; (b) a temp per-run streams dir (path then must travel: message or a new RunStarted field); (c) always create a run folder when the recipe has graph keys.
➡️ Recommended: (a) — simplest honest behaviour; revisit only if retests must graph.
Q3 — Does "graph stays until the next step starts" survive its cost? It contradicts how pictures behave today (they pop on StepFinished) and forces stickiness through sequence-finish and question repaints. The alternative: graph lives exactly while its step runs, like a picture.
➡️ Recommended: graph lives while the step runs; the §2 decision was made before these costs were known and deserves a re-check.
Q4 — Warning side: engine (Sequencer, run log, all frontends) vs GUI as designed.
➡️ Recommended: engine-side (H4).
Q5 — Copy scope: (a) whole package with 2–3 documented one-line deviations (drop the tdms_exporter import, drop/scope the global setConfigOptions, check trace_level vs pypts TRACE); (b) plot path only (plot_widget, data_store, trace_level, math_engine — ~1,400 of 3,286 LOC); (c) strictly verbatim and accept M5's breakage.
➡️ Recommended: (a) — keeps the later-swap story, removes the landmines, and the deviations are a short documented list to re-apply upstream.
Q6 — Lifetime semantics in §3's interface: push-after-close = silent drop + DEBUG? close under the push lock? abandon fence copied from LocalSetup? re-registration = same file, x-monotonicity documented as the caller's duty?
➡️ Recommended: yes to all four; they are one paragraph in the design and in stream_handler.md.
Q7 — Sequence steps: support graph: on them like image_path (explicit parameter, shows while the whole group runs), or exclude it from SequenceStepSchema?
➡️ Recommended: support it — symmetry with image_path, and B3's fix is the same size either way.
Q8 — Licence (B4): the author (ncass, CERN) must name licence + copyright holder before any copy is committed. Who asks, and is LGPL-2.1-or-later the target?
➡️ Recommended: ask for LGPL-2.1-or-later to match the host project; blocked until answered.
