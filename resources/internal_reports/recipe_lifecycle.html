Recipe Lifecycle — from file to verdict

One page, one run: open → parse → hand to the Sequencer → execute → results back through CORE → shown on the HMI. Everything travels as messages; modules never call each other.
HMIfrontend process
COREengine process — the mediator
Sequencerthread of CORE
1 · Load
LoadRecipe(path)
the operator picked a .yml
Parse & validate — Recipe.from_file(): normalize case, check every mandatory field against rules.py, fill the optional defaults, build Recipe → Sequences → Steps.
RecipeLoaded(summary)
fills the sequence chooser and the step table
UseRecipe(recipe)
the live, validated object — this link never leaves the process
2 · Run
StartSequence(name)
the operator pressed run
RunSequence(name)
Execute — on a worker thread, so the event loop keeps turning (heartbeats, StopSequence). Each step: resolve inputs → do the work → judge outputs → StepResult. Teardown always runs, even after a failure or an abort.
3 · Results
RunStarted → StepStarted / StepFinished (each step) → SequenceFinished → RunFinished(result)
emitted live by the Sequencer, forwarded unchanged by CORE to the HMI — the step table updates as the run happens
The verdict: every step ends as PASS, FAIL, DONE, SKIP, ERROR or STOP; a run aggregates to its highest one. Only ERROR stops a sequence — a FAIL is a result, not a crash.
A bad file never runs: parsing raises one RecipeError naming every problem at once; CORE reports it to the operator (ModuleErrorReported) and the Sequencer never sees the recipe.
