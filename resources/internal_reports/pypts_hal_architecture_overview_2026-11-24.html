PyPTS + HAL — architecture overview

Branch architecture_refactor, after HAL phase 3 (9ca56dc) · 2026-11-24 · written from the module context files

0. Start-up, and who is in charge

python -m pypts starts one small launcher. It spawns the Logger, then CORE, then the frontend, and after that only waits. CORE builds the rest itself: its two threads, and the link to the HAL server, which it either finds already running or starts as a detached process. Time runs left to right below; step through it.

HAL ↔ drivermultiprocessing Pipe, pickled tuplesyesone call at a time; hello, result, error, log, printed

Two families, on purpose. Inside PyPTS every link is a QueueWrapper[Msg] carrying plain dataclasses, one union type per direction, polled — never blocking — by each module's event loop; at TRACE every message is logged once when sent and once when received. Towards the HAL it is a small line protocol with a client (pyhal.client): one client per process, so the Sequencer's test code and CORE's hal_link share it. That is what lets the same test functions run in a plain script: with pyhal.connect("bench.ini"): ....

2. How data moves

Not all data takes the same road. Commands, the recipe and results go through CORE as messages. Bulk data goes around it, through files: streams, logs and pictures are written to disk and read back by the GUI, so a fast stream never fills a queue. Hardware data never touches the message layer at all — it goes over TCP to the HAL. Pick a kind of data to follow it.

4. Rules that hold it together

  • Only CORE routes. Modules never call each other or touch another's queue; the one exception is log records, which go straight to the Logger. CORE forwards the same object and never interprets recipe content.
  • Every handler is a closed match ending in unhandled(), over a link's union type — adding a message without its case fails mypy and test_messages.py.
  • Heartbeats both ways. Each watched module beats to CORE; silence of 5 s is a WARNING, 15 s takes the crash close. CORE beats to the HMI so a frontend can tell a busy engine from a dead one. The HAL drops a client silent for 5 s.
  • Devices are per run. pyhal.run_scope() wraps every run; a device opens on its first get_device() and closes, newest first, after the teardown steps and before RunFinished — whatever the result.
  • Failures stay small. A driver that crashes or hangs takes down its own process only; the HAL's teardown ladder tries teardown(), then a fresh driver process to tear down. A HAL PyPTS started gets shutdown at close; one it found running is left running.
  • One writer per file. The Logger owns the log, the Report owns the CSV/HTML, the HAL owns its log; readers (the GUI's log panel and graphs, CORE's LogTail) tail files and never write them.
