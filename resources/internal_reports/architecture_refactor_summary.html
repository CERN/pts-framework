PyPTS – architecture_refactor: what has been done

46 commits ahead of master • 2 September 2026
Converted from architecture_refactor_summary.rtf (written 2 September 2026). The original pointed to resources/roadmap/pypts_roadmap.md for status detail; that content now lives in pypts_implementation_status.html at the repo root, which is the current source of truth.

Short version

  • Architecture rebuilt – two processes (engine and operator frontend) plus a Logger process, with the Sequencer and Report as threads of the engine, and one launcher owning startup.
  • Messaging replaced end to end – typed frozen messages, one module per link, one transport class, and handlers that raise on anything unexpected instead of dropping it.
  • Health and error handling in place – heartbeats from every module, timeout detection in the engine, and a uniform error report naming module, method and exception.
  • Recipe layer rewritten – rules defined once in code, one validator for every step type, and a simplified format where optional fields can simply be left out.
  • The engine runs recipes – five step types (Wait, PythonModule, Indexed, UserInteraction, UserWrite), real sequence execution, and per-step continue-on-error.
  • Reporting produces artefacts – one folder per run, a CSV that grows during the run, an HTML report at the end, and the operator told where it is.
  • Logging centralised – a single writer process, a complete message trace at DEBUG level, and a Debug Monitor that reads it back.
  • Operator GUI rebuilt on PySide6 – visual parity with the old screen: four panels, live log, live step verdicts, light and dark themes.
  • Configuration made proper – a singleton handler, a per-user config file from a commented template, typed access, versioned and never silently repaired.
  • Cross-platform behaviour made deliberate – the same process-spawning semantics everywhere and all paths resolved per platform; verified on Windows, a Linux run still owed.

Longer version

1. Groundwork: architecture, messaging, modules

  • Architecture rebuild finished.
  • Message layer implemented.
  • Heartbeats, watchdog timeout detection, and two error-handling decorators.
  • Safe abort and release on unexpected crash, with the full traceback logged.

2. Recipes, rules and the execution engine

  • Recipe integration implemented: rules define, validator checks, parser builds, and the recipe object is pure data → passed to the Sequencer via CORE.
  • Format simplified – rules in one importable place, one validator for all step types, many fields made optional, slimmed-down required recipe format – less noise in .yml.
  • Five step types working: Wait, PythonModule, Indexed, UserInteraction and UserWrite. (A few more still to implement.)
  • Real sequence execution, plus demo recipes per step type.

3. Reporting

  • One folder per run, a CSV that grows step by step, and a self-contained HTML report when the run finishes.
  • The operator is told where it is – the CLI prints the path, the GUI opens the folder.

4. Logging

  • A single Logger process is the only writer of the run log; the level is resolved once by the launcher.
  • Full message trace at DEBUG – every message logged by both sender and receiver.
  • Debug Monitor helper renders the trace, heartbeats and module liveness from a log file, and is started beside the run – debugging only.

5. GUI features

  • Implemented a basic GUI with everything necessary for v1.0.0.
  • Four panels: step table, live log tail, interaction panel and results summary.
  • Some new features added – the step table shows live verdicts and a syntax-coloured YAML preview when hovering a step.
  • Operator interaction: images, buttons, keyboard navigation and free-text entry.
  • Full light and dark theming, working tooltips (including on disabled buttons), and a browse-and-pause mode.
  • File → Open Recent, and Edit → Remove Cache (recent-recipes cache + config file), which names and sizes everything before deleting it.

6. Configuration

  • One configuration handler replaced the ad-hoc functions that wrote into the temp directory.
  • Automatic config file discovery or creation.
  • The config file now lives in the per-user config directory, created from a commented template.
  • Typed access through a schema, with a single writer.
  • Versioned: a broken or mismatched file is discarded for that run, with a notice to the operator and an entry in the log – never silently repaired.

7. Cross-platform compatibility

  • Process spawning pinned to the same method on every platform, so Windows and Linux behaviour is the same.
  • Every per-user path (config, data, state, logs) resolved through one platform-aware place; no hardcoded locations.
  • Verified end to end on Windows; a Linux end-to-end run and a headless GUI test job are still to be tested.
