PyPTS – architecture_refactor: what has been done

82 commits ahead of master • updated 15 September 2026 (first written 2 September)
A summary, not the status. pypts_implementation_status.html at the repo root is the source of truth for what is done and what is next; usage_manual.html says how to use the application. The old porting-findings document (migration_status.html) was removed on 15 September once its last open gaps (M-2b, M-3) were closed.

Short version

  • Architecture rebuilt – two processes (engine and operator frontend) plus a Logger process, with the Sequencer and Report as threads of the engine, and one launcher owning startup.
  • Messaging replaced end to end – typed dataclass messages, one module per link, one transport class, and handlers that raise on anything unexpected instead of dropping it.
  • Health and error handling in place – heartbeats from every module, a watchdog that ends a run when a module goes silent (configurable), and a uniform error report naming module, method and exception.
  • Recipe layer rewritten – rules defined once in code, one validator for every step type, and a simplified format where optional fields can simply be left out.
  • The engine runs recipes – six step types (Wait, PythonModule, Indexed, UserInteraction, UserWrite, UserLoading) – nothing left to port – real sequence execution, and per-step continue-on-error.
  • Reporting produces artefacts – one folder per run, a CSV that grows during the run, an HTML report at the end, and the operator told where it is.
  • Logging centralised – a single writer process, a complete message trace at DEBUG level, and a rewritten Debug Monitor that reads it back.
  • Operator GUI rebuilt on PySide6 – visual parity with the old screen, a Settings dialog, and every step's measured values in the results tree.
  • Four ways to run it – GUI, CLI, the pypts.api embedding API, and a headless mode for CI that exits with a pass/fail code.
  • Configuration made proper – a singleton handler, a per-user config file from a commented template, typed access, versioned and never silently repaired, editable from the GUI.
  • Cross-platform behaviour made deliberate – the same process-spawning semantics everywhere, all paths resolved per platform, a Linux compatibility pass done; verified on Windows, a real Linux run still owed.
  • Recipe Creator refactored – a new main window with undo/redo, three step views and live validation.

Longer version

1. Groundwork: architecture, messaging, modules

  • Architecture rebuild finished.
  • Message layer implemented. Messages are plain dataclasses (no longer frozen), checked for pickle safety at the process boundary.
  • CORE owns the loaded recipe; the frontends only ever see summaries.
  • Heartbeats, and a watchdog that acts: prolonged silence ends the run, and can be turned off ([watchdog] enabled) for debugging with a breakpoint.
  • Two error-handling decorators; safe abort and release on unexpected crash, with the full traceback logged.

2. Recipes, rules and the execution engine

  • Recipe integration implemented: rules define, validator checks, parser builds, and the recipe object is pure data → passed to the Sequencer via CORE.
  • Format simplified – rules in one importable place, one validator for all step types, many fields made optional, slimmed-down required recipe format – less noise in .yml.
  • Six step types working: Wait, PythonModule, Indexed, UserInteraction, UserWrite and UserLoading (pick a file or a folder). The remaining old types were deliberately dropped, so the port is complete.
  • Every step's inputs, outputs and output checks reach the operator on every verdict, not only on a FAIL (M-3) – no change needed in recipes or test code.
  • Real sequence execution, plus demo recipes per step type.

3. Reporting

  • One folder per run, a CSV that grows step by step, and a self-contained HTML report when the run finishes.
  • The operator is told where it is – the CLI prints the path, the GUI opens the folder.

4. Logging

  • A single Logger process is the only writer of the run log; the level is resolved once by the launcher.
  • Two registers: INFO and above written for the technician, everything developer-facing at DEBUG.
  • Full message trace at DEBUG – every message logged by both sender and receiver.
  • Debug Monitor rewritten: discovers message types from the trace instead of recognising a fixed list, and shows the watchdog's fatal verdict – debugging only.

5. GUI features

  • Four panels: step table, live log tail, interaction panel and results summary.
  • The step table shows live verdicts, the measured values on hover, and a syntax-coloured YAML preview of each step.
  • The results panel is a tree: each step opens into its inputs and outputs, with each output's check.
  • Operator interaction: images, buttons, keyboard navigation, free-text entry and a file/folder picker, with an always-present Cancel.
  • Full light and dark theming, working tooltips (including on disabled buttons), and a browse-and-pause mode.
  • File → Open Recent and Open Config; Edit → Settings (theme, window size, folders, log level …) and Remove Cache. Opening a recipe is disabled during a run; the window title names the loaded recipe.

6. Running without the GUI

  • CLI mode: a text shell, Qt-free, which reacts to CORE shutting it down without waiting for Enter.
  • pypts.api: Pts drives the engine from Python code (load, run, answer questions, get a result back); open_gui() opens the window with a recipe loaded or started. Showcase: api_showcase.py.
  • Headless mode (M-2b): python -m pypts --mode headless --recipe x.yml runs one recipe unattended and exits 0 passed / 1 failed / 2 error or stopped / 3 nothing ran – ready for CI.

7. Configuration

  • One configuration handler replaced the ad-hoc functions that wrote into the temp directory.
  • Automatic config file discovery or creation, in the per-user config directory, from a commented template.
  • Typed access through a schema, with a single writer: CORE, which carries out changes the operator makes in the GUI's Settings dialog (they apply from the next start).
  • Versioned: a broken or mismatched file is discarded for that run, with a notice to the operator and an entry in the log – never silently repaired.

8. Cross-platform compatibility

  • Process spawning pinned to the same method on every platform, so Windows and Linux behaviour is the same.
  • Every per-user path (config, data, state, logs) resolved through one platform-aware place; no hardcoded locations.
  • A static Linux compatibility pass is done. Verified end to end on Windows; a real Linux run and a headless GUI test job are still owed.

9. Helper applications and documentation

  • Recipe Creator refactored: a recipe model with undo/redo, list, card and panel step views, a YAML editor, and live validation through the migrated recipe verificator.
  • usage_manual.html (repo root): a short manual for users – modes, options, answering prompts, where files go.
  • Every module has a context file beside its code; documentation, plans and TODOs cleaned up.
