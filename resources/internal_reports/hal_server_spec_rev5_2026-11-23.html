HAL server — design

Status: draft for review, revision 5, 2026-11-23. Branch architecture_refactor.

Revision 5 takes in every decision of the Claude Doc "HAL server — what is to be done" (https://claude.ai/artifact/7HRP7hqmvsdCciJkS1DWe9, answered 2026-11-20), the three answers of 2026-11-23 (D56-D58), the fixes of the rev 4 review (Claude Doc "HAL server spec rev 4 — review and decisions") and the code as it is after the teardown refactor (9d056f4). Revision 4 is in git history (db8edc6).

What changed from revision 4, in one paragraph: several clients may share one HAL and its devices; the HAL runs every request first in, first out. The Sequencer closes a run's devices again, before RunFinished, as LocalSetup does today. **PyPTS sends close_all without waiting for it, on every close, crash close included. No "HAL lost" state, no HAL heartbeat, no shutdown budget:** a dead HAL shows up as a failed call. PyPTS reads the HAL's log file to get its lines. The client sends a heartbeat instead, and the HAL drops a silent client.

Marked Claude's call = decided by Claude, for the user to check. Every row of the decision table (§5) was decided by the user. Review fix = a fix from the review of revision 4. Review 5 = a fix from the review of this revision on 2026-11-23 (two reviewers: the spec against the code, and safety and failure modes). Every finding of that review is fixed in place; none needed a new decision.

1. Intent

Today the hardware layer (src/pypts/hal/, hal/hal.md) is a library inside the CORE process. The Sequencer's run_body() wraps each run in with LocalSetup(...); a ConnectionDriver spawns one driver process per device and talks to it over a multiprocessing Pipe with pickled tuples.

The redesign makes the HAL **a package of its own, pyhal, running as a standalone local service, the HAL server, reached over TCP on localhost**. PyPTS connects to a HAL that is already running, or starts one. Why:

  • Clarity. One process owns the bench; every device call visibly goes to one place.
  • Standalone use. The HAL is usable without PyPTS — by a Python script, and later by clients in other languages (LabVIEW, C#, ...). Later pyhal becomes its own distribution.
  • Independence. The HAL lives on its own: PyPTS crashing does not take it down.
  • Visibility. A developer can look at the HAL and the bench from the PyPTS GUI.

The framework stays as small as possible: fewer code paths beat fewer processes. The user's rule for closing (2026-11-19): handle the standard close and a crash, nothing more.

2. Goals

  1. The HAL server is a standalone process (python -m pyhal). PyPTS, at startup, connects to one that is running or starts one. With an empty bench it starts anyway, idle (D50).
  2. One connect path for everyone: PyPTS and scripts both use pyhal.connect().
  3. Test code calls devices the same way: get_device("x").operation(...), and the same test module runs under PyPTS and in a plain script. Only the import path changes (D11).
  4. The driver contract unchanged: BaseDriver, the device types and their verbs, every shipped driver's behaviour. Only import paths change (D11). Value differences: §7.4.
  5. Several clients at once — PyPTS and a script, say — on one HAL and the same devices (D51).
  6. A run ends with its devices torn down, before RunFinished, as today (D42).
  7. Every close of PyPTS that runs Python code sends close_all (D45).
  8. A developer-only View → HAL window in the GUI: the HAL, the bench, two buttons (D49).

3. Non-goals

  • PyPTS killed outright (terminated, power cut): nothing sends close_all; the HAL keeps every device as it is (D36).
  • Detecting a dead or frozen HAL ahead of a call, restarting it, or keeping it alive (D47, D28).
  • Locking a device to one client between calls (D52).
  • Device probing / live availability.
  • A separate distribution now. pyhal ships inside pts-framework.
  • Remote (non-localhost) access, authentication. Anyone on the machine can reach the port.
  • Streams (D33).
  • A rich panel.

4. Anti-goals — failure even if it works

  • A normal close of PyPTS, or a crash close, that does not send close_all.
  • A run that ends with a device it opened still open, when the HAL is alive.
  • A device handle from an earlier run reaching a device again.
  • Pickle on the TCP link (a remote-code-execution hole, and Python-only).
  • A protocol that cannot be swapped without touching the architecture.
  • Two code paths: one for "PyPTS started the HAL", one for "it was already running".
  • pyhal importing pypts.

6.1 Who does what

  • The HAL server owns the bench. It reads the bench file at start, opens a device on the first open (or call) for it, keeps it open until close / close_all / a rescue (D44) / its own exit, and serves any number of clients. Clients come and go; devices stay (D36).
  • Inside the HAL server, today's machinery moves across nearly as-is: spawning driver processes, the pickle Pipe protocol, CALL_TIMEOUT_S, the teardown ladder with its rescue, recover. The Pipe stays pickle; it never leaves the HAL. One change: D44.
  • **pyhal's client** (client.py) is one object per process, made by pyhal.connect(). It holds the long connection test code uses, a beat thread (D53) and the log tail (§9). get_device(), recover_device(), device_info(), close_device() and run_scope() are module functions of pyhal that use the process's connected client.
  • CORE connects at startup (D24) through a small core/hal_link.py, on a worker thread of its own, never on its event loop (review fix for B3: connect-or-start can take HAL_START_TIMEOUT_S, the frontend gives up on a CORE silent for HEARTBEAT_FATAL_S = 15 s). It owns the close (D45) and View → HAL (§8). Each of CORE's own requests — close_all, shutdown, status — goes on a short connection of its own, so it never waits behind a test call holding the long connection (D18). Claude's call. A short connection: connect only, never start (1 s timeout); **read hello first (1 s), so no unread data is waiting when the socket closes; send one** request; then either read its answer, or half-close (shutdown(SHUT_WR)) and close without reading (review 5).
  • The Sequencer wraps each run in with pyhal.run_scope(): (D42), where LocalSetup is today. It never connects, and holds no HAL object: it uses the module function. Claude's call, so no module calls another (CLAUDE.md: modules never call each other).
  • Test code on the Sequencer's worker thread, and threads it starts, gets a device handle from pyhal.get_device(). A call on the handle is a request on the long connection. The handle keeps today's surface: __getattr__ turns a name among the device's operations into a call, and any other name raises AttributeError without a round trip (the opened answer carries device_type and operations).

6.2 Connect or start (D37)

  1. pyhal.connect(bench=..., port=DEFAULT_PORT, log_sink=None) connects to 127.0.0.1:<port>.
  2. A HAL answers → hello (§7.2). The client compares:
    • the version (D48) and the bench file (path after os.path.normcase(os.path.realpath()), and a SHA-256 of its bytes, so an edited bench.ini counts as different — Claude's call): a difference is a WARNING naming both, and the client uses the HAL anyway;
    • the open devices: a WARNING listing them only when no other client is connected (hello carries the count), since with other clients they are theirs, not leftovers (D40, Claude's call); otherwise DEBUG.
  3. Nothing answers → the client starts python -m pyhal --bench <file> --port <port> detached, passing its own sys.path so dotted driver paths resolve as today, then retries the connection until HAL_START_TIMEOUT_S (15 s).
    • Windows: CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP, not DETACHED_PROCESS, so the driver processes do not open console windows an operator can close (review fix).
    • Linux: start_new_session=True.
    • stdout/stderr go to a startup file in --log-dir; when the HAL fails to start, the client's error quotes its tail (review fix).
  4. "I started it" (D38): the client passes a one-time random start nonce (--nonce) to the HAL it starts, and hello echoes it. A pid does not work: on Windows a .venv's python.exe is a redirector that runs the real interpreter as a child, so the spawned pid never matches (review 5). The nonce also settles two starters at once: both start a HAL, the second cannot bind the port and exits (D56), both connect to the first; only its starter's nonce matches.
  5. **The wait for hello** is a handshake, not an answer, so D57 does not apply: it is bounded by HAL_START_TIMEOUT_S on the long connection, 1 s on a short one. Something on the port that accepts and stays silent is "not a HAL".
  6. A HAL that is shutting down (a shutdown is queued or running) answers a new connection with an error (origin hal, the HAL server is shutting down) instead of hello, and keeps its listener until it exits, so no second HAL can bind while the first is still tearing down. connect(), on that error, retries until the port is free, then starts a HAL, bounded by HAL_SHUTDOWN_WAIT_S (builder sizes it above a few close ladders). This is what File → Restart hits: the old CORE has just sent shutdown (review 5).
  7. **Timeout, or no hello** → D21: PyPTS starts anyway; get_device() raises the reason. No retry later in the session (D28).
  8. While the startup connect is still running (on hal_link's worker thread), run_scope() waits for it to finish, bounded by the same timeouts, then goes on or raises the D21 reason. A headless run starts at once, so this case is ordinary (review 5).

6.3 A run and its devices (D42)

A run is one press of Start: the top-level sequence, every sequence it calls, and the teardown steps (Sequencer.execute_sequence() → run_body()). The HAL never sees it.

  • run_body() today: with LocalSetup(self.read_hardware_sections): around run_sequence_body(). Rev 5: with pyhal.run_scope(): in the same place. The run log closes (end_run_log()) and RunFinished goes out after it, exactly as today.
  • **run_scope() on entry fills the process's active-scope slot** (successor of today's _active_setup), raising the scope counter.
  • **get_device(name)** inside the scope sends open (which opens, or reuses an open device), and records the name in the scope. Outside a scope it raises, as today (No local setup is active. ..., reworded: get_device() works in test code PyPTS is running, or inside 'with pyhal.connect(...)' in a script of your own.).
  • **run_scope() on exit:** (1) clear the slot and raise the counter — no lock needed, so a polling test thread cannot delay it (review fix for B4); (2) send close for each device the run asked for, newest first, each waiting for its answer, so the teardown lines are in the run log (B1); (3) drain the log tail synchronously (§9). Never raises; a failed close is logged as today's Device 'x' did not close: ....
  • The fence (anti-goal 3): each handle remembers the counter it was made under. Every request from a handle compares it with the client's counter in the same step as the send, under the long connection's lock. A stale handle raises locally: Device 'x' belongs to a run that has ended; call get_device('x') again. The HAL never produces it. The open inside get_device() is fenced the same way (closes B4's first hole).
  • Another client using the same device (D42 B, D51): the run's close tears it down anyway. That client's next call opens the device again (D44's rule: the next request for a closed device opens it).
  • A script: pyhal.connect(...) opens a scope itself, with or not, so a script that skips with still gets devices (D54, review 5). Leaving the with, hal.close() or the atexit ends it: the same close as PyPTS's (§6.4), not per-device closes. CORE's connect() passes scope=False; the Sequencer's run_scope() is PyPTS's scope.
  • **Not fenced (gap, pyhal.md says so):** the active-scope slot is one per process, as _active_setup is today. A thread that test code started in run 1 and that calls pyhal.get_device("x") again during run 2 gets a valid handle of run 2. The fence covers handles, which is what anti-goal 3 asks.

  • The close (hal_link.close(), the same for both closes and for a script — review 5):
    1. Raise the scope counter and close the long connection. The HAL drops a disconnected client's queued open / call / recover / info (§7.5), so a teardown step or a test thread still running in a crash close cannot reopen a device behind the close_all (D44 would otherwise reopen it on its next call).
    2. If the startup connect is still running, wait for it (§6.2 step 8). No HAL → nothing to send.
    3. Send one request on a short connection: shutdown if this PyPTS started the HAL (shutdown runs close_all itself), otherwise close_all. Do not wait for its answer.
    4. On the closing thread itself, never handed to a worker: CORE's threads are daemons and close_at_once() leaves at once, so a send on another thread could die unsent. Bounded by the 1 s connect and the 1 s hello.
  • Sending without waiting is safe only with three rules: the HAL finishes a close_all it has read, even after the client has gone (D47); the client reads hello before it sends; and it half-closes after sending (shutdown(SHUT_WR), then close). Closing a socket with unread data waiting makes the OS reset the connection, and the reset can drop the request still in the HAL's receive buffer.
  • No shutdown budget changes: CORE_SHUTDOWN_TIMEOUT_S (30 s, launcher/startup.py) and CORE's deadline-free closes (core/core.md, Shutdown choreography) stay as they are.
  • The crash close's CRITICAL (BENCH_MAY_BE_ENERGISED, logged by close_at_once() with a run open, and by end_run_for_silent_module() before it) stays as it is: PyPTS does not wait for the close_all, so "may still be energised" stays true (review 5 dropped rev 5's rewording). Only its code comment, which says the driver processes end with CORE, changes.
  • Cutting other clients off (D51 C): a close_all or shutdown from PyPTS also closes the devices a script is using, and shutdown ends its connection. Accepted.

6.5 The HAL's own exit (D27)

  • Every exit path Python can observe — shutdown, Ctrl+C, console close (CTRL_CLOSE_EVENT on Windows, SIGTERM/SIGHUP on Linux), an uncaught exception in any server thread — first tears down every open device, newest first, then exits. The death of any server thread is fatal: teardown, then exit (review fix).
  • One thread owns the exit teardown, and it never runs beside a request (review 5): two threads on one driver Pipe would corrupt it. The exit path stops accepting new clients (§6.2 step 6), empties the queue of everything but the close_all / shutdown that caused it, and lets the request thread finish the request it is running (≤ CALL_TIMEOUT_S). The request thread then runs the teardown. If the request thread itself is what died, the main thread runs it; nothing else touches a driver then.
  • A second Ctrl+C during that teardown does not abort it (review fix).
  • Driver processes must not be ended by multiprocessing's exit-time terminate of daemon children: today they are daemon=True (ConnectionDriver._start()), which on a clean parent exit kills them without teardown(). How is the builder's call.
  • Driver processes ignore Ctrl+C, as today (driver_process_main() calls ignore_keyboard_interrupt()).
  • Not covered, listed as gaps: TerminateProcess / SIGKILL, logoff of a detached HAL, a job-object close. Then D29 applies. Only partly covered: closing the console of a HAL started by hand — Windows kills the process about 5 s after CTRL_CLOSE_EVENT, less than one close ladder (review 5).
  • The port after exit (review 5): the HAL closes its listener last, after the teardown (§6.2 step 6). On Linux it binds with SO_REUSEADDR, which still allows only one listener, so connections the HAL closed (in TIME_WAIT) do not block the next HAL's bind. On a shutdown it sends bye and lets the client close first.

6a. Packaging — the pyrade_xy_graph pattern

  • src/pyhal/, beside src/pypts/ and src/pyrade_xy_graph/, added to [tool.setuptools.packages.find] include in pyproject.toml.
  • **It never imports pypts**, enforced by a test in tests/quality_tests/. Today's HAL imports pypts in three places: pypts.logger.log.log (connection_driver.py, local_setup.py) becomes logging.getLogger(__name__); ignore_keyboard_interrupt (pypts.utilities.common, in connection_driver.py) gets a copy in pyhal; bench_sections() (local_setup.py, the lazy pypts.config_handler import) goes — the HAL reads the bench file itself (§9).
  • **pyhal/__init__.py stays import-light:** a driver's from pyhal import PSU runs in every driver process and must not pull in socket or client code. The client names (connect, get_device, run_scope, DEFAULT_PORT, ...) are reached through a module-level __getattr__ that imports client.py on first use (review 5).
  • The version in hello (D48) is importlib.metadata.version("pts-framework") for now (the distribution's version, from setuptools-scm), never pypts._version.
  • Our own code, unlike pyrade_xy_graph: no DEVIATIONS.md, under every quality gate.
  • **What stays in pypts:** core/hal_link.py (connect at startup, the close, status and the two buttons for View → HAL, the log sink), the run_scope() line in the Sequencer, and the View → HAL window in the GUI.
  • Its context file src/pyhal/pyhal.md (inline SPDX header) replaces src/pypts/hal/hal.md.

7. Protocol (public, TCP)

7.1 Three layers, one seam (Claude's call, so D7's "easy to change" holds)

  1. Typed messages: a dataclass per request and answer with a kind discriminator, one union per direction (ClientToHal, HalToClient), handled with match closed by unhandled() (CLAUDE.md convention). pyhal carries its own small unhandled() and a TRACE line per send/receive.
  2. The value domain: one recursive PlainValue type and one validator that names the path of anything outside it.
  3. The codec: JSON, one object per line (UTF-8, \n), allow_nan=False on output, and NaN/Infinity refused on input; deep nesting or huge integers count as a malformed line (review fix). Swapping the codec touches only this layer.

Sending (D30): send("close_all"), send("call", device="psu1", operation="output_off"). send() looks the kind up in one kind → dataclass table and builds the dataclass at once (a misspelt kind or field raises before anything is encoded), validates and encodes. A test checks the table covers both unions.

7.2 Connection and handshake

  • Bind to 127.0.0.1 only, on the fixed default port (D56; --port overrides it). On Windows bind with SO_EXCLUSIVEADDRUSE, never SO_REUSEADDR. The port taken → the HAL exits with an error naming it.
  • Handshake: the server's first message is hello: pid, the start nonce it was given (or null), version, the absolute path of its bench file and its SHA-256, the path of its log file (§9), the devices it has open, how many other clients are connected. A HAL shutting down sends an error instead (§6.2 step 6).
  • Maximum message size: 16 MB (D32). An answer that would exceed it is not sent: the HAL answers with an error (origin hal, 'op' ran, but its result is too large to send: N bytes.) and the connection stays open. The client refuses an oversized request itself, before sending, and keeps the connection (review fix). Only a malformed or oversized line arriving at either end closes the connection.
  • An answer goes only to the connection its request came in on (review fix): a client that reconnects never receives an older connection's result.

7.3 Requests and answers

  • One request outstanding per connection (D18), no request ids. The HAL sends nothing unprompted after hello: there is no HAL heartbeat (D47). A client therefore reads exactly one answer per request (none for beat).
  • Requests (D22, D55):
RequestAnswerQueued (D52)
open (device)opened (device type, operations); opens or reusesyes
call (device, operation, args, kwargs)result; opens the device first if it is closed (D44)yes
recover (device)recoveredyes
info (device)info (device type, operations, is open) — a round trip now, newyes
close (device)closedyes
close_allclosed_all, listing every device not torn down — newyes
shutdownbye, after close_all; then the HAL exitsyes
statusstatus (§8)no: answered by the connection thread
beatnoneno: only resets the watchdog (D53)
  • The queue (D52): one queue for all clients, one request thread, first in first out. Nothing locks a device between two requests, so two clients' calls to one device interleave request by request. close, close_all and shutdown wait their turn like any request.
  • Errors carry an origin:
    • driver — the driver raised; the client formats today's Device 'x': 'op' failed: Type: message;
    • hal — the HAL produced the whole message (timeout, stopped unexpectedly, not configured, could not be opened, cannot be sent, too large, shutting down); raised verbatim. (A HAL whose port is taken exits before it can answer anyone; the starter sees it in the startup file's tail.)
    • protocol — malformed request, value outside the domain, unknown kind; raised as DriverError("HAL protocol error: ...") and logged at ERROR.
    • The stale-handle refusal is produced in the client (§6.3), never by the HAL.
  • The test-code-facing DriverError texts in today's hal.md Failure table are kept. New: the connection closing while a request waits → DriverError("The HAL server closed the connection while 'op' was running on device 'x'."); that connection is not reopened (D28).

7.4 The value domain (D15)

  • JSON-native values: numbers, strings, booleans, null, lists, objects with string keys.
  • Tagged forms: {"$float": "nan" | "inf" | "-inf"}, {"$bytes": "<base64>"}, decoded back to float / bytes. A dict key starting with $ is refused, so a driver's own dict is never mistaken for one.
  • A tuple arrives as a list — a behaviour change for test code (step/step.md says so).
  • **Refused, with a DriverError naming the path:** non-string dict keys, numpy values (the validator checks exact types — numpy.float64 subclasses float), custom objects. An argument is refused in the client before anything is sent; a return value is refused in the HAL after the operation ran, and the text says so.
  • Integers beyond 2^53 lose precision for non-Python clients; pyhal.md says so.

7.5 Threads

  • HAL server:
    • an accept thread;
    • one connection thread per client: reads lines, answers status, resets the watchdog on beat (and on any line), puts every other request on the queue;
    • the request thread: takes the queue first in first out, runs one request, writes the answer to the connection it came from;
    • the watchdog (D53): a client silent for CLIENT_SILENCE_S (5 s) is dropped. A client with a request queued or running is never counted as silent: it is waiting for the HAL, not frozen, so a short connection that waits 50 s for closed_all is not dropped (review 5).
    • A client that is gone — dropped, or its connection closed or reset: its queued open / call / recover / info are removed; a request of its that is already running finishes and its answer is discarded; its queued close, close_all and shutdown stay and run (D47). The bench is left as it is (D36). Claude's call on what stays queued; the close relies on it (§6.4 step 1).
    • Socket writes go through one lock per connection, held for one line.
  • Client: two locks on the long connection (review 5). The request lock is held by whoever sends a request until its answer arrives (D18); the fence check happens under it (§6.3). The write lock is held for one line only, by a request's send and by the beat thread; the beat thread never takes the request lock, so beats go on during a long call. The thread that sent the request reads its answer itself: the HAL sends nothing unprompted, so no reader thread is needed (rev 4 had one for the HAL's heartbeats). A closed connection ends that read with DriverError (§7.3). One beat thread: beat every CLIENT_BEAT_S (1 s), under the write lock alone. One log tail thread (§9).
  • No client-side deadline (D57): a wait ends with the answer or with the connection closing.

All HAL constants live in pyhal (today in connection_driver.py: STARTUP_TIMEOUT_S 30 s, CALL_TIMEOUT_S 30 s, EXIT_TIMEOUT_S 5 s, RESCUE_TIMEOUT_S 10 s, LIVENESS_POLL_S 0.2 s). They bound the HAL's work, not the client's wait:

After Stop HAL, get_device() fails until PyPTS is restarted (D28).

9. Configuration, bench data and logs

  • **bench.ini** stays beside config.ini (D10). PyPTS passes its path to pyhal.connect(); the HAL reads the file itself with bench.py, anchoring relative driver files to the file's folder (today's anchor_driver_files(), moved). config_handler keeps owning the path and its discarded-file check: when PyPTS's bench.ini was discarded at startup, CORE does not connect, and get_device() raises today's text (bench.ini was discarded at startup, so this start has no devices: ...).
  • The port (D56) is pyhal.DEFAULT_PORT, a --port option and a connect() argument, not a config.ini key, so CONFIG_VERSION is untouched. PyPTS uses the default.
  • The HAL log (D16): the HAL process writes its own log file in --log-dir (default: a fixed per-user folder of pyhal's own), with the standard library only. Technician lines keep today's text (Device 'x' connected. ...). Driver processes' records reach it as today. The format is the builder's call, with two constraints: each record's level can be read back, and a multi-line record (a traceback) can be told from the next record.
  • PyPTS reads that file (D46). hello names it. The client's log tail thread starts at the file's end at connect time, reads new records every LIVENESS_POLL_S-like interval, and hands each to the log_sink given to connect(). CORE's sink re-logs it through PyPTS's log at its own level, as HAL: <message> (Claude's call on the prefix). run_scope()'s exit drains the tail to the file's end before it returns, so a run's teardown lines land in that run's log (the HAL writes a request's lines before it sends the answer). A script passes no sink: it reads nothing.
  • Why the drain works, and what it needs (checked in review 5): the sink re-logs inside CORE, and end_run_log()'s message and log records go to the Logger on one queue, in order. So a line re-logged before end_run_log() lands in the run log, given three rules:
    1. the drain calls the sink itself, synchronously, before it returns — handing lines to the tail thread is not enough;
    2. the drain emits the last record it holds too — a parser that holds a record back until the next record's header (for multi-line records) must flush at end of file;
    3. the drain and the tail thread share one lock, so no record is logged twice or out of order.
  • Log level: python -m pyhal --log-level LEVEL (a number or a name, TRACE = 5 included, defined in pyhal as PyPTS defines it in logger/levels.py). PyPTS passes its own level to a HAL it starts, so today's DEBUG call traces still reach its run log. A HAL found running keeps its own level.
  • Accepted consequence of D46 + D51: PyPTS's log also shows the HAL lines of other clients' requests made while it is connected.
  • PyPTS's run log still gets every DriverError test code sees. CORE logs at INFO that it connected to the HAL, started it or found it; pid, port and paths at DEBUG (logging_rules.md §5, review fix).

11. Scripts and standalone use

import pyhal

with pyhal.connect(bench="my_bench.ini") as hal:   # connect, or start a HAL
    print(pyhal.get_device("ssh1").execute("uname -r"))
# leaving the block: close_all; shutdown only if this script started the HAL (D38)
  • A script that never uses with: connect() registers an atexit that does the same (D54); leaving the with unregisters it.
  • By hand: python -m pyhal --bench FILE [--port N] [--log-dir DIR] starts a HAL in a console; it runs until Ctrl+C, its console is closed, or a shutdown.
  • **python -m pyhal --close-all [--port N] and --stop [--port N]** (D49): connect only, never start; send close_all (--stop sends shutdown, which runs close_all itself); wait for the answer and print the devices not torn down; exit non-zero when there were any or when no HAL answered. --bench, --port, --log-dir, --log-level and --nonce (set by a starting client, §6.2) are the other options.
  • A non-Python client implements one TCP connection, JSON lines, hello, the requests of §7.3, and a beat every second (a client with a request waiting is never dropped, §7.5). pyhal.md documents them with examples.

14. Known gaps that stay

  • PyPTS killed outright leaves instruments as they are (D36).
  • A HAL that freezes with its socket open freezes the test that waits on it (D57).
  • A HAL killed outright (TerminateProcess, SIGKILL) tears nothing down itself; its driver processes do when their Pipe closes, unless stuck in a call (D29).
  • A call blocked inside a driver is not interrupted by Stop; CALL_TIMEOUT_S bounds it.
  • Two clients' calls to one device interleave; nothing serialises a sequence of calls (D52).
  • close_all / shutdown from one client cut the others off (D51).
  • PyPTS's log shows other clients' HAL lines (§9).
  • A thread test code started in one run can get a fresh handle in the next run (§6.3).
  • Closing the console of a HAL started by hand gives it about 5 s on Windows (§6.5).
  • Anyone on the machine can reach the port; no authentication.
  • Large waveforms travel as JSON arrays; no side channel for bulk data.
