3. Leftovers, and what is executable

3.1 The un-refactored islands — the real problem

Three directories inside the new tree are pre-refactor code that was carried across and never touched. They are not stubs waiting to be filled in; they are old working files, and two of them no longer work at all. Every ruff finding worth having is in here.

stream_handler/StreamContainer.py executes on import and prints. Line 31 is container = GlobalContainer() at module scope, and GlobalContainer.__new__ opens with print("Something is creating the container object"). Importing this module — which is all it takes — writes to stdout from library code. It also carries a redundant global container at module level, an 18-line commented-out if __name__ == "__main__" block, parameters named Stream that shadow the class, and a kill() whose body is del(self), which does nothing at all. Nothing imports it. This is the single worst file in the new tree and the clearest candidate for deletion or for a move next to old_code/.

hmi/gui/XYGraph/XY_graph.py and simulated_signals.py are the same story one level up: they reference Stream, container, Simulated_sine_wave, csv and datetime without importing any of them, so the module raises NameError the moment those lines are reached, and XY_graph.py still ends in an executable if __name__ == '__main__':. They sit inside hmi/gui/, which is otherwise new code — a reader looking at the GUI package has no way to tell the two apart except by opening them.

tests/unit_tests/test_stream_handler.py already describes both as "a StreamContainer plus an XYGraph spike exist but are not integrated; Phase 3 promotes them", so the intent is on record. The question is only whether they should sit in the shipping package until then.

3.4 Dead-ish odds and ends

  • utilities/common.py — convert_string_to_int() has no production caller. The only users are its own three assertions in test_utilities.py. It also re-raises ValueError inside except ValueError without from, so the original context is dropped, and its value: str hint contradicts the TypeError branch that exists precisely to handle a non-string.
  • src/pypts/__main__.py has no trailing newline — three lines, the last one unterminated.
  • utilities/local_storage.py:46 — datetime.now() with no timezone (ruff DTZ005). Harmless for a filename, and the Monitor deliberately parses naive timestamps, so this is a "decide and silence it" rather than a bug.
  • No ruff configuration is committed. There is no [tool.ruff] in pyproject.toml and no ruff.toml, yet the code carries # noqa: BLE001, # noqa: DTZ007 and # noqa: B008 — codes from rule sets nothing enables. The suppressions read as documentation; nothing enforces the rules they suppress, and ruff check on a fresh clone has no agreed baseline.

3.5 Documentation that has drifted from the code

Three statements are now false. Flagged rather than fixed, per the rule about not silently working around a disagreement between the docs and reality.

  1. CLAUDE.md: "config.ini … ships as INFO". configuration_schema.py:94 ships DEBUG, deliberately and with a comment saying it reverts before v1.0. The doc describes the pre-refactor default.
  2. messages/messages.md: "PendingRequests has no user". The Sequencer constructs one (sequencer.py:63) and calls it (:141). What has no user is the asking half.
  3. debug_monitor/__init__.py: "The first two import no Qt and no running framework". True of trace_parser.py; false of liveness.py — see below.
Importing the Monitor's liveness fold imports the whole engine. liveness.py:43 is from pypts.core.core import HEARTBEAT_TIMEOUT_S, HMI, REPORT, SEQUENCER — four constants. Measured: importing that module loads 30 pypts modules, including sequencer.sequencer, report.report, all four config_handler modules and every link module. The intent is explicit and good ("the timeout is imported, never copied"), and log_source.py goes to the trouble of a function-level import specifically to keep the configuration out of the tool's import graph — which liveness.py then pulls in anyway, transitively. The four constants want a home that is not core.py.

4. Comments

This is the most unusual thing about the codebase and the hardest to give a single verdict on. The comments are, in kind, better than almost anything I would expect to find: they explain why, they name the defect a decision was a reaction to, and they warn about the thing the next person would otherwise get wrong. queue_wrapper.py's note that the trace uses %-args so the repr() is not computed below DEBUG is exactly the kind of comment that stops a well-meaning rewrite.

Four consequences, in the order they will bite:

  1. Prose rots, and some already has. The garbled log.py comment (§3.2) and the three false statements (§3.5) are all prose failures, not code failures. At 1.14 : 1 there is more surface to maintain than there is code, and every rename has to be performed twice.
  2. It is duplicated against the .md files. queue_wrapper.py's 159 lines of prose, messages/messages.md, messaging_overview.html and README.md all explain the transport. Four copies of one explanation is four things to update, and it is why the two documents disagreed about PendingRequests.
  3. Some of it is history rather than description. "Previously the HMI link had no branch for this at all", "which is how the old code lost the ErrorSeverity enum on every hop", "the old helper had if event:". This is genuinely valuable now, during a port where old_code is the reference. It stops being valuable the day the port is finished, and it will not remove itself. The commit message is the conventional home for it.
  4. A few comments encode coupling instead of documenting it. liveness.py's _note_core_opinion() matches on two literal log sentences from core.py and says so honestly ("fragile and known to be"). Saying it out loud does not make it less fragile — a reworded log line silently blanks the verdict column.
What I would not do: a blanket cut. The rationale comments are the reason a reader can follow decisions like the daemon threads, the single-writer Logger and the batching in receive(). The target is not "fewer comments" — it is one home per fact: mechanism in the module docstring, status and plan in the roadmap, catalogue in messages.md, and history in the git log.

6. Modern syntax, and what it costs to undo

You asked for old-school, clear, understandable code. The honest answer is that the new code uses a lot of recent Python, and it splits sharply into two groups: constructs the architecture is built out of, where "modernising away" means redesigning, and constructs that are just cleverness and would read better plainly.

6.1 Load-bearing — cannot be removed without a redesign

ConstructWhereWhat it is buying
match / case (3.10) 8 handlers: CORE ×3, HmiClient, Sequencer ×2, Report, Logger, CLI Together with unhandled() it is the routing mechanism, documented in CLAUDE.md, README.md and messages.md. The case Type(field=name) form also destructures in the same line it dispatches on.
@dataclass(frozen=True, slots=True)~30 message types Immutability and typo-safety of the whole message contract
A | B | C union types7 link unions The unions are the contract: the type checker's completeness check and test_messages.py's enumeration both read them
typing.Never / NoReturnunhandled() The compile-time half of exhaustiveness. Exotic, and the eight-line docstring explaining it is warranted.
Generic[Msg] + TypeVarQueueWrapper QueueWrapper[HmiToCore] is what stops a module sending on the wrong link
typing.get_args()log.py:62, test_messages.py Derives the control-message tuple from the union, so adding one cannot leave an isinstance check stale

My recommendation on this group is to keep all of it. Rewriting the eight match blocks as if isinstance(...) chains would be more familiar line by line and would lose the one property the design is built on — that a forgotten message is an error rather than silence. If you want this group changed anyway, that is a design decision and deserves its own conversation, not a cleanup pass.

6.3 Things that are already plain

Worth saying, because a cleanup pass should not disturb them: no walrus operator anywhere in the new code, no nested comprehensions beyond the two in template_writer.py, no metaclasses, no functools beyond @wraps, no async, no __slots__ hand-rolling, and every event loop is a plain while with a time.sleep(0.01). The control flow of the framework is genuinely simple to follow — the complexity is in the type layer, not in the logic.

7. Consistency

7.1 Two different ways of calling the logger

Both styles are in use, sometimes in the same file:

log.info("Run log: %s", log_file_path)                  # lazy, %-args    startup.py
log.info(f"Starting sequence '{sequence_name}'.")       # eager, f-string  core.py

startup.py, report.py:84 and config_handler.py:381 use %-args; core.py, sequencer.py, hmi_client.py, cli.py and gui.py use f-strings. queue_wrapper.py documents at length why the lazy form matters there. It matters much less at INFO than at DEBUG, so this is a readability call rather than a performance one — but it should be one call, not two.

7.2 The module lifecycle is logged in five different wordings

TextEmitted by
"Starting module..."Core, Sequencer, Report, GUI, and CLI — and CLI also logs "Starting CLI module..." nine lines later, so the CLI announces itself twice
"Stopping module..."Core, Sequencer, Report — from start()
"stopping module"Sequencer, Report — from stop(), lower case, no ellipsis
"Stopping module"HmiClient — capital, no ellipsis
"exited main event loop."Sequencer, Report — lower case, trailing full stop

Sequencer and Report emit "Starting module..." into a log whose process column says Core for both, because they are threads. They remain tellable apart by the filename:funcName field, so nothing is actually ambiguous — but the message itself carries no identity, and it is the message a human reads first.

7.3 Import order

Three files have unsorted import blocks (ruff I001): core.py (the links import sits between two link modules), startup.py, sequencer.py (run_events before core_sequencer_communication). All three are one ruff check --fix away, and nothing else in the refactored tree is.

7.4 Line length

No limit is configured, and 14 lines in the refactored modules exceed 100 characters — 4 in config_handler.py, 2 each in core.py and log.py, 1 each in six other files. Worth deciding a number and putting it in pyproject.toml alongside the ruff rules that the noqa comments already assume.
